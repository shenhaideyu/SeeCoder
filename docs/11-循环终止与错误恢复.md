# 循环终止与错误恢复

## 1. 为什么终止条件是 Agent 的核心

普通聊天在模型停止生成时结束；编程 Agent 还可能正在等待审批、运行命令、处理失败或准备下一轮。若把“模型这次不再输出”当作完成，会产生过早完成；若只等待模型主动说完成，则可能无限循环。

SeeCoder 通过显式终止条件、迭代预算、无进展检测和统一 finally 清理共同保证 Turn 最终收敛。

## 2. 正常终止

### 2.1 无工具调用

模型返回正常文本且没有 tool calls 时，Core 将其视为最终回答并完成。这支持只读解释任务，不强迫每个回答调用 `finish`。

### 2.2 finish 工具

修改型任务应调用 `finish({summary,verification})`。Zod 要求 summary，verification 默认为数组。真实评测可以要求出现 finish、写入和命令证据，避免只有一句“已完成”通过质量门禁。

## 3. 输出截断

`finishReason=length` 表示输出达到上限，不表示任务完成。Core：

1. 记录本轮 assistant 文本。
2. 注入“不要重复长篇分析，执行最小动作并 finish”的恢复提示。
3. 强制压缩上下文。
4. 继续下一轮。
5. 连续三次 length 后以 `output_limit` 失败。

设置上限能防止模型持续生成不完整长文并消耗资源。

## 4. 迭代上限

主 Agent 最多 24 轮，子 Agent 最多 6 轮。循环耗尽且未完成时，Turn 状态为 `limitReached`，错误码 `iteration_limit`。不能为了让 UI 显示绿色而把它转换为 completed。

## 5. 无进展检测

普通失败工具调用增加 `noProgress`；成功调用清零。连续三次没有成功动作时失败。探索预算信号不计为普通失败，因为它是 Harness 主动要求重新规划；否则一次受控限制可能直接触发错误终止。

此外，连续只读探索有独立的 4/7 轮软硬预算，解决“工具都成功但没有推进任务”的另一类无进展。

## 6. 用户取消

`cancelTurn` 中止 Turn AbortController，并传播到：

- 当前模型 fetch 和 retry sleep。
- commandRunner 与子进程树。
- 所有父 Turn 匹配的子 Agent。
- 待审批 Promise，按拒绝解决。
- 待输入 Promise，按取消解决。

Core 捕获取消后生成 `turn.cancelled`，而不是 `turn.failed`。finally 删除活动 Turn 映射，允许用户重新运行。

## 7. 工作区切换

工作区切换调用 `cancelAll`，等待中的审批和输入被解决，所有控制器中止，然后销毁旧 Core 并创建绑定新 WorkspacePolicy 的 Core。这样旧任务不能在用户切换后继续写原工作区。

## 8. 错误模型

### ToolResult 错误

工具预期内失败使用 `{ok:false,error:{code,message,retryable},durationMs}`，并回填模型。例如 `invalid_args`、`patch_failed`、`command_failed`。它不会立刻终结 Turn，模型可以修正。

### AgentRunError

模型故障、取消、输出上限等控制 Core 生命周期的错误使用 AgentRunError。它携带 code 和 retryable，最终形成 `turn.failed` 或 `turn.cancelled`。

### 未知异常

意外异常归一化为 `agent_error`，消息使用 Error.message 或“未知错误”。这保证 UI 总能得到终态，但日志仍应保存足够定位信息。

## 9. 模型错误

- 缺少 Key：`missing_api_key`，不可重试。
- HTTP 401 等：`http_<status>`，按状态判断。
- 限流/网关错误：Provider 内最多重试三次。
- 网络失败：`network_error`。
- 空响应体：`empty_response`。

Provider 重试耗尽后只返回一次 error 事件，由 Core 决定 Turn 失败，避免重试逻辑散落在 UI 和 Core。

## 10. 工具错误恢复示例

```text
模型发出非 unified diff
→ apply_patch 返回 patch_failed
→ ToolResult 回填
→ 模型下一轮改用标准 diff
→ 修改成功
→ 测试失败 command_failed
→ 模型读取 stderr 并调整命令/代码
→ 测试成功
```

错误是 Observation，而不是一律异常退出。只有持续无进展或不可恢复错误才终止。

## 11. 应用异常中断恢复

应用关闭时内存控制器消失。下次 `hydrateThread` 查找最后一个 `turn.started`；若没有匹配 completed/failed/cancelled，则补写一次：

```text
status = failed
code = interrupted
retryable = true
```

这不会自动续跑，因为无法证明上次副作用执行到何处。保守失败并让用户重试比猜测续跑更安全。重复 hydrate 不会重复补写。

## 12. finally 清理

无论成功或失败，Core 最终清理 controllers、activeThreadTurns、turnModes、executedCalls，并解决该 Turn 遗留审批。没有这一层会出现 UI 已失败但后台 Map 仍认为任务运行的僵尸状态。

## 13. UI 错误呈现

普通用户看到“发生了什么、影响、建议动作”，技术 code 和原始 ToolResult 放在详情。Trace 按轮次汇总真正失败；`exploration_budget_exhausted` 显示“已限制”而不是红色错误。

## 14. 当前限制

- 无自动从 Checkpoint 重启整个 Turn；用户需要明确恢复并重试。
- 无错误策略表驱动的工具级自动重试，模型负责根据 Observation 修正。
- 非幂等外部命令即使 callId 防重，也不能防止命令自身部分完成。
- 24/6/4/7 等预算目前是经验值，需要真实 Eval 持续校准。

## 15. 完整决策表

| 条件 | 是否继续模型循环 | Turn 结果 |
| --- | --- | --- |
| 正常文本、无 calls | 否 | completed |
| 任一 calls | 是，除非 finish 成功 | running |
| finish 成功 | 否 | completed |
| finish 参数非法 | 是，作为 invalid_args observation | running |
| length 第 1–2 次、无 calls | 是，强制压缩 | running |
| length 第 3 次 | 否 | failed/output_limit |
| 模型 retryable error 已由 Provider 耗尽 | 否 | failed/model code |
| 普通工具失败不足 3 次 | 是 | running |
| 连续 3 次无成功工具 | 否 | failed/turn_failed |
| 24 轮耗尽 | 否 | limitReached/iteration_limit |
| AbortSignal | 否 | cancelled |
| 崩溃后 hydrate 发现无终态 | 不续跑 | failed/interrupted |

## 16. 状态转换触发者

Core 是 TurnStatus 唯一写者。Renderer 只能请求 start/cancel/resolve，不得自行把任务改成 completed。Provider 只能产生 ModelEvent，Tools 只能产生 ToolResult。该单写原则避免不同层争夺状态。

等待审批或输入时，Turn 对象在内存中改为 waiting 状态，但当前没有单独持久化 `turn.status.changed` 事件；恢复依赖 approval/input 请求事件。这是协议可观测性的一个不足，未来如新增状态事件，应保持旧终态兼容。

## 17. 三种“成功”不能混淆

```text
HTTP 200             仅表示模型请求成功
ToolResult.ok=true   仅表示一个工具成功
turn.completed       表示 Harness 认为本轮结束
```

测试命令退出 0 也只证明该命令成功，不自动证明全部用户验收条件满足。成熟 Agent 的可靠性来自把这些层级分别记录，而不是用一个绿色勾覆盖所有含义。

## 18. 失败恢复边界

可在同一 Turn 内恢复的错误：参数非法、补丁冲突、命令非零、审批拒绝、探索预算。模型获得 ToolResult 后可选择新动作。

终结 Turn 的错误：模型连接最终失败、连续截断、迭代上限、连续无进展、用户取消、意外异常。它们可能标记 retryable，但重试需要新 Turn，由用户明确触发，避免复用不确定的副作用状态。

## 19. Error Taxonomy 映射

当前协议以稳定 code 为主，没有单独 category 字段。逻辑映射如下：

| 类别 | code 例子 | 责任边界 |
| --- | --- | --- |
| USER_ERROR | approval_denied、输入为空 | 用户决策/IPC |
| MODEL_ERROR | missing_api_key、http_*、network_error | Provider |
| TOOL_ERROR | patch_failed、command_failed、spawn_error | Tools |
| POLICY_ERROR | path_denied、plan_read_only | Core/Tools |
| TIMEOUT | timeout、output_limit、iteration_limit | Tools/Core |
| CANCELLED | cancelled | 全链路 AbortSignal |
| SYSTEM_ERROR | interrupted、turn_failed | Core/恢复 |

新增 category 可提升 UI 一致性，但不能替代具体 code；模型恢复通常需要知道是 patch_failed 还是 command_failed。

## 20. 完成证据的新鲜度

理想规则是“最后一次源码变更之后至少有一次相关验证成功”。当前 Ledger 只保存测试字符串，没有 ChangeSet 版本号关联，`finish.verification` 也未自动对照 ToolResult。因此 Core 可以保证 finish 调用存在，却不能形式化证明验证是最新的。

后续最小演进可记录 `changeRevision`，每次 changes.created 加一，成功 run_command 保存 revision；finish 时若修改型任务没有同 revision 验证，则返回 `verification_stale`。在实现前，真实 Eval 应检查事件顺序作为外部门禁。

## 21. 取消时序

取消可能发生在模型流、审批、用户输入、子 Agent 或命令阶段。所有路径共享父 AbortController：

```text
cancelTurn
├─ abort parent
├─ abort matching children
├─ resolve approvals as deny
├─ resolve user inputs as cancelled
└─ runTurn catch/finally → turn.cancelled + cleanup
```

工具可能在收到 abort 与实际 OS 进程退出之间存在短暂窗口，因此测试应验证最终无残留进程，而非只验证 cancel IPC 返回。

## 22. 错误注入测试

- Provider 在首 token 前抛网络错误。
- Provider 输出半截 tool arguments。
- Provider 连续三次 length。
- patch 第二个 hunk 上下文冲突。
- command 输出大量 stdout 后超时。
- approval 等待中取消。
- ask_user 等待中切换工作区。
- 写入完成后应用被强制退出，再 hydrate。
- 恢复前人工修改目标文件触发 hash conflict。

每个用例至少断言终态事件、活动 Map 清理、文件最终内容和是否存在后台进程。

## 23. 为什么不自动无限恢复

无限重试会放大费用、重复副作用并掩盖配置错误。自动回滚所有失败也不正确，因为测试失败后的代码改动正是下一轮修复所需现场。SeeCoder 的策略是：短暂网络错误在无副作用阶段有限重试；预期工具错误作为 observation；生命周期错误明确终止并保留证据。
