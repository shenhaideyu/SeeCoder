# 源码级端到端调用链

本文从一次真实点击出发，解释 SeeCoder 中数据、控制权与错误如何跨越 Renderer、Preload、Main、Agent Core、Model、Tools 和 Storage。它是排查“用户点击发送后究竟发生了什么”的入口。

## 1. 组件与代码入口

| 层 | 入口 | 只负责什么 | 明确不负责什么 |
| --- | --- | --- | --- |
| Renderer | `apps/desktop/src/renderer/main.tsx` | 收集意图、渲染事件、发起明确 IPC | 文件系统、密钥、Agent 状态机 |
| Preload | `apps/desktop/src/preload/preload.ts` | 暴露固定 API、转发 IPC | 任意 Node API、业务判断 |
| Main | `apps/desktop/src/main/main.ts` | 进程边界、工作区、配置、IPC、日志 | 推理循环细节 |
| Core | `packages/agent-core/src/index.ts` | Turn 生命周期、上下文、工具调度、终止 | HTTP 与文件实现细节 |
| Model | `packages/model/src/index.ts` | 请求序列化、SSE、重试 | 工具权限与任务完成判断 |
| Tools | `packages/tools/src/index.ts` | 本地能力、路径策略、进程控制 | 会话与 UI |
| Storage | `packages/storage/src/index.ts` | 追加事件、元数据、状态、快照 | 派生 UI 状态 |

这种边界的核心不是目录整齐，而是确保模型永远无法直接跨过 Main 的可信边界。

## 2. 创建 Thread

```text
用户点击“新建任务”
→ Renderer 调 window.seecoder.thread.create(title)
→ Preload invoke thread:create
→ Main 校验 title 并调用 core.createThread
→ Core 创建 Thread、空 ModelMessage[]、ContextLedger
→ Store 原子写 meta.json
→ Core 持久化并发布 thread.created
→ Main 转发 seecoder:event
→ Renderer 按 threadId 更新左栏和当前任务
```

Thread 与 workspacePath 永久绑定。加载或列举时 Core 再次比较规范化工作区路径，不能仅依赖 UI 当前选择。

## 3. 启动 Turn

`turn:start` 的输入是 `threadId`、用户文本和可选附件。Core 执行顺序具有安全含义：

1. 确认 Thread 存在且属于当前工作区。
2. 确认该 Thread 没有活动 Turn，防止同一任务并发写入。
3. 固化本 Turn 的 ExecutionMode；运行中切换全局模式不改变已启动 Turn。
4. 附件通过 WorkspacePolicy 解析；最多 4 个，文本最多 40,000 字符。
5. 更新 ContextLedger.goal。
6. 先写 `turn.started` 和用户 Item，再异步进入 `runTurn`。

IPC 可以快速返回 turnId，长任务不占用 Electron invoke 请求。实际进度由事件流驱动。

## 4. 一轮模型请求

```text
runTurn(iteration)
├─ 检查 AbortSignal
├─ 注入排队 Follow-up
├─ 必要时加入探索收敛提醒
├─ compactMessages
├─ systemPrompt + context + tool schemas
├─ model.requested
├─ provider.stream
│  ├─ textDelta       → message.delta（仅实时）
│  ├─ toolCallDelta   → 按 callId 聚合
│  ├─ usage           → usage.updated
│  ├─ retry           → 统计次数
│  └─ completed       → finishReason
├─ model.completed
└─ 保存完整 assistant 文本或 toolCalls
```

必须先保存 assistant 的完整 tool calls，再保存 tool results。若只保存结果，恢复后生成的 Chat Completions 消息缺失配对关系，兼容服务会拒绝请求。

## 5. 工具调用链

每个工具调用经过同一条管道：

```text
聚合 arguments 字符串
→ JSON.parse
→ ToolRegistry 查找
→ Zod safeParse
→ Plan 副作用硬拒绝
→ WorkspacePolicy / commandRisk
→ 自动执行或等待审批
→ definition.execute / Core 内建调度
→ ToolResult
→ tool.completed
→ ChangeSet / Ledger 等派生动作
→ tool role message 回填模型
```

`delegate`、`ask_user`、`checkpoint`、`review_changes` 和 `compact_context` 虽注册为工具，但由 Core 拦截执行，因为它们需要访问 Turn 生命周期；文件与命令工具不需要会话状态，留在 Tools 包中。

## 6. 写文件的完整路径

以 `write_file` 为例：

1. 模型提出 path/content，并不直接写盘。
2. Zod 验证类型；权限策略决定是否审批。
3. WorkspacePolicy 同时做词法与真实路径检查。
4. 工具读取 before，写同目录临时文件后 rename。
5. 返回 `{kind:"changes",files:[{path,before,after}]}`。
6. Core 创建 ChangeSet，更新 Ledger.changedFiles。
7. Store 保存 before snapshot。
8. Core 创建带 beforeHash/afterHash 的 Checkpoint。
9. UI 同时获得 tool.completed、changes.created、checkpoint.created。

职责分离使新写工具只需返回标准 ChangeFile，即可复用审计与恢复逻辑。

## 7. 命令与流式输出

`run_command` 在独立 PowerShell 子进程执行。stdout/stderr 每个 chunk 先进入 `tool.output` 供 Terminal 实时显示，同时在内存中分别保留最后约 1 MiB；进程退出后形成一个 ToolResult。取消和超时会终止进程树，而非只结束 shell 父进程。

`tool.output` 不进入模型消息历史；模型只接收最终裁剪后的 ToolResult。这样 UI 可以实时，模型上下文不会被数百个日志 chunk 污染。

## 8. 审批与用户输入

审批和 `ask_user` 都使用 Promise 暂停，而不是轮询：

```text
Core 设置 waitingApproval/waitingInput
→ 发布请求事件
→ 保存 resolver
→ runTurn await
→ Renderer 提交 resolve IPC
→ resolver 被调用
→ 状态恢复 running
→ 结果作为 observation 回填模型
```

取消 Turn 时这些 Promise 必须被主动解决，否则 runTurn 永远挂起，形成僵尸任务。

## 9. 完成与失败

成功路径最终产生 `turn.completed`；失败路径产生带稳定错误码的 `turn.failed`；取消单独产生 `turn.cancelled`。finally 无条件删除 controller、activeThreadTurns、turnModes、callId 缓存和残留审批。

UI 不应从“是否还有流式文字”推断完成，而应只认终态事件。日志也以同一事件为关联点。

## 10. 应用重启

重启不续跑进程。`hydrateThread` 从 meta、state、events 重建可审计状态，清理不合法工具消息组；发现 started 但无终态的 Turn 时补写 `interrupted`。原因是崩溃时无法证明外部命令或写入处于哪个阶段，自动续跑可能重复副作用。

## 11. 调用链不变量

- Renderer 不拥有文件、密钥和进程能力。
- 一个 Thread 同时最多一个主 Turn。
- 每个 tool 消息必须匹配同组 assistant tool call。
- 每个请求的模式在 Turn 启动时固定。
- 每个 ToolCall 至多得到一个持久化执行结果。
- 每个 started Turn 最终必须有 completed、failed、cancelled 或恢复生成的 interrupted。
- 每个文件变更都必须可映射到 ChangeSet。

## 12. 诊断顺序

当 UI 看似卡住时，按以下顺序定位：

1. `turn.started` 是否存在：判断 IPC 和 Core 启动。
2. `model.requested/completed` 是否成对：判断模型链路。
3. `assistant.tool_calls` 是否存在：判断解析结果。
4. `tool.requested/completed` 是否成对：判断审批或工具阻塞。
5. 是否存在 waitingInput/waitingApproval：判断用户决策点。
6. 最后是否有 Turn 终态：判断清理与 UI 收敛。
