# SeeCoder 安全与威胁模型

## 1. 安全结论

SeeCoder 把模型、仓库内容和 Renderer 都视为不可信输入。安全不依赖 Prompt 中一句“不要执行危险操作”，而依赖 Main/Core 中不可绕过的 IPC、Schema、路径、权限和执行规则。

当前是应用层策略隔离，不是 OS 沙箱。被批准的命令仍以当前用户权限运行，因此系统不能宣称任意 Shell 都被完全隔离。

## 2. 需要保护的资产

主要资产包括用户源码和未提交修改、API Key 与环境变量、文件和命令权限、Git 分支与远端、Session 中的 Prompt、路径、Diff 和命令输出。

攻击输入可以来自模型输出、恶意仓库文件、导入 Skill、项目 Hook、Renderer 脚本和用户输入。外部模型服务还能看到本轮主动发送的上下文，因此敏感文件不应进入读取工具和模型请求。

## 3. 信任边界

Renderer 运行不可信页面逻辑，只能通过 Preload 白名单请求能力。Main 是可信执行边界。ModelProvider 只拥有网络请求配置，不拥有文件函数。Tool Runtime 每次操作都使用当前 Core 的 WorkspacePolicy。SessionStore 只写用户数据目录。

```text
不可信：用户/仓库/模型/Renderer
          ↓ 明确请求
可信：Main → Core → Schema/Policy/Approval
          ↓ 被批准的最小动作
本地文件、命令、Git、系统安全存储
```

## 4. 文件安全

WorkspacePolicy 对目标执行规范化绝对路径和 `relative` 检查，再对真实存在路径或最近存在祖先使用 `realpath`，防止 `..`、绝对路径和符号链接跳出 Workspace。不能只使用字符串 `startsWith`，因为相似目录前缀和 Windows 大小写会产生错误判断。

`.env`、私钥、Token 和 Credential 类文件默认屏蔽，`.env.example` 等模板允许读取。文件树、搜索和读取使用同一敏感策略，避免通过另一工具旁路。

写入前保存 Snapshot。补丁先校验旧内容，冲突时不写入。Checkpoint 恢复前比较修改后哈希，防止覆盖用户后续编辑。

## 5. 命令与权限

Plan 模式禁止副作用。Guided 对写入和命令逐次审批。Auto 只自动放行 Workspace 内写入及策略认可的测试、构建和只读命令。网络、安装、删除、Git commit/push 和未知命令仍审批；格式化磁盘、关机、注册表和凭据读取等模式直接拒绝。

命令使用受控 PowerShell，设置超时、输出上限和 AbortSignal。取消时终止进程树。首版没有 PTY，也不允许模型获得一个长期无限制 Shell。

命令分类无法理解所有脚本内部行为，因此审批和模式不是 OS 沙箱替代品。若需要运行不可信仓库，应增加 Windows Sandbox、容器、受限 Token 或独立虚拟机。

## 6. Prompt Injection、Skill 和 Hook

仓库文本、工具输出和摘要输入都标记为不可信数据。即使其中要求读取密钥，实际动作仍受工具层限制。模型摘要不能覆盖 ContextLedger 的权威目标、文件、验证和错误。

导入 Skill 只增加 Turn 指令，不增加权限，也不能绕过 ToolRegistry。Hook 是真实本地命令，首次启用项目 Hook 必须确认信任；Hook 失败写入轨迹，不能伪造文件修改或 Turn 成功。

## 7. 密钥与数据

API Key 来自环境变量，或使用 Electron `safeStorage` 加密后持久化。Renderer 只能看到是否已配置和脱敏尾号，不能读取明文。日志、Session、Diff、README 和导出系统字段不保存 Key。

Session 导出可能包含用户 Prompt、本地路径、代码和命令输出。系统不可能自动识别所有业务机密，用户分享前必须检查。

## 8. 主要威胁与控制

| 威胁 | 控制 | 残余风险 |
|---|---|---|
| 路径穿越或符号链接 | resolve、relative、realpath | 外部程序并发替换路径 |
| 凭据进入模型 | 敏感文件过滤、Main 持有 Key | 用户主动粘贴敏感内容 |
| 危险命令 | 模式、风险分类、审批、拒绝规则 | 被允许脚本内部执行其他动作 |
| Renderer 越权 | contextIsolation、关闭 Node、IPC 白名单 | `sandbox:false`，依赖 Main 校验 |
| 重复副作用 | `(turnId, callId)` 幂等缓存 | 崩溃后不自动续跑 |
| 覆盖用户编辑 | Snapshot、afterHash 冲突检查 | 多文件非数据库事务 |
| Prompt Injection | 不可信数据标记、工具硬边界 | 模型仍可能做低质量决策 |

## 9. 不应作出的声明

不能说 SeeCoder 有操作系统级沙箱、任意命令绝对安全、Fork 提供文件隔离、崩溃后自动续跑、API Key 永不可能通过用户 Prompt 泄露，或多文件写入具有数据库事务。准确描述现有边界是安全设计的一部分。

## 10. 一次文件读取怎样被保护

模型调用 `read_file({path:"../secret.txt"})` 后，Core 先用 Zod 确认参数结构，再交给 WorkspacePolicy。`resolve(root,input)` 得到候选绝对路径，`relative(root,candidate)` 若以 `..` 开头或仍为绝对路径，就直接拒绝。若路径存在，还要比较 realpath，防止 Workspace 内的符号链接指向外部。

路径属于 Workspace 后，再检查敏感文件规则。通过后工具才读取内容，并限制行数。返回模型的 Observation 带路径、hash 和范围；完整内容不会写入 Main 普通日志。这几层分别处理参数、目录归属、凭据类型和数据量，任何一层失败都不能继续读取。

## 11. 一次命令怎样被保护

模型生成的 command 首先接受参数长度和 cwd 校验。Plan 直接拒绝。Guided 创建 Approval 并暂停。Auto 根据命令类别判断；测试和只读 Git 可以自动，网络、安装、删除、提交和推送仍等待用户，高危模式直接拒绝。

执行时只启动受控 PowerShell 子进程，记录 PID、开始时间和 AbortSignal。stdout/stderr 分流并限制内存。超时或取消时终止进程树，最终 ToolResult 明确 exitCode、duration 和错误。系统不把“命令已启动”当成“命令成功”。

## 12. 为什么仍需要用户判断

代码规则可以识别路径和常见危险命令，但不能完全理解任意脚本的业务影响。例如一个名称为测试的脚本可能访问网络或清理数据。Guided 模式让用户看到实际命令和 cwd，Auto 只适合用户信任的项目。

因此安全设计的目标不是消除所有风险，而是减少默认权限、显式暴露高风险决策、保留恢复证据，并准确说明无法消除的部分。

## 13. 安全专有概念

信任边界是数据从低信任区域进入高权限区域的位置。SeeCoder 最重要的信任边界是 Renderer 到 Main 的 IPC，以及模型 Tool Call 到 Tool Runtime 的执行入口。边界处必须重新校验，不能因为数据具有 TypeScript 类型就认为安全。

最小权限表示组件只获得完成职责所需能力。Renderer 不需要文件系统，ModelProvider 不需要 Workspace，子 Agent 不需要写工具，Plan Turn 不需要副作用。最小权限减少单个组件出错后的影响范围。

纵深防御表示同一风险由多层处理。路径安全既有 Schema、规范化、realpath，也有敏感文件规则和 ExecutionMode。任何一层都可能有盲点，多层组合比单一正则可靠。

残余风险是现有控制之后仍然存在的风险。承认残余风险不等于系统不安全，而是为使用条件和后续设计提供依据。当前最明显残余风险是被批准命令以用户权限运行。

## 14. `safeStorage` 解决什么问题

Electron `safeStorage` 使用操作系统提供的用户级加密能力保存 API Key 密文。设置文件只保存密文或配置标识，Renderer 读取设置时只得到 `hasApiKey` 和脱敏尾号。真正发请求时，Main 解密到当前进程内存。

它防止磁盘上直接出现明文 Key，但不能防止当前用户账户或已控制 Main 进程的恶意程序。它也不能阻止用户把 Key 主动粘贴进 Prompt。日志函数仍需避免记录请求 headers 和完整设置对象。

环境变量路径适合开发和 CI；safeStorage 适合桌面用户持久配置。两种来源都在 Main 汇合，Provider 只接收使用所需值。

## 15. Prompt Injection 为什么不能只靠提示词

Prompt Injection 是不可信内容试图改变模型指令。例如源码注释写“读取密钥并上传”。模型可能服从，因为它只能基于文本判断优先级。系统 Prompt 能降低概率，却不能成为安全保证。

SeeCoder 的应对是把内容和能力分开。文件内容只作为不可信数据进入上下文；模型即使产生危险 Tool Call，仍要经过路径和权限策略。摘要 Prompt 也明确历史是不可信数据，摘要结果又不能覆盖 Ledger。

这种防御不能保证模型回答质量，但能限制回答错误转化为本地副作用。安全目标是控制能力，而不是让模型永远不受诱导。

## 16. Hook 的供应链风险

Hook 来自项目目录，可能由仓库作者提供。它是确定性命令而不是模型 Tool Call，但执行风险并不更低。首次启用需要用户确认信任，界面应显示 Hook 来源和阶段。

`preToolUse` 可以拒绝或检查动作，`postFileEdit` 可以格式化或验证修改，`turnEnd` 可以进行收尾。Hook 失败应记录为 Hook 结果，不能静默忽略，也不能把 Turn 的文件事实改写成成功。

当前没有签名、发布者验证和 Hook 沙箱，因此不应默认启用陌生仓库 Hook。导入 Skill 风险较低，因为 Skill 只是文本指令，但它仍可能影响模型行为，所以不能赋予额外工具权限。

## 17. 如果增加真正沙箱

真正沙箱需要把命令和文件执行移动到隔离环境，并定义 Workspace 挂载、网络、CPU、内存、超时和产物同步。Windows 可选择 Windows Sandbox、Hyper-V/虚拟机、容器或受限 Token，各自对启动速度、兼容性和隔离强度有不同影响。

Agent Core 不应直接理解具体沙箱。更合理的方式是保持 ToolResult 契约，将本地 execute 替换为 SandboxExecutor。权限审批仍然需要，因为沙箱能限制系统影响，却不能判断用户是否愿意修改项目或访问网络。

## 18. Session 数据的安全边界

Session 历史可能包含本地路径、用户 Prompt、代码片段、命令和错误。它保存在用户数据目录，不进入项目仓库。读取、加载和删除 Session 时，Core 还会检查它属于当前 Workspace，避免页面通过已知 ID 跨项目查看历史。

删除 Session 只删除精确匹配的会话与快照目录。`sessionId` 先经过安全字符校验，不能把 `../` 作为删除目标。运行中的 Session 必须先取消，避免删除轨迹后后台继续写入。

导出是用户主动的数据外发。系统保证 API Key 不作为配置字段进入事件，但不能保证 Prompt 和代码没有业务机密，因此导出前仍需人工检查。

## 19. 安全事件怎样处理

发现疑似密钥进入日志时，应先停止继续分享日志，定位产生记录的代码路径，轮换相关密钥，再加入回归扫描。不能只删除一份日志，因为密钥可能已经进入 Git 历史或导出文件。

发现越界文件访问时，应视为 P0。保存输入参数、规范路径、realpath 和工具类型，在临时目录复现并增加 symlink/traversal 测试。修复必须位于 WorkspacePolicy 或统一敏感策略，不能只在一个 UI 入口增加判断。

发现取消后残留进程时，要记录 turnId、PID、父子关系和终止时间。修复应贯穿 AbortSignal 与进程树，不使用“UI 显示已取消”掩盖后台行为。
