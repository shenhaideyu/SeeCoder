# 模型协议与流式输出解析

## 1. Provider 抽象

Core 只依赖：

```ts
interface ModelProvider {
  stream(request: ModelRequest, signal: AbortSignal): AsyncIterable<ModelEvent>;
}
```

异步迭代器天然表达流式事件和背压，也容易用 Fake Provider 测试。Core 不依赖 HTTP、DeepSeek 或 SSE 细节，设置更新时可以替换 Provider 而不重建 Thread 状态。

## 2. 请求模型

ModelRequest 包含角色消息、函数工具、模型名、temperature 和 maxOutputTokens。Provider 将内部 camelCase 转为 Chat Completions 的 snake_case：

- `toolCallId → tool_call_id`
- `toolCalls → tool_calls`
- 图片 ContentBlock → `image_url` data URL

请求发送到 `<baseUrl>/chat/completions`，启用 `stream: true` 与 `stream_options.include_usage`。

## 3. 为什么使用原生 fetch

原生 fetch 已支持 HTTPS、ReadableStream 和 AbortSignal，不需要供应商 SDK。直接实现能展示考核关注的重试、流解析和工具协议，也避免 SDK 版本把消息格式差异隐藏在内部。

代价是需要自行维护兼容细节；因此 Provider 保持小而独立，并有碎片化 SSE 测试。

## 4. SSE 字节流解析

网络 chunk 不等于 SSE 行。解析器维护字符串 buffer：

```text
reader.read bytes
→ TextDecoder(stream=true)
→ append buffer
→ split CRLF/LF
→ 保留最后一个不完整行
→ 只解析 data: JSON
→ data: [DONE] 结束
```

完整流结束后再尝试解析剩余 buffer。空行、非 data 行和无法解析的完整行被忽略。当前实现不是严格 SSE 语法解析器，不处理多行 `data:` 合并或 `event:` 字段；这符合主流 Chat Completions 返回格式，但属于兼容边界。

## 5. 文本增量

`choices[0].delta.content` 转成 `textDelta`。Core 立即发 `message.delta` 给 UI，同时累积本轮完整文本。流结束后只将 `message.completed` 持久化，避免每个 token 一次磁盘写入。

## 6. Tool Call 增量

一次工具调用的 id、name 和 arguments 可能分散在多个 SSE chunk。Provider 用 OpenAI `index` 维护 `index → callId`，每个 chunk产生：

```ts
{ type: 'toolCallDelta', callId, name?, argsDelta }
```

Core 再按 callId 聚合 name 与 arguments 字符串。只有流结束后才 JSON.parse；在半截 arguments 上解析必然产生伪错误。

多工具调用使用不同 index/callId 独立累积。若服务没有提供 id，Provider 生成稳定的 `call-<index>` 作为本轮兜底。

## 7. 参数解析与校验

Core 对完整 arguments 执行 JSON.parse。失败时不是执行猜测结果，而是构造 `__invalid` 输入，让对应 Zod schema 产生 `invalid_args`。模型收到结构化错误后可以重试。

这形成两道边界：JSON 只解决语法，Zod 解决字段、类型、枚举、长度和数值范围。

## 8. Usage 与 Finish Reason

usage 转为输入/输出 token 事件，UI 和日志记录每轮成本。`finish_reason` 转为 `completed` ModelEvent，但 Core 不直接将所有 finish reason 当成任务成功：

- `length`：输出截断，进入恢复。
- tool calls：执行工具后继续。
- 无工具的正常文本：结束 Turn。
- `finish` 工具成功：显式完成。

## 9. 重试

HTTP 429、502、503、504 和网络异常最多尝试 3 次。退避为 `250ms × 2^attempt + 0–100ms jitter`。每次重试发出 `retry` 事件，最终模型完成事件记录 retries。

4xx 参数、鉴权错误通常不可重试，立即返回 `http_<status>`。响应正文最多读取 1,000 字符，防止服务端错误页污染日志和 UI。

## 10. 取消

同一个 AbortSignal 同时传给 fetch 和重试 sleep。取消可中断正在读取的响应，也可清除退避 timer。Provider 产生 `cancelled`，Core 将其映射为 Turn 取消而不是普通模型故障。

## 11. 副作用与模型重试的边界

HTTP 请求重试只发生在工具执行前。工具执行完成并写回历史后，Core 不因网络问题自动重放该工具；相同 callId 还有 Turn 内幂等缓存。这避免“模型响应丢失导致写文件执行两次”。

## 12. 兼容性限制

- 首版只支持 Chat Completions，不支持 Responses 或 Anthropic 原生协议。
- 默认读取 `choices[0]`，不处理多候选。
- 假定 tool calls 使用 OpenAI 兼容 delta 结构。
- 某些服务不支持 `stream_options.include_usage`，可能没有 token 数据。
- 当前 `parseJsonLine` 忽略畸形完整行，不会产生专门 parser_error；严重异常通常最终表现为空响应或不完整结果。

新增其他协议时应实现新的 ModelProvider，而不是在 Core 中加入供应商分支。

## 13. 请求线格式示例

内部消息：

```ts
{
  role: 'assistant',
  content: '',
  toolCalls: [{ id: 'call-7', name: 'read_file', arguments: '{"path":"src/a.ts"}' }]
}
{
  role: 'tool',
  toolCallId: 'call-7',
  toolName: 'read_file',
  content: '{"ok":true,...}'
}
```

发送时转换为：

```json
{"role":"assistant","content":"","tool_calls":[{"id":"call-7","type":"function","function":{"name":"read_file","arguments":"{\"path\":\"src/a.ts\"}"}}]}
{"role":"tool","content":"{\"ok\":true,...}","tool_call_id":"call-7","name":"read_file"}
```

camelCase 直接透传是一个真实兼容性错误来源；序列化函数单独导出并测试，防止协议字段被内部命名污染。

## 14. 碎片化 SSE 示例

服务可能按如下片段发送：

```text
data: {"choices":[{"delta":{"tool_calls":[{"index":0,"id":"c1",
data: ...不能假定这里恰好是完整 JSON...
```

更常见的是网络字节 chunk 在 `data:` 行中间断开，而不是服务真的发两行半 JSON。Provider 先用 TextDecoder 拼接到换行，再把完整 `data:` 行交给 JSON.parse。函数参数也可能跨多个合法 SSE 事件：第一段 `{"path":"src/`，第二段 `a.ts"}`；Core 必须在流结束后聚合。

## 15. 完成事件的判读表

| Provider 观察 | Core 含义 |
| --- | --- |
| finish_reason=tool_calls + calls | 执行工具并继续 |
| finish_reason=stop + 无 calls | 正常文本完成 |
| finish_reason=length + 无 calls | 不完成，注入恢复提示 |
| `[DONE]` 但无 finish reason | 流结束；根据 calls/text 决定 |
| error event | 抛 AgentRunError |
| AbortSignal | cancelled，不记模型完成 |

网络流结束本身不是业务完成条件。Provider 负责“传输结束”，Core 负责“任务结束”。

## 16. DeepSeek 兼容性案例

曾观察到 HTTP 400 提示 tool 消息缺少 `tool_call_id`。根因不是 API Key，也不是 SSE，而是恢复/压缩历史中丢失 assistant toolCalls 或配对 ID。修复包括：完整持久化 assistant toolCalls、wire format snake_case、hydrate 清理孤立组、压缩不切断多工具组。

这说明错误正文只能作为证据，不能据字符串加供应商专用补丁。修复应恢复协议不变量，使所有 OpenAI 兼容服务受益。

## 17. 重试安全分析

Provider 只重试同一模型 HTTP 请求。因为此时响应尚未转化并执行工具，不存在本地副作用重放。如果服务端已经生成响应但连接在客户端接收前断开，重试可能产生不同 tool call；但旧响应没有被 Core 观察或执行，因此仍满足本地 exactly-once 边界。

模型请求成功之后的下一轮网络失败不会回滚已完成文件修改。工具结果已进入历史，用户可以重试 Turn 或恢复 Checkpoint；自动假装事务回滚会掩盖真实外部状态。

## 18. 错误正文与隐私

HTTP error body 只截取 1,000 字符。供应商可能回显请求片段，因此日志不应记录完整 message/body；用户 UI 默认显示错误分类和操作建议，详情中也应避免包含 API Key。Authorization header 从不进入 event。

## 19. Provider 合约测试

- 网络 chunk 在任意字节位置切分仍能还原文本。
- tool name/id/arguments 分片能按 index 聚合。
- 多个并行 tool call 不串参数。
- serialize 输出 `tool_call_id/tool_calls`。
- 429/502/503/504 重试有上限并可取消。
- 401/400 不盲目重试。
- usage 缺失不影响完成。
- `[DONE]`、readerDone 和尾 buffer 均能安全结束。
- Abort 后不产生伪 completed。

## 20. 为什么不在 Provider 判断任务完成

Provider 不知道 Plan、审批、测试、ChangeSet 或无进展预算。让 Provider 根据 finish_reason 直接返回 success 会把传输协议和 Agent 语义耦合，并造成截断响应被当完成。Provider 只输出归一化 ModelEvent；所有生命周期判断集中在 Core。
