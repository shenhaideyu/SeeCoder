## 5. 错误模型追踪

| 类别 | 例子 | 谁产生 | 谁恢复 | 用户动作 |
| --- | --- | --- | --- | --- |
| USER | approval_denied、invalid input | Core/Main | 模型换方案或用户重试 | 修改选择/输入 |
| MODEL | http_401、http_429、network_error | Provider | Provider 短暂重试，Core 终止 | 检查配置/稍后重试 |
| TOOL | patch_failed、command_failed | Tools | 模型读取 Observation | 修补代码/命令 |
| POLICY | path_denied、plan_read_only | Tools/Core | 不自动绕过 | 切工作区/改模式 |
| TIMEOUT | timeout、output_limit、iteration_limit | Tools/Core | 有界终止 | 缩小任务/重试 |
| CANCELLED | cancelled | 各层 AbortSignal | finally 清理 | 可重新开始 |
| SYSTEM | interrupted、turn_failed | Core/恢复 | 保守失败 | 查看 Trace 后重试 |

当前代码没有统一 ErrorCategory 枚举，上表是语义映射而非已实现字段。若引入枚举，必须保持现有稳定 code 兼容。

## 7. 关键缺口

1. IPC 入参尚未全部通过共享 Zod schema 自动验证。
2. 完成验证与当前代码版本没有强绑定，存在修改后未重跑测试的可能。
3. 多文件 patch 写阶段不具备跨文件事务。
4. 日志没有轮转、健康检查与会话损坏提示。
5. Renderer 大文件与长会话性能缺少量化基准。
6. 真实 API Eval 仍依赖本机 Key 和服务状态，CI 主要使用 Fake Provider。

这些缺口应进入后续任务，不应通过修改“状态=已完成”掩盖。

## 8. 变更控制

新增或修改需求时必须：分配稳定 ID → 更新 spec 验收条件 → 指向设计章节 → 实现 → 添加自动或明确人工证据 → 更新本矩阵。若测试无法自动化，要记录复现步骤和环境，不能只写“人工测试通过”。
