# 故障诊断与运维手册

## 1. 适用范围

SeeCoder 是本地 Electron 模块化单体，没有数据库、Redis、远程 Queue 或独立 WebSocket 服务。运行依赖是桌面进程、Renderer、OpenAI 兼容 HTTPS/SSE 服务、本地文件系统以及按需启动的子进程。排障时不要寻找并不存在的后端服务。

## 2. 数据与日志位置

Electron `app.setName('SeeCoder')` 后，Windows 用户数据通常位于 `%APPDATA%\SeeCoder`：

```text
config/settings.json              模型配置与 DPAPI 加密密文
sessions-data/sessions/<id>/      meta、events、state
sessions-data/snapshots/<id>/     文件恢复快照
logs/main.log                     结构化主进程日志
schedules.json                    本地计划任务
```

日志禁止记录 prompt 全文、文件全文、API Key 和 stdout/stderr 正文。当前 logger 记录事件类型、关联 ID、耗时、字节数、token 与错误码。

## 3. 一次任务的关联键

- threadId：长期对话与工作区关系。
- turnId：一次用户执行。
- tool callId：一次工具动作。
- childId：一次子 Agent。
- event seq/id：持久化顺序与去重。

当前没有单独 agentRunId/sessionId 字段，turnId 承担一次主 Agent run 的关联职责。这是现状，日志分析脚本不应假设不存在的字段。

## 4. 启动故障

### 页面空白

检查 Electron Main 是否记录窗口创建异常、Vite 开发地址是否可达、Renderer DevTools 是否有模块加载错误。若 preload API 不存在，优先核对 preload 构建格式与 BrowserWindow 配置，而不是在 UI 中增加假数据回退。

### 会话目录错误

开发运行曾可能写入 `%APPDATA%\Electron`。当前显式应用名应固定为 SeeCoder。检查 app.getPath('userData') 的实际值，不要硬编码用户目录。

### 设置保存一直进行中

依次检查 `settings:update` 是否 reject、safeStorage 是否可用、临时文件 rename 是否完成、Renderer 是否在 finally 清除 saving 状态。保存成功只表示密文持久化和 Provider 重配置成功，不等于模型连接已经验证。

## 5. 模型链路故障树

```text
无 model.requested
└─ turn:start / thread / active turn / UI 事件问题

有 model.requested，无 model.completed
├─ fetch 未返回：网络、DNS、代理、服务端挂起
├─ 等待 retry sleep
└─ AbortSignal 未传播

model.completed 后 turn.failed
├─ http_401/403：Key 或权限
├─ http_400：模型名、消息工具链或网关兼容性
├─ http_429/5xx：重试耗尽
├─ network_error：传输失败
└─ output_limit：连续截断
```

DeepSeek 等兼容服务出现 `missing field tool_call_id` 时，先检查持久历史是否含 assistant.tool_calls 及所有配对 tool 消息。不能通过删掉错误文本或盲目重试解决协议链损坏。

## 6. 工具卡住

若有 `tool.requested` 无 `tool.completed`：

1. 查是否紧接 `approval.requested` 或 `user.input.requested`。
2. 对命令检查子进程是否仍存在、timeoutMs 是否合理。
3. 对子 Agent 检查 child 的 currentAction 与 iteration。
4. 触发取消，确认 turn.cancelled 以及进程树消失。

Terminal 不是 PTY。运行等待交互输入的命令会挂到超时；正确修复是使用非交互参数或拒绝此类命令，不是延长到无限超时。

## 7. 状态错乱

### UI 显示 running 但后台已结束

核对终态事件是否包含正确 threadId、Renderer reducer 是否按 threadId 分桶、实时订阅是否在组件重建后重复或丢失。UI 不应通过最后一条消息类型推断状态。

### 取消后仍执行

查 controller 是否存在、provider 和 commandRunner 是否收到同一 AbortSignal、pending approval/input 是否被解决。仅把 UI 按钮变为“已取消”不构成取消成功。

### 重启后仍显示运行中

hydrate 应为无终态的最后 started Turn 补写 `interrupted`。若没有，检查 Thread 是否真正 hydrate、事件是否因 workspace 不匹配被拒绝。

## 8. 文件与 Git 故障

- `path_denied`：查看路径是否越界、符号链接是否指向外部或文件是否敏感。
- `patch_failed`：检查 unified diff 格式与旧上下文，不能直接改为模糊全局替换。
- `checkpoint_conflict`：用户或其他程序已改变文件，先查看 Diff 再决定手工恢复。
- Git 操作禁用：工作区是上级仓库子目录。切换到仓库根，而不是放宽保护。
- Git Diff 为空但工作区有文件：区分 untracked、unstaged、staged 和 ChangeSet；它们是不同来源。

## 9. JSONL 损坏

读取器逐行解析并跳过非法行，适合崩溃造成的尾行损坏。排障步骤：先复制整个 Thread 目录，再识别最后一个合法 seq。不要直接覆盖 events.jsonl；原始轨迹是审计证据。若中间大量损坏，当前实现不会报警，这是需要后续增加的诊断能力。

## 10. 性能问题

优先看结构性信号：每轮 inputTokens、工具调用分布、重复路径、单次 command 输出字节、Renderer 事件数量。高 token 通常不是“模型慢”，而是历史反复携带大文件；UI 卡顿通常不是网络，而是长列表全量重渲染或保存了所有流式 chunk。

## 11. 安全事件

若怀疑 Key 泄露：立即撤销供应商 Key，关闭应用，检查 settings.json 只含 `apiKeyEncrypted`，扫描 Git、日志和导出文件。DPAPI 密文可由同一用户上下文解密，它防止明文落盘，不防止已控制该账户的恶意程序。

若 Agent 访问意外文件：保留事件和日志，检查 WorkspacePolicy realpath 结果与符号链接，不要先删除证据。

## 12. 发布前运行手册

```text
pnpm lint
pnpm typecheck
pnpm test:unit
pnpm test:integration
pnpm test:e2e
pnpm build
node --test examples/task-board/tests/task-board.test.mjs
```

随后执行敏感信息扫描、真实兼容 API 冒烟测试和一次取消/恢复测试。真实 API 失败不能用 Fake Provider 成功替代，二者验证的是不同层。

## 13. 当前运维限制

没有日志轮转、集中指标、崩溃上报和会话修复 UI；计划任务只在应用运行时触发；模型连接没有独立“测试连接”协议证据；日志写入失败被降级忽略以避免拖垮任务。首版演示可以接受，但长期使用应优先补日志轮转与会话健康检查。
