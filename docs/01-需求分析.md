# SeeCoder 需求分析

## 1. 项目要解决的问题

大语言模型可以生成代码，但单次聊天不能可靠完成真实编程任务。真实任务需要读取项目、定位文件、修改代码、运行测试、观察失败、继续修复，并在涉及副作用时让用户保持控制。SeeCoder 的目标是把模型能力放进一个可执行、可取消、可恢复、可审计的本地闭环。

考核要求核心机制自行实现，不能封装现有 Coding Agent，也不能使用 Agent 编排框架隐藏循环。SeeCoder 因此直接实现对话历史、上下文预算、模型流解析、工具协议、本地执行、终止判断和错误恢复。

## 2. 用一个任务理解产品目标

用户选择一个项目并输入：“登录按钮点击后页面空白，请找到原因、修复并运行测试。”SeeCoder 应完成以下真实流程：

```text
理解目标和约束
  → 搜索相关代码
  → 读取最小必要文件
  → 提出修改
  → 按权限模式审批
  → 修改并生成 Diff/Checkpoint
  → 运行测试
  → 根据失败继续修复
  → 给出文件、验证和风险摘要
```

如果只返回一段建议，没有修改文件，不算完成；如果修改了文件但没有说明验证状态，也不能声称已验证；如果用户取消后后台仍执行，则属于严重错误。

## 3. 用户与使用场景

主要用户是需要完成本地编程任务的学生和开发者，其中包括不熟悉代码库的初学者。初学者需要清晰的计划、审批、Diff 和错误说明；熟悉开发的用户需要更高信息密度、快捷操作和可展开轨迹。

核心场景包括只读解释、明确缺陷修复、跨文件修改、测试失败后自主修正、代码 Review、长对话追问、任务取消和重启后查看历史。SeeCoder 不承诺替代完整 IDE，而是提供受控 Agent 工作台。

## 4. 功能需求

| ID | 需求 | 可验证结果 |
|---|---|---|
| FR-01 | Workspace 管理 | 可选择和切换项目；切换时取消旧项目任务 |
| FR-02 | Session 管理 | 支持新建、加载、重命名、置顶、归档、删除、Fork、搜索和导出；助手消息提供可直接发现的 Session Fork 入口 |
| FR-03 | Turn 执行 | 同一 Session 可多轮追问，同时只允许一个活动 Turn |
| FR-04 | 模型接入 | 支持 OpenAI 兼容 SSE、文本增量、Tool Call、usage 和重试 |
| FR-05 | 上下文管理 | 输入超过可用预算 75% 时压缩，目标降到 60% |
| FR-06 | 本地工具 | 支持目录、读取、批量读取、搜索、写入、补丁、命令和 Git Diff |
| FR-07 | 权限控制 | Plan 无副作用；Guided 逐次审批；Auto 只自动放行低风险动作 |
| FR-08 | 修改恢复 | 文件修改生成 ChangeSet、Snapshot 和 Checkpoint |
| FR-09 | 子 Agent | Explore/Review 独立只读上下文，最多并发 2 个，禁止嵌套 |
| FR-10 | 用户介入 | 支持审批、`ask_user`、Follow-up、计划批准和取消 |
| FR-11 | 终止 | 完成、失败、取消、输出截断、无进展和迭代上限都有明确结果 |
| FR-12 | 持久化 | Session 轨迹重启可读，损坏 JSONL 尾行不影响其他记录 |
| FR-13 | 工作台 | 对话、计划、Changes、Files、Terminal、Preview、Trace 由真实 IPC 驱动 |
| FR-14 | 本地扩展 | 支持导入 Skill 和受信任 Hook，不引入第三方 Agent SDK |

## 5. 非功能需求

安全方面，Renderer 不获得 Node.js 权限，文件工具不能越出 Workspace，敏感文件默认拒绝，API Key 明文不能进入磁盘配置、事件或日志。系统准确声明应用层隔离，不宣称 OS 沙箱。

可靠性方面，副作用调用必须幂等，取消要贯穿模型、子 Agent 和子进程；一次 Turn 只能出现一个终态；补丁冲突不能产生半写入；旧验证不能证明新 revision。

可理解性方面，界面默认展示当前阶段、需要用户处理的决策、文件变化和验证结果。原始 JSON、完整日志和调试指标按需展开。

可维护性方面，Protocol、Core、Model、Tools、Storage 与 UI 保持边界；UI 不复制 Agent 状态机；公共行为由类型和自动测试保护。

## 6. 范围边界

首版不实现远程执行、云同步、MCP、插件市场、交互式 PTY、完整 Worktree 并行写入、分布式任务队列和操作系统级沙箱。计划任务只在 SeeCoder 运行时触发，并固定使用只读 Plan 模式。

这些能力不是没有价值，而是会显著扩大安全和部署范围。首版优先证明本地 Agent 闭环正确。

## 7. 验收标准

系统应能在独立测试 Workspace 中完成简单、中等和复杂任务，实际经历读取、修改、测试和继续修复。Plan 模式必须证明不能写入；取消后不能留下活动 Turn 和受控子进程；重启后能恢复 Session、消息、计划、Diff、Checkpoint 和终态；所有文件与命令副作用都经过策略；界面状态与 Core 事件一致。

演示成功不以“模型最后说完成”为准，而以真实文件变化、当前 revision 的验证证据和完整事件轨迹为准。

## 8. 三类任务怎样验收

只读任务的目标是解释代码，不应产生写入和命令副作用。系统需要展示读取过的文件和证据来源，回答应与用户语言一致。Plan 模式就是这类任务的强制安全边界。

修改任务必须同时检查实现和过程。假设用户要求新增筛选功能，SeeCoder 应找到数据结构、界面和测试之间的关系，修改所有必要文件，避免无关格式化，并展示 Diff。若测试无法运行，需要明确说明原因，不能把“代码看起来正确”写成“测试通过”。

故障修复任务通常不知道根因。SeeCoder 需要从日志或现象开始，逐步缩小范围。测试失败是继续分析的证据，不是立即结束的理由。完成时应说明根因、修改点、验证命令和剩余风险。

## 9. 需求之间的依赖

本地工具依赖 Workspace 安全边界；权限模式依赖工具能够声明副作用和风险；取消依赖 ModelProvider、子 Agent 和命令都接收同一 AbortSignal；重启恢复依赖事件先持久化再广播；上下文压缩依赖 Tool Call 消息组能够完整识别。

因此不能孤立实现功能。例如只有取消按钮而没有 Abort 传播，不满足取消需求；只有 Diff 页面而没有真实 ChangeSet，不满足修改可恢复；只有聊天记录而没有 Tool Call 配对，不满足历史恢复。

## 10. 产品完成状态的判断

需求分为“已实现”“已验证”和“设计范围外”。已实现表示源码存在；已验证表示自动测试或真实流程证明；范围外表示首版主动不做。答辩中不能把“已实现但未真实验证”说成稳定能力，也不能把未来设计说成当前功能。

## 11. 需求是怎样从问题推导出来的

编程智能体的根本问题不是“怎样调用模型”，而是“怎样让不确定模型在本地环境中完成有边界的工作”。从这个问题可以推导出四组需求。

第一组是执行闭环。模型必须能够观察项目，所以需要目录、读取和搜索；模型必须能够采取动作，所以需要写入、补丁和命令；动作结果必须进入下一轮，所以需要结构化 Tool Result 和 Observation；任务必须停止，所以需要终止条件。缺少任一环节，系统都只是半闭环。

第二组是控制权。文件和命令会产生真实副作用，必须有 Workspace 边界、权限模式、审批、取消和回滚。Prompt 中的安全要求只能影响模型行为，不能代替代码约束，因此这些需求必须由 Main/Core 和 Tools 实现。

第三组是长任务稳定性。真实修复通常需要多轮模型调用，历史会不断增长，文件还会在执行中变化。因此需要 Session、ContextLedger、FileEvidence、revision、上下文预算和压缩。它们不是附加优化，而是避免模型遗忘目标、引用旧代码和使用过期测试的必要条件。

第四组是可观察和可恢复。用户需要知道 Agent 当前阶段、修改内容和验证结果；开发者需要定位模型、工具和状态错误；应用重启后需要恢复已经发生的事实。因此需要 AgentEvent、JSONL、Trace、ChangeSet 和明确终态。

## 12. 角色的真实职责

用户不是只负责输入 Prompt。Guided 模式下，用户是副作用决策者；`ask_user` 出现时，用户是缺失需求的提供者；Checkpoint 冲突出现时，用户决定如何处理外部编辑。系统需要把决定所需信息展示清楚，而不是把完整内部日志推给用户。

模型是决策建议者。它根据上下文选择读取、修改、测试或完成，但不拥有本地权限，也不是事实来源。模型说“文件已修改”不算证据，工具结果和 Workspace 文件才是事实。

Agent Core 是执行协调者。它不负责写业务代码内容，但负责消息、状态、权限、幂等、取消和终止。Tool Runtime 是能力提供者，只执行一项受控动作，不自行继续循环。Renderer 是交互层，不得成为第二套状态机。

## 13. 用户旅程中的异常路径

正常流程之外，需求必须覆盖失败。模型接口 429 时，Provider 有限重试并在事件中显示重试；补丁旧内容不匹配时，工具返回冲突，模型重新读取；测试失败时，模型继续修复；用户拒绝命令时，拒绝作为 Observation 返回；用户取消时，网络、审批和命令同时停止；应用崩溃后，未完成 Turn 标记为 interrupted。

异常路径之所以重要，是因为 Coding Agent 的价值正是在不确定环境中继续推进。如果系统只在第一次工具全部成功时工作，真实项目成功率会很低。但恢复也必须有边界：相同失败重复三次、输出持续截断或迭代耗尽时，应明确失败，不能无限尝试。

## 14. 非功能要求怎样落到可验证行为

“安全”不能只写成抽象目标。可验证行为包括越界路径被拒绝、敏感文件不出现在搜索结果、Plan 写入不改变文件、API Key 不出现在 Renderer 和日志。

“可靠”意味着同一 callId 不重复执行、Turn 只有一个终态、取消后没有活动资源、损坏 JSONL 尾行不影响合法历史、Checkpoint 不覆盖外部编辑。

“性能”不是单纯窗口打开速度。Agent 的主要成本是模型轮数和输入 token，因此要记录峰值上下文、重复工具、压缩次数和模型耗时。UI 还要避免每个极小文本 delta 导致整个三栏重渲染。

“易用”意味着用户能区分 Prompt、Agent 输出、工具活动、文件变化、错误和验证。对话流中的工具卡片只展示“做了什么、对谁操作、结果如何”：例如“已读取 `src/app.ts` 第 20–48 行”或“运行 `pnpm test` · 退出码 0”。折叠态和展开态均不展示事件 JSON、callId、turnId 或内部时间戳；开发者需要的原始轨迹只在 Trace 和本地日志中保留。所有按钮都必须有真实行为或明确不可用原因。

审批卡与工具活动使用同一内容栅格，默认只展示操作目标、风险和决策按钮。文件补丁按需展开为带行号、增删颜色和文件名称的 Diff，不直接展示 `*** Begin Patch` 等协议文本。窄栏 Diff 必须可横向滚动，并提供大窗口查看入口；用户不应因为检查器宽度不足而无法确认完整代码。Session 中的完成、失败和取消横幅只描述最新 Turn；新 Turn 开始后，上一 Turn 的终态仍保留在轨迹中，但不得继续作为当前页面状态。

## 15. 为什么首版主动缩小范围

每增加一种执行能力，都会扩大权限和状态空间。MCP 需要外部服务信任与协议；远程执行需要身份、网络和远端沙箱；交互 PTY 需要长期 Shell 状态；并行写 Agent 需要 Worktree、合并和冲突处理；插件市场需要分发和供应链安全。

如果首版同时实现这些功能，核心循环、上下文和安全边界反而难以验证。SeeCoder 选择本地单主进程、固定工具面、主 Agent 单写者和只读子 Agent，是为了把最重要的闭环做成可解释、可测试的系统。

## 16. 答辩时怎样说明需求价值

可以从“普通聊天为什么不够”开始。普通聊天无法证明文件是否修改、测试是否真实运行，也不能可靠处理审批、取消和恢复。SeeCoder 的需求不是增加聊天功能，而是为模型增加受控行动能力和工程证据。

随后用一项真实任务说明每个核心需求都参与结果：Workspace 限制范围，Session 保存长期目标，ContextBuilder 提供当前证据，Tool Runtime 完成动作，权限保留用户控制，revision 保证验证可信，Event 解释过程，终止规则控制成本。这样需求与系统实现形成完整逻辑，而不是孤立功能列表。
