# 真实任务执行案例分析

## 1. 案例文档的用途

单元测试证明局部规则，真实任务证明规则组合后是否仍能工作。本章使用项目已有真实 Prompt Eval 的证据模型，关注轨迹而非“最后一句看起来正确”。测试目标工作区必须是独立演示项目，不能让 SeeCoder 与开发 SeeCoder 的 Codex 同时修改同一目录。

## 2. 测试集设计原则

真实 Prompt 应具有自然语言省略、非唯一实现方式和验证要求，而不是直接告诉 Agent 文件名与补丁内容。按三层覆盖：

- 简单：解释模块、定位明确缺陷、只读回答。
- 中等：多个文件一致修改、测试失败后修复、需要审批。
- 复杂：先定位根因、修改、验证、Review，并处理一次可恢复失败。

每个案例记录 prompt、工作区初始提交、模式、模型配置、事件摘要、文件 Diff、命令结果、token、耗时和终态。

## 3. 案例一：只读架构解释

自然 Prompt：

```text
我刚接手这个项目。请告诉我登录状态从后端返回后，前端哪些地方会消费它，
以及修改这个字段最容易漏掉哪里。只分析，不要改代码或运行命令。
```

期望轨迹不是“遍历整个仓库”，而是：search_text 定位类型和字段 → read_files 批量读取定义与调用方 → 给出带文件证据的回答。验收点：无副作用工具、无重复读、读文件数量有界、没有虚构路径。

这类任务暴露的 Harness 问题通常是过度 planning、连续逐文件读取以及无工具文本过早结束。SeeCoder 的 4/7 轮探索预算只能限制极端循环，真正效率仍依赖 prompt 与 Eval。

## 4. 案例二：跨层缺陷修复

自然 Prompt：

```text
新增记录时，标题全是空格也能保存，列表里会出现一条看不见的记录。
请找到前后端各自应该承担的校验，修复后补测试。不要改变已有正常输入行为。
```

理想轨迹：

```text
set_plan
→ search/read 定位表单、API、领域校验和测试
→ apply_patch 修改最小文件集合
→ 运行针对性测试
→ 如测试失败，读取 stderr 并修正
→ git_diff
→ review_changes
→ finish(真实验证)
```

验收不仅看测试通过，还要检查客户端即时反馈与服务端最终约束是否一致、错误文案是否可理解、是否无关格式化大量文件。

## 5. 案例三：从日志定位根因

自然 Prompt：

```text
保存设置后页面一直显示“保存中”，后台偶尔已经写成功。请结合日志找根因，
修复重复提交或状态不同步的问题，并验证失败和成功两条路径。
```

该任务测试 observation 是否真正反馈：Agent 需要搜索保存状态、IPC handler 和异常路径，不能只在按钮上加 timeout。正确修复通常要求 finally 或统一状态归并，并用失败注入测试证明按钮恢复可用。

## 6. 案例四：复杂重构的收敛性

自然 Prompt：

```text
任务详情页越来越难维护。请先说明最影响后续修改的职责混杂，再做一次小范围重构，
目标是让任务状态展示与事件归并逻辑可独立测试。不要重做整个页面，完成后跑现有测试并审查 Diff。
```

观察点：Agent 是否先识别可验证边界，再进行最小重构；是否把“架构更优雅”当作无限扩张理由；是否能够在一次测试失败后调整，而非回滚全部或继续重写。

## 7. 轨迹评分

建议每次真实运行生成如下度量：

| 指标 | 定义 | 风险信号 |
| --- | --- | --- |
| Task success | 验收条件全部满足 | 只凭最终文本判成功 |
| Iterations | 模型请求次数 | 简单任务超过 5 轮 |
| Tool calls | 工具总数及分布 | 重复读同一路径 |
| Action ratio | 写入/验证调用占全部调用比例 | 长时间只有探索 |
| Context growth | 每轮 input token | 单调急剧增长 |
| Recovery | 失败后是否产生不同动作 | 原样重试同一失败 |
| Scope precision | 修改文件是否均与需求相关 | 大量无关格式化 |
| Verification freshness | 最后修改后是否重新测试 | 使用修改前结果 |
| Terminal state | 终态与后台事实一致 | UI completed 但测试失败 |

## 8. 项目已有真实证据

仓库的 `tests/evals/realistic-prompts.json` 保存自然任务定义，`evaluate-real-sessions.node-test.mjs` 从真实会话事件计算门禁。已有复杂会话曾达到 21 次模型迭代、35 次工具调用和单轮最高约 75,485 输入 token；它说明功能闭环可运行，也说明效率距离成熟 Agent 仍有明显差距。

该数字不能被“测试通过”掩盖。测试通过表示轨迹证据格式和最低行为成立，不表示成本、路径选择或回答质量已经最优。

## 9. 失败轨迹模板

```text
Prompt:
Workspace revision:
Mode / model:

Observed sequence:
1. model.requested ...
2. tool read_file ...
3. tool failed(code=...)

Expected divergence point:
Root cause:
Minimal fix:
Regression assertion:
Remaining uncertainty:
```

记录“期望在哪一步改变行为”比保存整段聊天更有诊断价值。

## 10. 成熟产品对比维度

与 Codex、Claude Code、TRAE、CodeBuddy 比较时只比较公开可观察的产品思想：执行阶段清晰、工具细节渐进披露、审批与取消可靠、修改和验证证据可回看、长任务上下文可控。不能根据 UI 相似度推断其内部实现，也不能引用泄露源码作为设计依据。

## 11. 当前结论

SeeCoder 已具备真实多轮任务的最小闭环，但“能完成”与“高效稳定完成”仍有距离。最值得继续优化的是基于内容哈希的重复读取抑制、验证新鲜度检查、更严格的完成证据和真实会话分位数指标，而不是继续增加工具数量。
