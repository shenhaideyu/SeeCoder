# 工具定义与本地执行

## 1. 工具不是函数列表，而是安全协议

每个 ToolDefinition 同时定义：名称、模型描述、Zod 参数、是否有副作用、静态风险和执行函数。Core 还维护一份模型侧 JSON Schema。模型只看到 schema，实际执行必须再次通过 Zod；TypeScript 类型不能替代运行时校验。

```ts
interface ToolDefinition {
  name: string;
  description: string;
  parameters: ZodTypeAny;
  sideEffect: boolean;
  risk: "low" | "medium" | "high";
  execute(args: unknown, context: ToolContext): Promise<ToolResult>;
}
```

ToolResult 统一为 `ok/output/error/durationMs`。错误包含稳定 code、用户可读 message 和 retryable，使模型、UI、日志和测试共享语义。

## 2. 内置工具

| 工具 | 副作用 | 关键限制 |
| --- | --- | --- |
| `list_files` | 否 | depth 0–5，最多 200 个，跳过依赖/构建/敏感目录 |
| `read_file` | 否 | 单次最多 400 行 |
| `read_files` | 否 | 最多 30 个，每文件最多 400 行 |
| `search_text` | 否 | 最多 100 结果，优先 rg |
| `git_diff` | 否 | 当前工作区范围 |
| `write_file` | 是 | 单文件临时文件 + rename |
| `apply_patch` | 是 | unified diff，先验证全部 hunk |
| `run_command` | 是 | cwd、超时、取消、输出上限 |
| `set_plan` / `finish` | 否 | Core 同步状态或终止 |
| `delegate` / `review_changes` | 否 | Core 调度只读子 Agent |
| `ask_user` | 否 | Promise 暂停等待用户 |
| `checkpoint` | 否 | 创建恢复标记 |
| `compact_context` | 否 | 强制上下文压缩 |

## 3. WorkspacePolicy

路径检查分两步：

1. **词法边界**：`resolve(root,input)` 后用 `relative` 拒绝 `..` 和绝对越界。
2. **真实边界**：解析 workspace 和目标已存在祖先的 realpath，拒绝符号链接逃逸。

对于尚不存在的新文件，`canonicalizeFuturePath` 向上找到最近存在祖先，再拼回缺失部分。仅检查字符串前缀是不够的，例如 `C:\work2` 会错误匹配 `C:\work`；使用 `relative` 才有路径段语义。

## 4. 敏感文件策略

以下内容不进入 Files、Search 和 Agent 上下文：`.env` 及非模板变体、pem/key/p12/pfx、SSH 私钥，以及文件名含 secret、credential、token、apikey、private 的文件。

`.env.example/.sample/.template` 被允许，因为它们是项目结构和配置说明的一部分。规则是应用层最小权限，不替代操作系统访问控制。

## 5. 文件读取和搜索

`read_file` 按行裁剪，避免一次读取大型生成文件。已知多个目标时使用 `read_files`，减少模型往返。搜索先启动 `rg --line-number --no-heading`，并传入敏感 glob 排除；若 rg 不存在，再由 Node 遍历最多 1,000 个文件、跳过二进制和常见依赖目录。

为什么不直接让模型运行 `Get-ChildItem`/`Select-String`：专用工具有固定结果结构、路径检查、取消和输出上限，也更容易评估重复调用。

## 6. 写文件

`write_file` 将内容写到同目录临时文件，再 rename 覆盖目标。这样进程在写入中途崩溃时，原文件通常仍完整。成功结果携带 before/after，Core 据此创建 ChangeSet。

## 7. Unified Diff

`apply_patch` 自行解析 `---/+++/@@`：

1. 解析所有目标文件和 hunk。
2. 读取 before 内容。
3. 先在内存验证所有旧上下文。
4. 行号不匹配时在 ±80 行寻找唯一候选。
5. 任一文件验证失败则不开始写入。
6. 全部验证后逐文件原子替换。

模糊定位只接受唯一候选，避免补丁应用到重复代码的错误位置。限制是最终写入不是跨文件事务；若第二个 rename 发生罕见 I/O 故障，第一个文件可能已完成。ChangeSet/Checkpoint 提供后续恢复，但不能宣称数据库式全有或全无。

## 8. 命令执行

Windows 使用：

```text
powershell.exe -NoProfile -NonInteractive -Command <command>
```

环境继承当前进程并增加 `CI=1`。stdout/stderr 分开收集并实时发出 `tool.output`，每路保留最近约 1 MiB。默认超时 60 秒，模型参数范围 1–120 秒。

取消或超时使用 `taskkill /pid <pid> /t /f`，因为只 kill PowerShell 父进程可能留下测试 runner、编译器或 dev server。非 Windows 使用对应信号。

当前不是 PTY，不支持 Vim、交互式安装确认等 TUI，这是有意范围限制。

## 9. 风险分类

高风险模式包括递归删除、格式化、关机、注册表、网络下载、依赖安装和危险 Git 操作。低风险白名单包括 Git 查询、测试、lint、typecheck、build、pytest 和 `node --test`。其他命令为 medium。

静态 ToolDefinition 将 `run_command` 标为 high；实际审批卡使用 `commandRisk(command)` 动态计算。这样 schema 仍保守，而用户看到的风险更准确。

## 10. 权限决策

```text
Plan:    sideEffect => 拒绝
Guided:  sideEffect => 等待审批
Auto:    policy 可自动批准 => 执行
         否则 => 等待审批
```

权限检查发生在参数验证后、执行前。拒绝以 ToolResult 回给模型，而不是吞掉调用。这样模型知道动作没有发生，不会基于虚假前提继续。

当前 `write_file` 参数直接包含 path，因此 Auto 可在 `isInside` 成功时放行；`apply_patch` 参数只有整段 patch，`canAutoApprove` 无法从统一字段取得目标路径，所以仍会进入审批。这比未经解析就自动执行补丁更保守，也应在 UI 中如实表现。

## 11. 幂等与并发

每个 Turn 按 callId 缓存 ToolResult。模型或网络层重复同一 ID 时不会再次写入。主循环目前顺序执行同一轮多个工具，牺牲部分只读并行速度，换取明确事件顺序和无写竞争。子 Agent 可以并发，但全部只读。

## 12. ChangeSet、Snapshot、Checkpoint

工具只返回 before/after，不直接负责存储。Core 统一创建 ChangeSet、写 snapshot、更新 Ledger 并发出事件。这保持工具运行时无会话依赖，也让任何未来写工具自动复用同一恢复流程。

Checkpoint 恢复前验证 afterHash，防止覆盖用户后续编辑。撤销新建文件时删除目标，撤销已有文件时原子写回 before。

## 13. Git 和 Terminal IPC

UI 的 Git/Terminal 操作不绕过主进程：路径、Git 根和风险仍校验。Git 专用按钮使用固定命令和引号转义；如果工作区只是上级仓库的子目录，则禁用 Git 操作，防止 `git add -A` 影响工作区外。

## 14. 错误分类

常见 code：`path_denied/read_failed/search_failed/write_failed/patch_failed/command_denied/command_failed/spawn_error/timeout/cancelled/invalid_args/approval_denied/plan_read_only`。模型可据此调整方案，UI 将技术详情放在展开区，日志按 WARN/ERROR 记录真正故障。

## 15. 为什么不暴露任意 Node API

“让模型生成 JavaScript 并在主进程执行”代码量更少，但会绕过路径、风险、schema、幂等和审计，等价于 Full Access。明确的小工具面虽然需要更多代码，却能逐项测试和解释，是安全 Harness 的核心。

## 16. ToolDefinition 与模型 Schema 的双表示

当前 Zod schema 位于 Tools，模型用 JSON Schema 位于 Core。双表示的原因是模型协议需要可序列化 JSON，执行需要运行时解析器；代价是可能漂移。例如 Zod 为字符串设置 max，而 JSON Schema 未同步时，模型不知道限制但执行会拒绝。

长期更稳妥的方向是从同一声明生成 JSON Schema，但不应为此引入 Agent SDK。无论如何，Zod 是执行权威，模型 schema 只是提示。回归测试应比较 required、enum 和数值上限，而非假定 TypeScript 能保障外部 JSON。

## 17. 工具逐项契约

### list/read/search

成功输出必须包含相对路径，避免把用户绝对目录发送给模型或展示在分享内容。批量读取允许单个文件失败并继续，整体 `ok:true` 表示批处理完成，不表示每个条目都成功；模型必须检查各条目的 error。

### write_file

适合创建或完整替换小型文本。它不保留编码、BOM 或权限位，不适合二进制。rename 的原子性依赖同一文件系统和平台语义；临时文件与目标同目录正是为了提高该保证。

### apply_patch

适合最小化修改并保留未触及内容。验证阶段先计算所有 after，写阶段再逐文件进行。±80 行偏移只处理上下文前移/后移，且要求唯一匹配；不会做语义 AST 合并。

### run_command

成功定义为进程退出码 0，不是“stdout 包含 success”。非零退出的 stdout/stderr 仍保存在 output，使模型能诊断。超时或取消返回受控错误，即使 taskkill 稍后才完成，Turn 也不应继续等待交互。

### finish

`finish` 只是 Harness 终止信号和证据容器，不自行运行测试。verification 的真实性来自轨迹中已经发生的命令，当前 Core 没有强制交叉验证，这是重要限制。

## 18. 权限决策伪代码

```ts
definition = registry.get(call.name)
args = definition.parameters.safeParse(call.args)
if invalid: return invalid_args
if mode == 'plan' && definition.sideEffect:
  return plan_read_only
if policy.canAutoApprove(call, mode):
  return execute()
decision = await requestApproval(call, dynamicRisk(call))
if denied: return approval_denied
return execute()
```

先校验再展示审批，避免用户批准一个无法执行或参数伪造的动作。审批只授权该 callId 的这组参数，不是给后续同名工具永久授权。

## 19. 错误是否重试

| 错误 | 默认含义 | 建议恢复 |
| --- | --- | --- |
| invalid_args | 模型参数错误 | 模型修正一次，不原样重试 |
| path_denied | 安全边界 | 不绕过；换工作区或合法路径 |
| read/search_failed | 目标/工具环境问题 | 重新定位或使用回退工具 |
| patch_failed | 上下文过期/格式错误 | 重读目标后生成新 patch |
| command_failed | 命令真实失败 | 分析 stderr，修代码或参数 |
| timeout | 任务过长或阻塞 | 缩小范围/非交互参数 |
| approval_denied | 用户决策 | 改换无副作用方案 |
| cancelled | 用户终止 | 立即收敛，不自动恢复 |

工具层本身不做通用自动重试，因为文件写入和命令可能部分产生副作用。恢复决策需要 observation 语义，由模型或用户作出。

## 20. 并发模型

主 Turn 内工具按返回顺序串行执行，确保 ChangeSet、日志与 observation 顺序可解释。即使模型在一轮请求两个只读工具，当前也不并行。这损失一些性能，却避免混合只读/写入调用时的竞态。

子 Agent 最大并发 2 且只读，是受控并行边界。`children.size` 是进程内限制，不是跨进程 semaphore；当前单 Main 进程假设下成立。

## 21. 工具实现完成定义

新增工具必须同时提供：Zod schema、模型 JSON Schema、sideEffect 与 risk、WorkspacePolicy 使用、AbortSignal 行为、结构化 ToolResult、事件证据、敏感信息策略、单元测试，以及在 Guided/Auto/Plan 三种模式下的期望。缺少任何一项都不应加入模型工具列表。
