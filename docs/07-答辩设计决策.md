# SeeCoder 答辩设计决策

本章只保留答辩高概率关注的问题：项目定位、架构、Agent Harness、上下文、工具安全、终止恢复、测试、UI 和当前限制。回答建议采用“结论 → 实现 → 取舍”结构。

## 1. 项目介绍

### 30 秒版本

SeeCoder 是一个面向 Windows 的 Electron 桌面编程智能体。它通过 OpenAI 兼容接口调用模型，但 Agent 主循环、Session、上下文、Tool Call 解析、本地执行、权限、终止和错误恢复均由项目自行实现。模型不能直接访问本地环境，只能提出经过校验和审批的工具调用；用户可以查看计划、Diff、终端、Trace 和验证证据。

### 2 分钟版本

系统采用模块化单体。React Renderer 是前端，Electron Main 是可信本地后端，Preload 提供类型化 IPC。Agent Core 维护 Turn 状态机，ModelProvider 处理原生 fetch、SSE、Tool Call 增量和重试，Tools 提供工作区内文件与命令能力，Storage 用 V3 JSONL 保存可回放轨迹。

一次 Turn 会反复执行“构建上下文、调用模型、解析 Tool Call、校验权限、执行工具、回填 Observation”，直到完成、失败、取消或达到上限。长任务使用 ContextLedger、FileEvidence、工具 Observation、轻量检索、模型语义摘要和确定性回退。主 Agent 是唯一写入者，Explore/Review 子 Agent 只读。

## 2. 为什么不用 Agent SDK

考核明确要求核心机制自研。Agent SDK 还会隐藏最需要说明的消息链、工具调度、重试、审批、终止和恢复。SeeCoder 只使用模型原生协议和常规验证库，Harness 保持为可阅读、可测试代码。

代价是边界测试必须自行完成，包括碎片化 SSE、Tool Call 配对、幂等、取消和回放。这个代价正是项目技术工作的主体。

## 3. 为什么选择 Electron 模块化单体

Coding Agent 同时需要本地文件/进程能力和高信息密度桌面 UI。Electron Main 可以作为本机后端，Renderer 提供对话、Diff、终端和 Trace，不需要启动额外端口和服务。

微服务适合多用户、独立扩缩容和远程执行，但本项目是单用户本地应用。现在拆服务会增加鉴权、RPC、部署和故障点。packages 已经提供逻辑边界，未来需要远程执行时再拆出服务更合理。

## 4. 前端和后端怎样划分

Renderer 是前端，只负责交互和事件展示。Main 是后端，负责密钥、工作区、IPC、Agent Core 和本地工具。Preload 是最小权限桥。不存在独立 HTTP 后端，但不能因此说系统没有后端。

可信状态位于 Core。Renderer 发出取消或审批命令后，必须等待 Core 事件，不能自行假装后台已经改变。

## 5. Agent 主循环是什么

模型只产生一次响应，Agent Core 负责持续闭环：

```text
User Intent
  → Context Builder
  → Model Stream
  → Tool Call Parser
  → Policy and Execution
  → Observation
  → Replanning
  → Validation
  → Completion
```

主循环最多 24 轮。模型正常文本且无 Tool Call、`finish` 成功、用户取消、不可恢复错误、连续无进展或达到上限都会结束。连续探索还有 4 轮提醒和 7 轮阻止，防止模型无限读取。

## 6. 为什么 Session 和 Turn 分开

Session 是可长期追问的任务对话，Turn 是一次请求的执行。Session 可以有多个 Turn，但同一时间只有一个活动 Turn。这样既能保留长期上下文，也能为每次运行提供独立状态、迭代、取消信号和终态。

重启时恢复的是事件、消息、Ledger、ChangeSet 和 Checkpoint，不是旧进程。未完成 Turn 标记为 interrupted，避免 UI 显示并不存在的后台任务。

## 7. 上下文压缩怎样设计

完整历史不等于模型输入。完整事件保留在 JSONL；ContextBuilder 每轮构建受预算限制的视图。

权威事实由 ContextLedger 保存，代码证据由 FileEvidence 管理，工具输出由 Observation 压缩，旧事实由轻量检索召回，旧自然语言由当前模型生成结构化摘要。摘要失败时使用确定性回退，不能覆盖 Ledger。

可用输入会预留输出 token 和至少 5% 安全余量。超过 75% 触发压缩，目标降到 60%。裁剪以协议组为单位，不能拆散 Assistant Tool Calls 和 Tool Result。

## 8. 为什么不只用最后几条消息或向量数据库

只保留最近消息会丢失原始目标、设计决定和验证状态。只使用向量检索不能保证 Tool Call 协议合法，也不能判断验证 revision。向量数据库还增加索引、更新和部署成本。

代码任务常使用路径、符号和错误码，当前轻量词法检索足够可解释。未来超大仓库可以替换检索层，但 Ledger 和协议保护仍然需要保留。

## 9. 工具为什么安全可控

模型只能看到工具 Schema，实际参数在 Core 中经过 JSON 解析和 Zod 校验。文件路径经过 resolve、relative 和 realpath；敏感文件统一过滤；写入前保存 Snapshot；命令有模式、风险分类、审批、超时、输出上限和取消。

安全来自模型外部代码规则，不来自 Prompt。当前仍是应用层策略，不能等同 OS 沙箱。若运行真正不可信代码，应增加容器、Windows Sandbox 或受限 Token。

## 10. 为什么主 Agent 单写者

并行写 Agent 会造成文件冲突、测试干扰、审批责任不清和回滚顺序复杂。SeeCoder 允许 Explore/Review 并行收集证据，但只有主 Agent 写入，ChangeSet、Checkpoint 和验证可以绑定唯一因果链。

并行写只有在引入 Worktree、合并策略和冲突调度后才值得实现，不属于当前首版。

## 11. 模型输出怎样解析

Provider 使用原生 fetch 读取 SSE。网络块、SSE 行和 JSON 参数边界不一致，因此先进行字节解码和行缓冲，再产生统一 ModelEvent。Tool Call 参数按 `callId` 聚合，流结束后才 JSON.parse 和 Zod 校验。

Core 必须先保存 Assistant Tool Calls，再保存相同 callId 的 Tool Result。曾出现的 DeepSeek 400 就属于消息链不完整，而不是模型不会调用工具。

## 12. 错误和取消怎样处理

测试失败、补丁冲突和审批拒绝通常是 Observation，模型可以继续修复。模型连接无法恢复、连续截断、达到上限和内部异常才让 Turn 失败。

取消通过 AbortSignal 传到 fetch、子 Agent 和工具。受控命令终止进程树，等待中的审批和输入 Promise 被解决，finally 清除活动 Turn。UI 只在收到终态事件后显示已取消。

## 13. 为什么使用 JSONL

Agent 事件天然按时间追加。JSONL 便于人工检查、演示轨迹和跳过损坏尾行，不需要原生数据库模块。当前只有单 Main 写入，复杂查询和多进程事务需求很弱。

代价是全文搜索线性扫描，多进程写入能力有限。若 Session 达到数万或需要复杂统计，SQLite 是合理迁移方向。

## 14. UI 的设计原则

界面帮助用户回答四个问题：Agent 正在做什么，刚刚改变了什么，现在需要我决定什么，结果是否验证。中央区域显示对话、计划和审批；右侧显示 Changes、Files、Terminal、Preview 和 Trace；左侧管理 Workspace 和 Session。

工具卡默认显示“读取 5 个文件”“运行测试”等人类可理解动作，raw JSON 和完整输出按需展开。错误卡说明发生了什么、影响、系统状态和用户下一步。任务进度使用阶段，不使用虚假百分比。

## 15. 为什么有 Plan、Guided 和 Auto

Plan 强制只读，适合先理解和生成方案。Guided 对副作用逐次审批，适合演示和敏感项目。Auto 减少工作区内写入和低风险测试的重复确认，但网络、安装、删除、提交和推送仍受审批。

系统没有 Full Access，因为当前没有 OS 沙箱支撑这一安全承诺。

## 16. 如何证明系统有效

确定性测试用 Fake Provider 固定模型行为，验证状态机、权限、消息链、取消、回放和上下文。集成测试在临时项目执行真实文件副作用。Electron E2E 检查完整用户流程。真实 DeepSeek Eval 使用自然 Prompt 评价成功率、模型轮数、工具效率、token、Diff 和验证。

最终回答正确不是唯一标准。还要检查真实文件、当前 revision 验证、终态、越权行为和完整轨迹。

## 17. 当前最重要的限制

当前没有 OS 沙箱、MCP、远程执行、云同步、交互式 PTY、完整 Worktree 隔离和多用户调度。Fork 只复制对话事件。根 `AGENTS.md` 已加载，但更细目录规则能力有限。多文件补丁使用补偿回滚，不是数据库事务。全文 Session 搜索没有索引。

这些限制应主动说明。项目亮点是把本地 Agent 闭环做得可解释和可控，而不是功能数量最多。

## 18. 高频追问速答

**SeeCoder 和普通聊天机器人有什么区别？** 普通聊天只生成文本；SeeCoder 有持续状态机、受控工具、Observation、验证和终态。

**为什么 TypeScript 类型还要 Zod？** TypeScript 在运行时消失，模型参数是不可信 JSON，执行边界需要真实校验。

**为什么 ToolResult 和 Observation 分开？** ToolResult 是完整审计事实，Observation 是面向模型预算的压缩视图。

**为什么验证要绑定 revision？** 修改后的旧测试不能证明新代码，revision 用来判断验证是否过期。

**为什么模型摘要不能作为事实？** 摘要可能遗漏或改写内容，目标、文件和验证必须由 Ledger 保存。

**如何避免重复副作用？** 使用 `(turnId, callId)` 缓存首次 ToolResult，同一调用只执行一次。

**为什么不自动提交 Git？** 自动提交会污染用户历史，也不适用于非 Git 项目；Checkpoint 独立于 Git。

**是否保存思维链？** 不保存。只保存用户可见文本、行动、工具、结果和验证证据。

**API Key 怎样保存？** 环境变量或 Electron safeStorage 加密持久化，Renderer 看不到明文。

**下一步最值得做什么？** 若强调安全，增加 OS 沙箱；若强调大型项目效果，增强索引和 Eval；若强调并行开发，引入 Worktree 调度。应根据真实瓶颈选择，而不是同时扩张。

## 19. 两分钟演示讲法

先展示 Workspace、Session 和三档权限。输入真实任务后，在 Trace 中展示 Explore 或读取过程；Guided 模式批准修改，Changes 查看 Diff；批准运行测试，让 Agent 根据一次失败继续修复；最后展示当前 revision 的验证、Review 结果和 Session 恢复。

讲架构时只强调三点：Main 是可信边界；Core 自研循环并保持工具协议；完整历史和模型上下文分离。这样能在有限时间覆盖最有技术含量的内容。

## 20. 答辩时怎样画顶层架构

先画 Renderer、Main 和外部模型三块。Renderer 到 Main 标注 typed IPC，Main 内部再画 Agent Core。Core 向下连接 Tools 和 Storage，向外连接 ModelProvider。不要先画十几个类，否则评委看不出信任边界。

讲解顺序是：用户在 Renderer 发出意图；Main 是唯一可信本地边界；Core 维护循环；模型只能提出 Tool Call；Tools 执行最小动作；Storage 保存事件；AgentEvent 返回 UI。随后再进入上下文和安全细节。

## 21. 如果被问到“最难的问题是什么”

可以回答模型能力不是最难部分，最难的是维持跨多轮工具执行的一致性。具体包括 Assistant Tool Calls 和 Tool Result 必须合法配对；取消要同时影响网络、审批和子进程；长上下文压缩不能丢失目标、revision 和验证；重启只能恢复事实，不能重复副作用。

回答时选择一个真实缺陷作为证据，例如 DeepSeek 因缺少 `tool_call_id` 返回 400。说明根因是历史消息链没有完整保存，修复方式是先持久化 Assistant Tool Calls，再写 Tool Result，并在回放和压缩时保护整个协议组。这样比只说“上下文管理很难”更具体。

## 22. 如果被问到“项目创新点是什么”

创新点不应描述为从未有人做过，而应说明项目如何组合成熟思想解决本场景。SeeCoder 的亮点是可视化 Harness：普通用户在同一界面看到计划、权限、工具活动、Diff、终端、Trace 和验证；底层用 Ledger、Evidence、Observation 和 revision 让这些状态有真实依据。

第二个亮点是“完整历史与模型视图分离”。JSONL 保留审计，ContextBuilder 控制 token，语义摘要失败也不影响权威状态。第三个亮点是只读子 Agent 与主 Agent 单写者，在展示多 Agent 协作的同时避免并行写冲突。

## 23. 如果被要求比较成熟产品

SeeCoder 借鉴 Codex 的任务、事件和本地工作台思想，借鉴 Claude Code 的 Plan、只读子 Agent、Skill 和 Hook 边界，借鉴 TRAE 的完整轨迹，借鉴 CodeBuddy 的对话、变更和预览分区。借鉴的是公开交互和架构思想，不复制闭源实现。

差距需要主动说明：成熟产品通常有更强沙箱、模型优化、代码索引、Worktree 调度、遥测和长期评测。SeeCoder 的价值在于核心机制自研、范围清晰和适合答辩验证，而不是达到商业产品全部能力。

## 24. 常见错误回答

不要说“模型会自己判断安全”，安全由 Core 和工具策略保证。不要说“用了 Electron 所以没有后端”，Main 就是本地后端。不要说“上下文压缩就是总结历史”，它还包括 Ledger、Evidence、Observation、检索和协议保护。

不要说“JSONL 比数据库更先进”，只能说它更适合当前单主进程追加审计。不要说“支持沙箱”，当前只有应用层策略。不要把 Fork 说成 Worktree，也不要把旧测试说成当前代码验证。

## 25. 专有名词怎样用普通语言解释

Harness 可以解释为“模型外部的执行控制系统”。它不负责生成代码内容，而是组织模型、上下文、工具、状态和安全。普通聊天有模型调用，但没有完整 Harness。

SSE 是服务器单向持续发送事件的 HTTP 流。SeeCoder 用它边接收模型文本和 Tool Call 参数，边更新界面。它不同于 WebSocket；当前模型协议只需要服务器向客户端流式发送，Renderer 与 Main 又已有 IPC，因此不需要额外 WebSocket。

幂等表示同一个动作重复请求不会重复产生副作用。SeeCoder 用 `(turnId, callId)` 识别一次工具动作。它只解决同一 Turn 中模型重发，不承诺崩溃后自动续跑。

Compaction 是上下文压缩，不是删除历史。它把旧模型视图替换为 Ledger、摘要和必要消息，原 JSONL 仍然保存。Replay 是事件回放，把持久化事实重新归约成消息、ChangeSet 和终态，而不是重新执行动作。

Revision 是代码状态版本号。每次 Agent 文件变更都会增加，用于判断测试是否仍然有效。它不是 Git commit，也不代表整个仓库所有外部变化。

## 26. 如何回答“为什么不用更复杂技术”

不要把 KISS 解释成技术能力不足。可以说明当前约束是本地、单用户、一个 Main 写入。JSONL、词法检索和顺序主工具已经满足可审计、可测试和确定因果。引入数据库、向量服务和并行写会增加一致性问题，却未被当前规模证明必要。

同时给出演进条件。Session 数量达到数万并需要组合查询时考虑 SQLite；代码知识规模很大且词法召回不足时增加 Embedding；需要并行实现多个功能时增加 Worktree 与合并调度；运行陌生代码时引入 OS 沙箱。这样的回答体现不是拒绝复杂技术，而是按问题选择技术。

## 27. 如何回答“为什么模型能自主修复”

自主修复不是模型一次生成正确补丁。第一次测试失败后，命令工具把退出码和诊断作为 Tool Result，Observation 进入下一轮上下文。模型读取新证据后再修改和测试。Core 保持循环，直到显式完成或触发边界。

因此自主性来自模型决策和 Harness 反馈闭环的组合。没有 Observation，模型看不到真实失败；没有迭代与终止，循环可能失控；没有 revision，旧测试可能被误用。答辩时应同时说明能力与约束。

## 28. 如何回答“上下文算法先进在哪里”

亮点不是使用某个单独摘要算法，而是分层事实管理。Ledger 保证目标和验证，Evidence 保证代码版本，Observation 控制工具输出，MemoryIndex 召回旧决定，模型摘要保留叙事，协议分组保持 API 合法。

任何一层失败都有替代或边界：摘要失败使用确定性回退，Evidence 写入后失效，检索结果预算有限，原历史不删除。相比直接截断最近消息，这套设计更适合多轮代码修改；相比完全依赖向量库，它更容易解释和测试。

## 29. 如何回答“系统是否已经能生产使用”

应回答当前是功能完整的本地 Demo，而不是商业生产平台。核心闭环、权限、回滚、Session 和测试已经实现，能够完成真实任务；但缺少 OS 沙箱、大型仓库索引、多用户隔离、远程调度、完整遥测和长期大规模 Eval。

这种定位不影响项目价值。考核重点是底层机制和工程设计，SeeCoder 已把核心控制流公开实现，并能用测试和轨迹说明实际行为。

## 30. 如何回答“系统前后端如何通信”

Renderer 通过 Preload 暴露的 `window.seecoder` 调用固定 IPC。IPC 是命令，例如创建 Session、启动 Turn、批准工具。Main 校验后调用 Core。Core 产生 AgentEvent，Main 再通过订阅推送给 Renderer。

命令和事件分开很重要。点击取消只是命令，`turn.cancelled` 才是事实。Renderer 不能先改 Zustand 假装成功。Preload 也不暴露通用 channel，避免页面调用未授权 Main 能力。

## 31. 如何回答“为什么错误处理不是 try/catch”

try/catch 只能捕获异常，不能表达测试失败、审批拒绝和输出截断的业务语义。SeeCoder 使用 ToolResult 表示可恢复步骤失败，使用 AgentRunError 表示 Turn 级失败，再用 TurnStatus 表示最终状态。

Provider 负责网络错误和有限重试，Tools 负责本地错误，Core 决定继续或终止，Renderer 负责用户表达。分层后，测试失败能继续修复，取消不会被误报为系统异常，日志也能使用稳定 code。

## 32. 如何回答“为什么 UI 也是技术亮点”

Coding Agent 的可控性需要交互承载。审批必须展示真实路径和命令，Diff 必须对应 ChangeSet，Trace 必须对应 AgentEvent，验证状态必须对应 Ledger revision。UI 不是给后端套皮，而是把 Harness 的状态和证据变成用户能理解的决策界面。

对初学者，渐进披露能隐藏 raw JSON，同时保留“正在读取、修改了哪些文件、测试是否通过”。对答辩者，展开 Trace 又能说明模型轮次、工具参数、耗时和错误。两类用户共享同一事实源。

## 33. 如何回答“为什么没有直接照搬 Codex”

SeeCoder 参考成熟产品的公开思想，例如任务工作台、事件轨迹、计划和只读审查，但核心协议和执行逻辑依据考核要求自行实现。界面采用相似的信息层级，不复制品牌、源码或未公开机制。

成熟产品是设计参照，不是功能完成证据。SeeCoder 每项能力仍要由本地源码、事件和测试证明。
