# SeeCoder 软件质量保证计划

## 1. 质量原则

质量优先级是：数据和权限安全、状态正确、任务成功率、可理解性、性能、视觉细节。不能为了演示速度跳过路径检查、取消、回滚和密钥保护，也不能为了架构美观重写没有可观察问题的模块。

每次修改遵循：

```text
可复现问题
  → 保存证据
  → 定位根因
  → 最小正确修复
  → 增加回归测试
  → 运行相关门禁
  → 真实流程复验
```

## 2. 缺陷优先级

P0 包括越界写入、数据损坏、取消失效、任务无法终止和前后端状态相反，必须停止发布。P1 包括 Tool 消息链错误、长任务无限探索、恢复错误和主流程不可用，优先于新功能。P2 是信息层级、维护性和次要性能。P3 是不影响使用的视觉细节。

缺陷等级按用户影响和数据风险判断，不按修复代码量判断。

## 3. 变更与评审

协议、权限、持久化和工具副作用属于高风险变更，需要先更新对应设计说明，再修改源码，并覆盖异常路径。UI 文案和样式可以使用较轻门禁，但仍需真实页面检查。

评审重点包括：是否扩大本地权限；Session、Turn、Event 语义是否改变；Tool Result 是否始终回填；AbortSignal 是否传到新增异步操作；是否可能重复副作用；日志是否包含密钥或完整敏感内容；UI 是否只依赖公开事件；测试是否对应根因。

## 4. 分支、提交和发布

`main` 保存可发布版本，开发通过经过验证的里程碑进入主分支。提交使用清晰的功能或修复主题，不强推、不伪造时间、不把无关改动混成一次提交。发布前检查 Git 状态、公开仓库、许可证、README、敏感信息和演示材料。

发布候选必须通过完整测试和构建。截止后停止远端 Push。已知限制记录在答辩文档，不用“后续会修”替代当前验证。

## 5. 可观测性与故障管理

一次任务使用 `sessionId`、`turnId` 和 `callId` 关联 UI、模型、工具和事件。Main 日志记录事件类型、耗时、错误码和必要元数据，不记录 API Key、完整文件正文或模型私有思维链。

故障诊断先找 Session 中最后一个成功事件。停在 `model.requested` 时检查 Provider；停在 `tool.requested` 时检查审批和工具；已存在终态但 UI 仍 running 时检查事件订阅与 reducer。重启只能验证恢复，不能掩盖状态清理问题。

## 6. 性能管理

Coding Agent 的主要成本是模型轮数、重复上下文和长工具执行，而不是按钮响应几毫秒。性能记录应包含首 token、整轮耗时、input/output token、工具耗时、审批等待、压缩次数和最终状态。

当前优先优化重复读取、无效探索、过长 Observation 和流式 UI 高频更新。FileEvidence、批量读取、75%/60% 上下文预算、探索上限和 Tool Observation 都同时服务成功率与性能。没有 profiling 证据时不引入缓存层、进程池或数据库。

## 7. 完成定义

每项任务交付变更清单、验证命令、实际结果和已知限制。源码变更至少通过 lint、typecheck 和相关测试；高风险修改运行集成测试；用户流程修改实际启动 Electron；文档修改检查链接、术语和事实一致性。未执行的测试必须明确写“未运行”。

## 8. 文档与源码怎样保持一致

文档只描述当前源码和明确范围。协议字段、上下文阈值、工具权限、Session 操作或安全边界变化时，相关主文档必须与源码同一里程碑更新。答辩文档引用主设计，不再复制一套不同实现。

事实核对优先查看公共类型、Core 控制流和自动测试。README 或旧计划不能作为当前实现证据。文档中的“支持”表示代码存在；“已验证”还需要测试结果；“可演进”表示尚未实现。

## 9. 发布前实际检查

发布候选从干净环境安装依赖并构建，启动 Electron 后走一遍 Workspace、Session、发送、审批、Changes、Terminal、Trace、取消和恢复。随后检查用户数据目录和日志，确认密钥未出现。公开仓库用未登录浏览器访问，确保 README 地址、提交历史和许可证真实。

演示项目应固定初始状态，避免录制前残留上次 Agent 修改。两分钟脚本连续运行三次，记录失败原因。只有偶然一次成功不能作为发布依据。

## 10. 质量指标怎样解释

单元测试数量不能直接代表 Agent 质量。更重要的是 P0/P1 缺陷、真实任务完成率、取消残留进程、消息协议错误、峰值输入 token、重复工具调用和当前 revision 验证率。

指标用于发现趋势，不合成一个虚假的总分。例如 token 降低但任务失败率上升不是优化；工具调用减少但遗漏必要测试也不是进步。

## 11. 软件质量在 SeeCoder 中具体指什么

功能正确性表示系统完成了用户目标，文件和验证结果真实。状态正确性表示 Core、事件和 UI 对 queued、running、waiting、completed、failed 和 cancelled 的理解一致。安全性表示模型不能绕过 Workspace、权限和敏感文件规则。可恢复性表示应用退出后能解释已发生事实，文件修改可以在没有冲突时恢复。

可维护性表示一个模块变化不会迫使无关模块同时修改。例如增加模型供应商应主要发生在 ModelProvider；新增只读工具应通过 ToolRegistry 接入，而不是改写 Renderer；事件字段变化应先修改 Protocol。性能质量表示长任务不会因重复上下文、无限迭代或高频渲染失控。

这些质量属性可能冲突。更强审计会增加磁盘，更多上下文可能提高成功率但增加 token，更严格审批提高安全却降低效率。质量管理的任务是明确优先级和证据，而不是让每项指标都最大。

## 12. 需求追踪怎样实际使用

以“取消必须终止后台执行”为例，需求存在于需求分析，设计存在于 Agent Core 的 AbortSignal 传播，代码入口位于 `cancelTurn`、ModelProvider 和命令工具，测试证据是模型取消与进程树取消用例。如果其中一层缺失，就不能声称需求闭环。

协议变更时，追踪尤其重要。字段重命名不能只改类型，还要覆盖事件信封、Storage、IPC、Renderer、测试和文档。一次全仓库旧术语扫描是这种变更的必要验证。

当前整合后的文档不单独维护大型追踪矩阵，避免与源码快速失真。核心需求表、源码入口和测试场景共同承担轻量追踪；高风险变更在提交说明中列出受影响链路。

## 13. 代码评审关注控制流而非风格

Agent 代码最危险的问题通常不是命名，而是控制流遗漏。例如抛错前没有持久化终态、取消只终止 fetch 没终止命令、Tool Result 在 Assistant Tool Calls 之前写入、finally 没清理活动 Turn。这些问题需要沿真实路径阅读。

评审 `runTurn` 时，应检查每个 return 和 throw 是否进入统一清理；评审 `executeCall` 时，检查校验、审批、Hook、执行和事件顺序；评审 ContextBuilder 时，检查裁剪是否保持协议组；评审 IPC 时，检查 Main 是否重新验证来自 Renderer 的输入。

格式化、lint 和类型检查仍然必要，但它们只消除低层错误。评审结论要指出具体不变量和失败后果，不能只写“结构可以优化”。

## 14. 版本冻结与发布候选

功能冻结后只修复阻断演示、数据安全和主流程的缺陷。不在冻结期增加新工具、重构协议或升级大版本依赖，因为这些变化会扩大回归范围。

Release Candidate 应记录确切 Git commit、Node/pnpm 版本、模型配置名称和测试 Workspace 初始状态。演示视频、README 和公开仓库都对应同一提交，避免现场运行与提交版本不同。

若某项测试因环境无法运行，要记录原因和替代证据。例如 Electron 下载失败不能写成 E2E 通过；可以说明未运行，并保留单元、构建和人工界面证据。真实、可追溯的结果比完整但不可信的清单更重要。

## 15. 缺陷复盘

P0/P1 缺陷修复后需要简短复盘：触发条件、用户影响、为什么现有测试没发现、最小修复和新增防线。复盘不用于追责，而是判断问题来自实现遗漏、协议不清、测试缺口还是文档误导。

例如 DeepSeek 400 的复盘应指出 Tool Result 缺少对应 callId，根因是完整 Assistant Tool Calls 没进入持久历史，新增防线包括消息 sanitize、回放诊断和多工具压缩测试。这样一个缺陷可以同时改善架构、测试和文档。

## 16. 依赖与配置质量

新增依赖前要确认是否真的解决当前问题、是否包含原生模块、许可证和打包影响。Agent 框架依赖被明确禁止。普通工具库也应避免与现有 TypeScript、Electron 和 Vite 版本产生重复运行时。

模型、Base URL、context window 和 API Key 属于运行配置，不能硬编码在源码。修改配置后 Provider 必须实际更新，Session 历史不能丢失。开发和发布环境使用同一配置结构，差异来自值而不是两套逻辑。

Lockfile 是可重复构建的一部分。升级 Electron、Vite、React 或模型协议相关依赖需要单独里程碑和完整回归，不与功能修复混合。

## 17. 已知限制管理

已知限制必须具体说明影响和使用条件。例如“没有 OS 沙箱”表示陌生仓库命令需要谨慎审批；“Fork 不复制 Workspace”表示两个 Session 会操作同一文件；“未完成 Turn 不续跑”表示重启后需要用户重试。

限制不能只存在于代码注释，应出现在答辩与用户可见说明。未来实现对应能力后，再删除限制并增加验证证据。这样文档始终反映实际系统，而不是同时保留旧限制和新宣传。
