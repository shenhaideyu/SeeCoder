# 性能模型与容量分析

## 1. 性能目标

Coding Agent 的性能不是单一首屏时间，而是三段延迟：用户动作到请求发出、模型首个 token、工具执行与验证。优化重点是减少无价值模型轮次和上下文，而不是让本地按钮快几毫秒。

## 2. Turn 成本模型

设第 i 轮输入 token 为 `I_i`、输出为 `O_i`，模型轮数为 N，工具耗时为 `T_j`：

```text
总 token = Σ(I_i + O_i)
总墙钟 ≈ Σ(model latency_i) + Σ(T_j) + 审批/用户等待
```

由于完整历史会在后续轮次重复发送，未压缩时输入成本近似随轮数二次增长。批量读取、工具输出裁剪和早期收敛比微调 temperature 更能降低总成本。

## 3. 当前容量边界

| 对象 | 边界 | 超出行为 |
| --- | --- | --- |
| Context | 配置窗口 70% 触发压缩 | 确定性摘要 + 最近完整组 |
| 文本附件 | 每个 40,000 字符 | 截断 |
| 图片附件 | 每轮最多 4 个 | 多余忽略/不进入请求 |
| read_file | 400 行 | 按行返回片段 |
| read_files | 30 文件×每个 400 行 | schema 拒绝更多 |
| list_files | 200 项 | 停止遍历 |
| search fallback | 1,000 文件、100 结果上限 | 停止收集 |
| ToolResult 给模型 | 约 16,000 字符 | 保留首尾 |
| stdout/stderr | 各最近约 1 MiB | 丢弃更旧部分 |
| Thread JSONL | 暂无归档上限 | 持续增长 |

## 4. 启动性能

Electron 主进程启动需要加载设置、创建 Core、注册 IPC 和窗口。SessionStore 不会启动时解析全部 Thread 事件，列表只读取各 meta.json；这是合理的惰性策略。潜在瓶颈是 Thread 数量很大时逐目录串行读 meta，目前首版规模可接受。

建议测量：Main ready 到 did-finish-load、首个可交互帧、线程列表完成时间。不得用开发模式 Vite 热启动结果冒充打包版启动性能。

## 5. Streaming 性能

Provider 逐 SSE 行产生事件，Core 对每个 textDelta 广播。优点是低首字延迟；风险是极细粒度 delta 造成 Renderer 高频 setState。正确优化点在 Renderer 合并渲染，而非在 Main 持久化每个 delta。最终文本只写一次 JSONL 已避免磁盘放大。

## 6. 上下文性能

`estimateTokens` 为 O(总字符数)，每轮会遍历上下文；compactMessages 又可能构造摘要。对 128k 级文本仍可接受，但长会话会重复计算。若 profiling 证明占比明显，可在消息追加时维护估算增量；在此之前增加缓存会引入失效复杂度，不符合 KISS。

缺少文件内容缓存会导致模型重复读取同一文件，既增加工具轮次又增加输入 token。合理演进是缓存 `(canonicalPath,mtime,size/hash) → 最近摘要/读取范围`，但必须在写入后失效，且不能用缓存绕过权限检查。

## 7. 本地 I/O

JSONL append 简单稳定，但高频 tool.output 也会持续写入；大命令可能形成较多事件。当前输出每块实时持久化与“只记录摘要”的目标存在张力。若真实 profiling 显示会话膨胀，应按固定时间/字节合并 tool.output，最终 ToolResult 保留结构化摘要。

Snapshot 保存 before 全文，适合 Demo 的小文件；大文件或多次修改会放大磁盘。未来可按内容哈希去重，但删除快照前必须考虑仍被 Checkpoint 引用。

## 8. 子进程资源

每条命令独立启动 PowerShell，冷启动成本高于常驻 shell，但隔离、超时和回收更清晰。首版不引入 PTY 或进程池，因为常驻 shell 会携带目录、环境和后台作业状态，显著增加可重复性风险。

需要监控命令结束后 PowerShell、node、测试 runner 是否残留。Windows 使用 taskkill `/t /f` 终止进程树，但极端情况下被分离到其他作业对象的进程仍可能逃逸，这是应用层限制。

## 9. Renderer 容量

长会话主要对象包括消息、工具卡、终端输出和 Trace。默认折叠只减少视觉密度，不自动减少 DOM 数量。达到数百 Item 时应采用窗口化或分页；实现前先用 React Profiler 证明瓶颈，并优先拆分 thread-local reducer，避免任一 delta 让整个三栏重渲染。

## 10. 网络与限流

重试最多 3 次，退避最长仍较短，适合瞬时 429/网关故障，不是完整速率控制。并发两个子 Agent 加主 Agent 可能同时请求模型；当前没有全局请求队列或供应商速率预算。真实使用若频繁 429，应先降低并发或引入简单 semaphore，而不是无限加重试。

## 11. 基准测试方案

| 场景 | 指标 |
| --- | --- |
| 冷启动 50 Thread | 可交互时间、meta 加载 |
| 20 轮流式对话 | 首 token、更新次数、Renderer CPU |
| 100 Tool Item | 展开/切换 Trace 帧时间 |
| 1 MiB stdout | Main 内存、Terminal 响应、JSONL 增量 |
| 100k token 历史 | compact 耗时、压缩后 token、消息合法性 |
| 两子 Agent 并发 | 请求数、峰值内存、取消传播 |
| 命令超时 | 终态延迟、残留进程 |

每个结果记录机器、构建模式、模型/网关与工作区提交，避免不可比较。

## 12. 性能优先级

P0：僵尸进程、无限等待、状态无法终结。P1：重复模型轮次、上下文爆炸、UI 被流式事件卡死。P2：启动和面板切换延迟。P3：小于用户感知阈值的微优化。

## 13. 当前结论

最主要成本来自 Agent 行为效率而非本地算法复杂度。已有真实复杂会话的 21 轮、35 工具和 75k 级输入峰值应作为优化基线。短期优先减少重复读取、强化验证后完成、对流式 UI 批处理；不建议为 Demo 引入 Redis、远程 Queue、数据库或常驻 PTY。
