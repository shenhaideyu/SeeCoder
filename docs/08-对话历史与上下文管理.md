# 对话历史与上下文管理

## 1. 两类数据不能混为一谈

SeeCoder 同时维护：

- **审计历史**：发生过的用户消息、工具调用、结果、审批、变更和终态，目标是完整恢复与追责。
- **模型上下文**：下一次请求真正发送给模型的有限消息，目标是相关、合法且不超过窗口。

若把二者视为同一数组，要么历史被删除而不可审计，要么所有日志反复发送导致 token 无限增长。SeeCoder 以 JSONL 保存前者，以 `ModelMessage[]` 和 ContextLedger 构造后者。

## 2. Thread、Turn、Item、Message

```text
Thread  长期任务容器，绑定 workspace
└─ Turn 一次用户请求的执行
   ├─ Item  恢复语义：message/tool/change/error/compaction
   └─ Event 运行事实：requested/output/completed/status
```

`ModelMessage` 只有 `system/user/assistant/tool` 四种角色。工具调用并非普通文本：assistant 保存 `toolCalls[]`，每个 tool 消息必须保存匹配的 `toolCallId`。

## 3. 消息链不变量

OpenAI 兼容接口通常要求：

```json
{"role":"assistant","tool_calls":[{"id":"call-1"},{"id":"call-2"}]}
{"role":"tool","tool_call_id":"call-1"}
{"role":"tool","tool_call_id":"call-2"}
```

不能从中间删除某个 assistant，也不能只保留第二个 tool 结果。SeeCoder 在实时执行中先落盘完整 Assistant Tool Calls，再执行；恢复时 `sanitizeModelMessages` 丢弃孤立或不完整的历史工具组；压缩时若切点落在 tool 消息上，会向前移动到对应 assistant。

这一机制来自真实故障：固定保留最后 8 条曾从多工具结果中间切断消息链，DeepSeek 返回 `missing field tool_call_id` 的 HTTP 400。

## 4. ContextLedger

Ledger 是结构化工作记忆：

```ts
interface ContextLedgerState {
  goal: string;
  constraints: string[];
  plan: PlanStep[];
  changedFiles: string[];
  tests: string[];
  errors: string[];
}
```

它只保存用户目标、公开计划、文件、测试和错误，不保存私有思维链。集合有明确上限：目标 4,000 字符、计划 50 步、文件 100 个、测试和错误各 30 条，每条 500 字符。

Ledger 的价值是让“关键事实”不依赖其原始消息仍在最近窗口。例如旧工具输出被压缩后，模型仍知道哪些文件已修改、哪些测试失败。

## 5. 上下文组装顺序

每次模型请求由以下内容组成：

1. Core 动态系统提示：模式、安全规则、工作区、效率和终止要求。
2. 工作区根 `AGENTS.md`，最多 20,000 字符，低于固定安全规则。
3. 当前 Thread 的模型消息历史。
4. 本轮开始前排队的 Follow-up。
5. 必要时的探索收敛提示。

附件在用户消息中表现为 ContentBlock。文本附件截断到 40,000 字符；图片以内联 data URL 发送。敏感路径在读取前已经被 WorkspacePolicy 拒绝。

## 6. Token 估算

在没有供应商 tokenizer 的情况下使用保守 Unicode 估算：ASCII 字符约 0.25 token，非 ASCII 字符约 1 token，每条消息增加 4 token 开销，图片按占位符估计。

该算法不是精确计费器，但具有三项优点：零模型绑定、速度快、确定可测。精确 tokenizer 会为每个模型引入不同依赖，兼容网关的模型别名也未必能匹配正确词表。

## 7. 自动压缩

当估算值超过 `contextWindow × 70%` 且消息超过 8 条时：

1. 初始保留最近 8 条。
2. 若切点位于 tool 消息，向前移动到 assistant tool_calls。
3. 将旧消息每条取最多 500 字符。
4. 与 ContextLedger 合并，整体摘要最多 6,000 字符。
5. 构造 `[历史压缩摘要] + 最近完整消息组`。
6. 写入 `context.compacted` Event 与 Compaction Item。

原始 JSONL 不删除。当前算法并不承诺压缩到窗口 55%，而是承诺减少历史并保持工具协议合法。

## 8. 主动压缩

模型可以调用 `compact_context`，Core 以 `force=true` 执行同一确定性算法，并返回 before/after token 估算。它适用于模型已经发现上下文冗余、但尚未达到自动阈值的情况。

## 9. 工具输出裁剪

完整 ToolResult 进入事件存储；发送给模型时 `serializeToolResultForModel` 将超过约 16,000 字符的结果压缩为前 10,000、后 4,000 和说明文本。

保留首尾是因为命令开头通常含命令上下文，末尾通常含失败摘要。只保留开头容易丢失编译器最终错误，只保留末尾又可能丢失执行目标。

## 10. 流式 Delta 为什么不持久化

`message.delta` 只服务当前 UI。最终 `message.completed` 保存完整助手文本。逐 token 写 JSONL 会造成大量磁盘追加、恢复事件膨胀和 Trace 噪音，却不增加语义信息。

异常中断时可能失去尚未形成 completed 的部分文本，这是有意权衡：不完整回复不能作为可靠历史继续驱动 Agent。

## 11. 恢复算法

`hydrateThread` 读取 meta、state 和 events：

- 从 Item 重建模型历史。
- 恢复 ChangeSet、Checkpoint、计划和 Ledger。
- 兼容 V1 `event` 与 V2 `payload`。
- 跳过损坏 JSONL 行。
- 清理孤立工具链。
- 若最后 `turn.started` 没有终态，补写一次 `interrupted` 失败事件。

## 12. 为什么不使用向量数据库

当前任务规模下，向量库会增加索引一致性、Embedding 成本和依赖，却不能自动解决消息协议和状态恢复。代码定位首先通过 `rg` 和文件工具完成，Ledger 保存任务状态。未来面对百万行仓库时可增加检索索引，但它应是 Context Acquisition 的可替换部件，不应成为历史事实源。

## 13. 已知限制

- 只加载根 `AGENTS.md`，没有目录作用域规则合并。
- 无文件内容哈希缓存，模型仍可能重复读取同一版本文件。
- 确定性摘要不理解语义重要性，依赖 Ledger 弥补。
- 图片 token 估算不精确。
- JSONL 完整历史会持续增长，目前没有归档压缩策略。

## 14. 历史、工作记忆与即时上下文的生命周期

三类信息的保留周期不同：

| 信息 | 产生 | 保留 | 消费者 |
| --- | --- | --- | --- |
| Event/Item | 每次状态变化 | 原始 JSONL 长期保留 | 恢复、Trace、审计 |
| ContextLedger | 目标/计划/改动/测试/错误变化 | `state.json` 原子覆盖 | 压缩、完成摘要 |
| ModelMessage | 用户、assistant、tool 语义消息 | 内存，压缩后替换 | 下一轮模型 |
| message.delta | 流式 token | 当前 Renderer 生命周期 | 实时显示 |

Ledger 不是 Event 的替代品：它只保存最新结构化结论，不能回答“第 3 轮发生了什么”；Event 也不是 Ledger 的替代品：每轮让模型扫描全部事件会放大 token 并混入过期状态。

## 15. 消息选择示例

压缩前：

```text
U1 原始目标
A1 tool_calls(read a, read b)
T1 read a result
T2 read b result
A2 分析 + tool_call(apply_patch)
T3 patch result
A3 tool_call(run_command)
T4 失败日志 40k
U2 用户追加要求
A4 tool_call(read_file)
T5 最新文件
```

若阈值触发，不能简单 `slice(-8)` 后从 T1 或 T2 开始。算法把切点向前移动到 A1，使工具组完整；更早内容进入 Ledger + 确定性摘要。压缩后模型看到：

```text
U(summary: 原目标、计划、改动、失败测试、早期消息片段)
A1 tool_calls(...)
T1
T2
...
T5
```

若最近一个工具组本身非常大，裁剪发生在 ToolResult 序列化层，而不是删除配对消息。

## 16. 恢复时的工具链修复

`sanitizeModelMessages` 使用“整组提交”策略：遇到 assistant.toolCalls 后暂存整组，收到全部匹配 callId 才提交到安全历史；缺失、重复外来或孤立 tool 消息被丢弃。这样恢复出的消息链一定满足最小协议约束。

这不是业务数据修复：被丢弃的原始 Item 仍在 JSONL，Trace 可见。算法只修复下一次模型请求视图，避免为了兼容接口篡改审计历史。

## 17. Token 预算计算示例

假设窗口配置 128,000，自动阈值约 89,600。对 20,000 个 ASCII 字符估算约 5,000 token，对 20,000 个常见中文字符估算约 20,000 token，再加每消息 4 token。该估算刻意对中文更保守。

图片只按 `[image]` 占位估算，明显低估视觉模型实际成本。因此图片轮次不能依赖 70% 阈值作为严格防溢出；附件数量与大小上限是第二道容量边界。

## 18. 过期信息与冲突

对话可能同时包含“测试失败”和更晚的“测试通过”。Ledger 当前按时间追加而非状态归并，模型需理解新旧关系。更强设计可把测试记录建模为 `{command,revision,status,timestamp}` 并只保留每个验证目标最新结果，但当前尚未实现。

原则是：压缩摘要必须标注这是历史，而不能把旧 observation 写成当前事实；ChangeSet 之后的验证才可作为完成证据。文档和 UI 不应宣称当前实现已经严格验证“新鲜度”。

## 19. 为什么不用 RAG 代替上下文管理

RAG 解决“从大语料找相关片段”，不解决工具消息配对、审批状态、变更版本和终止条件。若只把所有消息向量化再检索，可能取回旧文件版本或孤立 ToolResult，破坏时序语义。SeeCoder 将代码搜索与会话状态分开；未来加入索引时也只作为文件检索候选，最终内容仍需 WorkspacePolicy 和 read_file 获取。

## 20. 上下文回归测试要求

- 自动压缩前后 token 估算下降。
- 原始用户目标只在压缩请求中保留一个权威副本。
- 多工具组不能被从中间切开。
- orphan tool 消息不会发往 Provider。
- 超长 ToolResult 给模型的版本小于边界，事件中的结果仍完整。
- 主动 compact 产生 call、result 与 CompactionItem，顺序正确。
- 工作区切换后不能复用旧 Thread 的 ModelMessage。
