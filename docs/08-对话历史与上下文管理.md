# 对话历史与上下文管理

## 1. 两类数据不能混为一谈

SeeCoder 同时维护：

- **审计历史**：发生过的用户消息、工具调用、结果、审批、变更和终态，目标是完整恢复与追责。
- **模型上下文**：下一次请求真正发送给模型的有限消息，目标是相关、合法且不超过窗口。

若把二者视为同一数组，要么历史被删除而不可审计，要么所有日志反复发送导致 token 无限增长。SeeCoder 以 JSONL 保存前者，以 `ModelMessage[]` 和 ContextLedger 构造后者。

## 2. Thread、Turn、Item、Message

```text
Thread  长期任务容器，绑定 workspace
└─ Turn 一次用户请求的执行
   ├─ Item  恢复语义：message/tool/change/error/compaction
   └─ Event 运行事实：requested/output/completed/status
```

`ModelMessage` 只有 `system/user/assistant/tool` 四种角色。工具调用并非普通文本：assistant 保存 `toolCalls[]`，每个 tool 消息必须保存匹配的 `toolCallId`。

## 3. 消息链不变量

OpenAI 兼容接口通常要求：

```json
{"role":"assistant","tool_calls":[{"id":"call-1"},{"id":"call-2"}]}
{"role":"tool","tool_call_id":"call-1"}
{"role":"tool","tool_call_id":"call-2"}
```

不能从中间删除某个 assistant，也不能只保留第二个 tool 结果。SeeCoder 在实时执行中先落盘完整 Assistant Tool Calls，再执行；恢复时 `sanitizeModelMessages` 丢弃孤立或不完整的历史工具组；压缩时若切点落在 tool 消息上，会向前移动到对应 assistant。

这一机制来自真实故障：固定保留最后 8 条曾从多工具结果中间切断消息链，DeepSeek 返回 `missing field tool_call_id` 的 HTTP 400。

## 4. ContextLedger

Ledger 是结构化工作记忆：

```ts
interface ContextLedgerStateV2 {
  version: 2;
  goal: string;
  acceptanceCriteria: string[];
  constraints: string[];
  plan: PlanStep[];
  changeRevision: number;
  decisions: DecisionRecord[];
  files: FileStateRecord[];
  validations: ValidationRecord[];
  errors: ErrorRecord[];
}
```

它只保存用户目标、公开计划、文件 hash、验证和错误，不保存私有思维链。每次 ChangeSet、撤销或 Checkpoint 恢复都会产生新 `changeRevision`；验证记录绑定执行时的 revision，因此旧测试通过不能替更新后的代码背书。旧字符串数组状态在读取时迁移为 V2，原始 JSONL 不重写。

Ledger 的价值是让“关键事实”不依赖其原始消息仍在最近窗口。例如旧工具输出被压缩后，模型仍知道哪些文件已修改、哪些测试失败。

## 5. 上下文组装顺序

每次模型请求由以下内容组成：

1. Core 动态系统提示：模式、安全规则、工作区、效率和终止要求。
2. 工作区根 `AGENTS.md`，最多 20,000 字符，低于固定安全规则。
3. ContextLedger V2、当前 revision Evidence 和按需召回的历史事实。
4. 经协议分组保护的最近模型消息，以及必要时的旧语义摘要。
5. 本轮开始前排队的 Follow-up 与必要的探索收敛提示。

附件在用户消息中表现为 ContentBlock。文本附件截断到 40,000 字符；图片以内联 data URL 发送。敏感路径在读取前已经被 WorkspacePolicy 拒绝。

## 6. Token 估算

在没有供应商 tokenizer 的情况下使用保守 Unicode 估算：ASCII 字符约 0.25 token，非 ASCII 字符约 1 token，每条消息增加 4 token 开销，图片按占位符估计。

该算法不是精确计费器，但具有三项优点：零模型绑定、速度快、确定可测。精确 tokenizer 会为每个模型引入不同依赖，兼容网关的模型别名也未必能匹配正确词表。

## 7. 自动压缩

预算先扣除模型最大输出和安全余量：

```text
availableInput = contextWindow - maxOutputTokens - max(2048, contextWindow × 5%)
```

估算输入超过 `availableInput × 75%` 时自动压缩，目标不超过 `availableInput × 60%`。旧自然语言交给当前 Provider 以 `purpose=context_summary`、`temperature=0`、无工具模式生成 Zod 校验的 JSON 摘要；网络、非法 JSON、超时或取消时立即使用确定性摘要，不让摘要失败升级为主 Turn 失败。摘要输入自身也按可用窗口限制，避免“为了压缩而超窗”。

预算不足时依次去除检索结果、Evidence、裁短旧摘要和最近自然语言原文；Ledger、最新交互和最近完整 assistant/tool 组不会被拆除。原始 JSONL 不删除，`context.compacted` 记录 before/after、可用预算、摘要来源、召回数和丢弃 Evidence 数。

## 8. 主动压缩

模型可以调用 `compact_context` 主动触发同一流程。真正压缩必须延后到当前轮全部 Tool Result 写回之后；否则 `compact_context` 自己的 assistant/tool 组会被拆断。工具先返回“已接受压缩请求”，before/after 指标通过 `context.compacted` 事件和 Compaction Item 提供。

## 9. 工具输出裁剪

完整 ToolResult 进入事件存储；发送给模型的是按工具语义生成的 Observation。读取保留路径、hash、行范围和 Evidence 引用；搜索去重并保留文件与行号；命令保留 exitCode、stdout 首尾、stderr 尾部、诊断行和 duration；Diff 保留统计与关键 hunk；写入只返回路径、revision 和规模，不重复注入完整 before/after。未知工具才使用 16,000 字符首尾回退。

这种设计优于统一字符截断：它保留 Agent 下一步判断所需的稳定字段，同时把审计完整性留给 JSONL，避免把巨大日志反复塞回模型。

## 10. 流式 Delta 为什么不持久化

`message.delta` 只服务当前 UI。最终 `message.completed` 保存完整助手文本。逐 token 写 JSONL 会造成大量磁盘追加、恢复事件膨胀和 Trace 噪音，却不增加语义信息。

异常中断时可能失去尚未形成 completed 的部分文本，这是有意权衡：不完整回复不能作为可靠历史继续驱动 Agent。

## 11. 恢复算法

`hydrateThread` 读取 meta、state 和 events：

- 从 Item 重建模型历史。
- 恢复 ChangeSet、Checkpoint、计划和 Ledger。
- 兼容 V1 `event` 与 V2 `payload`。
- 跳过损坏 JSONL 行。
- 清理孤立工具链。
- 若最后 `turn.started` 没有终态，补写一次 `interrupted` 失败事件。

## 12. 为什么不使用向量数据库

当前任务规模下，向量库会增加索引一致性、Embedding 成本和依赖，却不能自动解决消息协议和状态恢复。代码定位首先通过 `rg` 和文件工具完成，Ledger 保存任务状态。未来面对百万行仓库时可增加检索索引，但它应是 Context Acquisition 的可替换部件，不应成为历史事实源。

## 13. 已知限制

- 只加载根 `AGENTS.md`，没有目录作用域规则合并。
- Evidence 当前只在进程内保存；重启后会从后续真实读取重新建立，不把文件正文写入 `state.json`。
- 语义摘要质量取决于当前模型；确定性回退保证可继续执行，但叙事质量较低。
- 图片 token 估算不精确。
- JSONL 完整历史会持续增长，目前没有归档压缩策略。

## 14. 历史、工作记忆与即时上下文的生命周期

三类信息的保留周期不同：

| 信息 | 产生 | 保留 | 消费者 |
| --- | --- | --- | --- |
| Event/Item | 每次状态变化 | 原始 JSONL 长期保留 | 恢复、Trace、审计 |
| ContextLedger V2 | 目标/计划/改动/验证/错误变化 | `state.json` 原子覆盖 | 压缩、完成新鲜度判断 |
| FileEvidence | 文件读取 | 当前 Thread 进程生命周期，修改即失效 | 去重读取、ContextBuilder |
| MemoryEntry | Event 与 Ledger 派生 | 内存，可从持久化数据重建 | 本地关键词/路径召回 |
| ModelMessage | 用户、assistant、tool 语义消息 | 内存，压缩后替换 | 下一轮模型 |
| message.delta | 流式 token | 当前 Renderer 生命周期 | 实时显示 |

Ledger 不是 Event 的替代品：它只保存最新结构化结论，不能回答“第 3 轮发生了什么”；Event 也不是 Ledger 的替代品：每轮让模型扫描全部事件会放大 token 并混入过期状态。

## 15. 消息选择示例

压缩前：

```text
U1 原始目标
A1 tool_calls(read a, read b)
T1 read a result
T2 read b result
A2 分析 + tool_call(apply_patch)
T3 patch result
A3 tool_call(run_command)
T4 失败日志 40k
U2 用户追加要求
A4 tool_call(read_file)
T5 最新文件
```

若阈值触发，不能简单 `slice(-8)` 后从 T1 或 T2 开始。算法把切点向前移动到 A1，使工具组完整；更早内容进入 Ledger + 确定性摘要。压缩后模型看到：

```text
U(summary: 原目标、计划、改动、失败测试、早期消息片段)
A1 tool_calls(...)
T1
T2
...
T5
```

若最近一个工具组本身非常大，裁剪发生在 ToolResult 序列化层，而不是删除配对消息。

## 16. 恢复时的工具链修复

`sanitizeModelMessages` 使用“整组提交”策略：遇到 assistant.toolCalls 后暂存整组，收到全部匹配 callId 才提交到安全历史；缺失、重复外来或孤立 tool 消息被丢弃。这样恢复出的消息链一定满足最小协议约束。

这不是业务数据修复：被丢弃的原始 Item 仍在 JSONL，Trace 可见。算法只修复下一次模型请求视图，避免为了兼容接口篡改审计历史。

## 17. Token 预算计算示例

假设窗口配置 128,000、最大输出 8,192，安全余量 6,400，则可用输入为 113,408，自动触发约 85,056，压缩目标约 68,045。对 20,000 个 ASCII 字符估算约 5,000 token，对 20,000 个常见中文字符估算约 20,000 token，再加每消息 4 token。该估算刻意对中文更保守。

图片只按 `[image]` 占位估算，明显低估视觉模型实际成本。因此图片轮次不能依赖 70% 阈值作为严格防溢出；附件数量与大小上限是第二道容量边界。

## 18. 过期信息与冲突

对话可能同时包含“测试失败”和更晚的“测试通过”。Ledger V2 将验证建模为 `{command,revision,status,timestamp}`；只有当前 `changeRevision` 的成功验证才是新鲜证据。再次写入、撤销或恢复后，旧通过记录仍留作审计，但 `finish` 返回 `verificationStatus=warning`，UI 明确显示“完成，但验证已过期”。

语义摘要始终标注为叙事参考，不能覆盖 Ledger 的文件、验证和错误事实；检索也会排除旧 revision 的成功验证、resolved 错误和 superseded 决策。

## 19. 为什么不用 RAG 代替上下文管理

RAG 解决“从大语料找相关片段”，不解决工具消息配对、审批状态、变更版本和终止条件。若只把所有消息向量化再检索，可能取回旧文件版本或孤立 ToolResult，破坏时序语义。SeeCoder 将代码搜索与会话状态分开；未来加入索引时也只作为文件检索候选，最终内容仍需 WorkspacePolicy 和 read_file 获取。

## 20. 上下文回归测试要求

- 自动压缩达到 75% 触发条件并压到可用输入 60% 目标内。
- 原始用户目标只在压缩请求中保留一个权威副本。
- 多工具组不能被从中间切开。
- orphan tool 消息不会发往 Provider。
- 摘要非法、网络失败与取消不会拖垮主 Turn。
- 各类超长 ToolResult 生成语义 Observation，事件中的结果仍完整。
- 主动 compact 在当前工具组完成后产生 CompactionItem，顺序正确。
- 重复读取同一 hash/范围返回 Evidence 引用；修改和恢复使其失效。
- 修改后未重新验证时 finish 给出过期警告。
- 工作区切换后不能复用旧 Thread 的 ModelMessage。

## 21. 方案 F：分层混合上下文

SeeCoder 2.0 的目标上下文不再由固定“最近 8 条”单独决定，而由预算器按优先级组合：固定安全规则、Ledger V2、协议完整消息组、当前 revision Evidence、最近对话、轻量检索结果和旧语义摘要。可用输入预算先扣除最大输出与安全余量；达到 75% 时压缩，目标低于可用预算 60%。

每次实际压缩使用当前模型以 `temperature=0`、无工具、最多 2,048 输出 token 生成结构化语义摘要。摘要只处理叙事内容，不能覆盖 Ledger 中的文件、验证、错误和审批事实；网络、取消或 JSON 校验失败时使用确定性摘要，主 Turn 继续。

文件读取以 path、contentHash、行范围和 changeRevision 建立 Evidence。相同版本的重复读取只返回引用，由 ContextBuilder 注入权威 Evidence；文件写入、补丁、撤销和 Checkpoint 恢复均使对应缓存失效。历史召回采用本地关键词、中文二元组、路径、错误码、状态和 revision 评分，不引入向量数据库。
