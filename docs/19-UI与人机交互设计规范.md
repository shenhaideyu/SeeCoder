# UI 与人机交互设计规范

## 1. 设计目标

SeeCoder 的界面不是 IDE 功能堆叠，而是帮助用户回答四个问题：Agent 正在做什么、刚刚改变了什么、现在需要我决定什么、结果是否经过验证。参考成熟 Coding Agent 的渐进披露和任务工作台思想，不机械复制品牌或布局。

## 2. 信息优先级

从高到低：

1. 待审批、待输入、失败和取消。
2. 当前执行阶段与最近动作。
3. 用户目标、Agent 最终回答和验证结果。
4. 文件变更与计划。
5. 工具参数、原始输出、token 和调试轨迹。

低优先信息默认折叠或进入右侧面板。主对话不展示 raw JSON、完整 stdout 或内部事件名。

## 3. 三栏职责

| 区域 | 内容 | 禁止内容 |
| --- | --- | --- |
| 左栏 | 工作区、全局入口、任务分组 | 当前工具日志、Diff 正文 |
| 中栏 | 对话、计划摘要、决策卡、Composer | 永久展开的技术 Trace |
| 右栏 | Changes、Files、Terminal、Preview、Trace | 重复完整聊天 |

1280×800 时右栏折叠为抽屉，不能通过压缩中栏使 Composer 或正文不可用。左栏折叠后仍保留打开入口和当前工作区识别。

## 4. 工作区切换

左栏顶部显示当前工作区名称和可展开菜单；菜单列出最近目录、完整路径 tooltip、选择其他目录和打开目录。切换前若有活动 Turn，系统执行真实取消并给出反馈。任务列表只显示当前工作区 Thread，避免用户误以为 Agent 在另一个项目操作。

工作区是最高风险上下文，不能只显示一个模糊项目名。Composer 附近应以低视觉权重显示当前目录或安全边界提示。

## 5. 任务状态呈现

不使用虚假百分比。阶段由事件推导：

```text
准备中      turn.started 到 model.requested
思考与规划  model.requested 到完成流
读取项目    最近工具为 read/search/list
等待确认    approval.requested
等待回答    user.input.requested
修改代码    write/apply_patch
验证中      run_command 且命令为测试/构建
审查中      review.started
已完成/失败/已取消  终态事件
```

同一状态只保留一个主要位置。顶栏可显示紧凑状态，主流只在状态转换或需要行动时出现卡片。

## 6. 工具卡片

默认摘要使用用户语言：

```text
读取 5 个文件 · 1.2s
修改 src/form.ts · +8 −2
运行单元测试 · 通过 · 4.6s
```

展开层才显示参数、stdout/stderr、callId、错误码与耗时。执行中提供动效但避免持续大面积脉冲；完成后绿色只用于真实成功，受控限制用中性状态，拒绝与失败不能混淆。

## 7. 错误卡片

错误应分四层：

- 发生了什么：例如“模型服务拒绝了消息格式”。
- 为什么重要：例如“本轮无法继续，文件尚未修改”。
- 系统已做什么：例如“已停止任务并保留轨迹”。
- 用户可做什么：例如“检查模型兼容性后重试”。

原始 400 body 和 stack trace 放在详情/Trace。错误色用于图标、边框或短标题，不用整块高饱和背景压过正文。

## 8. Changes 面板

必须区分两种事实：Git 工作区状态和 SeeCoder ChangeSet。Git status 可能包含用户原有文件，ChangeSet 只表示 Agent 已记录的写入。面板结构应为：

```text
本轮变更摘要
├─ Agent ChangeSet 列表、查看 Diff、撤销
└─ Git 工作区
   ├─ Unstaged / Staged / Untracked
   └─ Stage、Commit、Push
```

当 Git 有改动但 ChangeSet 为 0 时，不应同时显示“0 个 ChangeSet”和大面积“还没有变更”造成矛盾；空态只针对当前分区。危险 Git 操作使用对话框展示范围与命令结果。

## 9. Composer

Composer 永远固定在中栏可见区域底部，但不能覆盖最后一条消息；对话区保留等于 Composer 高度的安全内边距。输入框支持多行增长到上限后内部滚动。主要按钮只有发送/停止，其他模式、附件、计划和模型使用次级控制。

- 空输入时发送禁用并说明原因。
- 运行中输入成为 Follow-up，按钮语义明确。
- 发送后不清除失败附件，成功受理后才清空。
- `Ctrl+Enter` 发送，`Esc` 取消只在任务活动时生效。

## 10. 权限交互

Plan、Guided、Auto 使用明确菜单而非循环按钮。每项包含一句行为解释，选择后显示当前模式。审批卡展示动作、目标、风险原因以及允许/拒绝；拒绝可填写原因并回传模型。

“Auto”不能使用“完全访问”等误导文案，因为网络、安装、删除、提交与推送仍需审批，且系统没有 OS 级沙箱。

## 11. 视觉系统

品牌种子色为 CMYK `C50 M100 Y0 K40` 的近似屏幕色 `#4D0099`。颜色语义与品牌色分开：紫色表示选择与主操作，绿色表示成功，橙色表示等待/风险，红色表示失败。

采用 4/8/12/16/24/32 间距尺度，控件高度集中在 32/36/40，圆角集中在 8/12。正文默认 14–15px，元数据 12px，页面标题 20–24px。避免每个卡片自定义 13、17、19、23px 间距。

## 12. 可访问性

- 文本和交互状态满足 WCAG AA 对比度。
- 所有图标按钮有 aria-label/tooltip。
- 键盘焦点环不可仅靠颜色差异。
- 选中、错误、成功不能只用颜色表达。
- 动效尊重 `prefers-reduced-motion`。
- 长中文路径、英文错误、代码均允许换行或水平滚动，不能挤出按钮。

## 13. 性能交互

流式文本应按帧或短时间片合并更新，避免每 token 触发整个页面重渲染；Terminal 与 Trace 只渲染可见或有限窗口；折叠工具输出不应先构造昂贵 Monaco 模型。优化以用户可感知延迟为目标，不为了理论性能提前引入复杂虚拟化。

## 14. 可用性验收

- 新用户在 30 秒内能选择工作区并发送任务。
- 运行中能在 5 秒内判断当前阶段。
- 所有等待状态都有明确可操作入口。
- 所有可见按钮产生真实动作、页面或明确不可用说明。
- 1280×800 无遮挡，1920×1080 不出现无意义超宽正文。
- 长错误、长路径、大 Diff 不破坏工具栏对齐。
- 仅用键盘可发送、切换面板、处理审批和取消。

## 15. 当前实现差距

Renderer 仍集中在大型 `main.tsx`，多个界面状态与组件同文件，增加一致性维护成本；尚无完整组件库和视觉回归基线；长会话没有虚拟列表；阶段状态部分依赖事件推导。后续应先抽取事件 reducer 与基础交互组件，再做视觉 polish，而不是继续添加页面。
