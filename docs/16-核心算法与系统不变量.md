# 核心算法与系统不变量

## 1. 为什么先定义不变量

Agent 的输出具有随机性，但 Harness 不能随机。系统不变量描述“无论模型说什么都必须成立”的事实，是设计、代码评审和回归测试的共同语言。

## 2. Turn 状态机

协议当前状态为：

```text
queued → running
running → waitingApproval → running
running → waitingInput    → running
running → completed | failed | cancelled | limitReached
waiting* → cancelled
```

`planning/waiting_tool/verifying` 目前是 UI 展示阶段，不是持久化 TurnStatus。这样减少状态爆炸，但意味着精细阶段需由最近事件推导。若未来把这些阶段加入协议，必须定义每条转换的唯一触发事件，不能让 UI 与 Core 各自维护一套枚举。

不变量：终态不可回到 running；每个 Thread 至多一个活动 Turn；所有退出路径都经过 finally。

## 3. 主循环伪代码

```ts
for iteration in 1..24:
  assert !cancelled
  injectFollowUps()
  maybeConstrainExploration()
  context = compactIfNeeded(history)
  response = streamModel(system + context, tools)
  persistCompleteAssistantResponse(response)

  if response.finishReason == 'length':
    recoverOrFailAfterThree()
    continue

  if response.toolCalls.isEmpty():
    complete()
    break

  for call of response.toolCalls:
    result = executeExactlyOnce(call)
    appendToolObservation(result)
    if call.name == 'finish' && result.ok:
      complete()

  if threeFailuresWithoutProgress(): fail()

if not finished: limitReached()
```

该算法把模型建议与系统裁决分开：模型可以请求完成、写入或命令，但 Core 决定是否合法以及 Turn 是否真正进入终态。

## 4. 工具消息配对算法

对每个含 toolCalls 的 assistant 消息，建立 pending callId 集合；只接受属于集合的 tool 消息；集合清空后整组进入安全历史。遇到普通消息前集合仍未清空，则丢弃整组。

复杂度为 O(n + c)，n 是消息数，c 是调用数。牺牲不完整工具 observation 是正确选择，因为保留孤立结果会让整个下一次 API 请求无效。

## 5. 上下文压缩算法

设历史消息为 `M[0..n)`：

```text
if estimate(M) <= 0.7 × contextWindow or n <= 8:
    return M
k = n - 8
while k > 0 and M[k].role == tool:
    k--
summary = truncate(ContextLedger + M[0..k), 6000 chars)
return [summaryUserMessage] + M[k..n)
```

关键不变量不是“正好保留 8 条”，而是保留的工具组完整。算法只保证明显减少，不保证压到 55%，因此极长的最近工具组仍可能超窗。

## 6. 路径归属算法

词法检查：

```ts
candidate = resolve(root, input)
rel = relative(root, candidate)
inside = !rel.startsWith('..') && !isAbsolute(rel)
```

真实检查：对 root 与目标存在祖先执行 realpath，再重复 relative 判断。新文件无法 realpath，因此从最近存在祖先推导。Windows 比较需要大小写归一化，但不能仅用字符串 startsWith。

不变量：任何工具实际访问的路径都由当前 Core 的 WorkspacePolicy 生成；工作区切换前取消旧 Core。

## 7. ToolCall 幂等算法

缓存键是 `(turnId, callId)`，值是最终 ToolResult：

```text
if cache[turnId].has(callId): return cachedResult
result = execute(call)
cache[turnId][callId] = result
return result
```

不能只用 callId 作为全局键，因为不同 Turn 的模型可能重复生成同一 ID。缓存只覆盖同一进程中的 Turn；崩溃恢复不会自动续跑，所以无需跨重启重放缓存。

## 8. 无进展算法

系统区分两类无进展：

1. 工具连续失败：三次后终止。
2. 工具都成功但只重复探索：连续 4 轮提醒，7 轮后只读调用返回受控预算错误。

如果只统计错误，重复 read_file 永远成功，Agent 可以耗尽 token；如果把探索预算当普通失败，则 Harness 自己的限制会误杀下一轮修复。因此两套计数器分离。

## 9. Checkpoint 冲突算法

文件修改后保存 afterHash。恢复前重新读取当前文件并计算 SHA-256：

```text
currentHash == afterHash → 可安全恢复 before
currentHash != afterHash → checkpoint_conflict
```

该算法保护用户在 Agent 修改后的手工编辑。它不能解决多个文件恢复中间的 I/O 故障，也不等价于 Git 三方合并。

## 10. 事件持久化算法

状态变更遵循“先持久化事实，再向监听器广播”，流式 delta 除外。这样 UI 收到完成事件时，重启恢复数据已经存在。JSONL 每行独立 JSON，使崩溃最多损坏尾行；读取器逐行容错。

## 11. 资源上限

| 资源 | 当前边界 | 目的 |
| --- | --- | --- |
| 主 Agent 迭代 | 24 | 保证最终收敛 |
| 子 Agent 迭代 | 6 | 限制委派成本 |
| 并发子 Agent | 2 | 控制 token 与竞争 |
| 连续只读轮 | 4 提醒、7 阻止 | 减少探索循环 |
| 模型重试 | 总计 3 次 | 覆盖短暂网络故障 |
| 命令超时 | 默认 60 秒，最大 120 秒 | 防止永久阻塞 |
| 命令输出 | stdout/stderr 各约 1 MiB | 控制内存 |
| 模型 ToolResult | 约 16,000 字符 | 控制上下文 |

这些是经验预算，不是理论最优值。调整必须基于真实 Eval 的成功率、token 和耗时分布。

## 12. 可测试不变量清单

- Plan 模式不能产生文件或进程副作用。
- 失败补丁不会修改任一目标文件的内容。
- 取消等待审批的 Turn 不留下活动状态。
- 截断响应不能标记 completed。
- 重复 callId 不重复写入。
- 不完整历史工具组不会发送给模型。
- 工作区 A 的 Thread 不能在工作区 B hydrate。
- 恢复 Checkpoint 遇到后续编辑必须拒绝。
- 敏感文件不出现在 list/read/search 结果。

## 13. 尚未形式化的不变量

“完成前必须验证”目前主要靠系统提示和 `finish.verification`，Core 没有证明验证命令真实成功并与当前 ChangeSet 对应；“模型不得修改无关文件”也只有工作区边界，没有需求级路径白名单。这些应作为质量评测目标，不应在文档中冒充强保证。
