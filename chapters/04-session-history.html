第二部分 · 理解核心

Session、事件与分支

Session 保存一项长期任务，事件保存已经发生的事实，分支允许从某个历史位置开始另一条对话路线。理解分支时，最重要的不是记住字段，而是分清“磁盘真正保存的内容”和“读取时临时拼出的可见历史”。

先理解四个基本概念

Workspace

用户选择的本地项目目录。不同 Session 可以属于同一个 Workspace，并看到同一份当前文件。

Session

左侧栏中的一项长期任务。它可以包含多次追问、多次执行和一条独立的事件历史。

Turn

用户发送一次请求后，从开始运行到完成、失败或取消的一个执行周期。

Event

已经发生的一项事实，例如用户发言、工具完成、文件产生修改或 Turn 结束。

层级关系Workspace：本地项目目录
└─ Session：修复登录错误
   ├─ Turn 1：定位登录失败原因
   │  └─ 多条 Event
   └─ Turn 2：根据结果继续修改
      └─ 多条 Event

Session 解决“这段长期任务属于哪条对话”；Turn 解决“这一次执行现在是什么状态”；Event 解决“执行过程中究竟发生过什么”。三者不能混成一个对象，否则恢复、取消和分支都会变得含糊。

Session 在磁盘上保存什么

每个 Session 都有自己的数据目录。目录里的文件不是项目源码，而是 SeeCoder 为恢复任务保存的运行数据。

内容用途写入方式
meta.json标题、Workspace、创建时间和分支关系整体替换
events.jsonl按顺序保存已经发生的事件只在末尾追加
state.json当前目标、计划、修改版本和验证结果整体替换
Artifact保存放不进模型上下文的大型工具输出独立文件
Snapshot保存文件修改前的内容，用于撤销或恢复独立文件

events.jsonl 是“一行一个 JSON 对象”的文件。每条事件都有一个从小到大递增的序号。序号只是 Session 内的时间位置，可以把它理解成事件时间线上的第几个节点。

为什么不能只保存最终聊天文字

一次任务不只有用户和模型的文字。模型可能请求读取文件、等待审批、执行补丁、运行测试，然后根据失败结果继续修改。如果只保存最终回复，应用重启后就无法回答下面的问题：

  • 模型当时请求了哪个工具，参数是什么？
  • 用户是否批准了写入？
  • 文件修改属于哪一次 Turn？
  • 测试结果对应修改前还是修改后的代码？
  • 任务为什么停止？

因此 SeeCoder 保存事件事实。应用重启后按序读取事件，重新建立消息、修改记录和任务状态，但绝不会重新执行历史工具。历史中即使出现“运行命令”事件，恢复过程也只承认它曾经发生，不会再运行一次命令。

分支要解决什么问题

假设父 Session 已经完成下面五个事件：

事件序号已经发生的事实
1用户要求修复登录问题
2Agent 读取登录模块
3Agent 修改验证逻辑
4测试失败，发现兼容性问题
5继续修改并完成任务

现在用户想回到事件 3，尝试另一种处理方式，同时保留原来的事件 4、5。直接删除事件 4、5 会破坏历史；复制全部事件又会浪费空间。分支采用第三种办法：

记录“我来自哪个 Session、继承到哪个位置”，然后只保存自己的新事件。

磁盘上没有一份完整的子历史

假设在父 Session 的事件 3 处分叉，磁盘实际保存的是：

概念示例父 Session
├─ meta.json
└─ events.jsonl：1、2、3、4、5

子 Session
├─ meta.json：父 Session + 分叉位置 3
└─ events.jsonl：4′、5′

这里的 4′、5′ 表示子分支自己的新事件。真实实现创建子分支后，第一条增量通常是“子 Session 已创建”，然后才是新的用户消息和执行事件。子分支的事件序号从分叉位置后继续增长，保证拼接后仍是一条有序时间线。

读取子分支时才拼出完整历史

当界面或 Agent 请求子分支历史时，SessionStore.readEvents() 不会只读子目录，而是执行三步：

  1. 递归读取父分支当前可见的历史。
  2. 只保留事件序号小于或等于分叉位置的父事件。
  3. 把这些继承事件与子分支自己的新事件合并，再按序号排序。
与源码一致的简化逻辑读取子分支：
  父历史 = 读取父分支()
  继承部分 = 父历史中序号 ≤ 分叉位置的事件
  自己部分 = 读取子分支自己的 events.jsonl
  可见历史 = 继承部分 + 自己部分

继承事件在返回前会把所属 Session 改成当前子 Session。这样后续回放器可以把继承事实当作子 Session 的历史来重建消息和状态，而不会误判为跨 Session 数据。

为什么父分支后来的事件不会进入子分支

子分支保存的不是“持续跟随父分支”，而是一个固定分叉位置。父分支以后即使新增事件 6、7，读取子分支时仍然只选择“小于或等于分叉位置 3”的父事件。

父分支继续运行以后父分支可见历史：1、2、3、4、5、6、7
子分支继承条件：父事件序号 ≤ 3
子分支可见历史：1、2、3、4′、5′

这叫“固定快照语义”：固定的是对话历史位置，不是磁盘文件快照。它保证子分支创建后不会被父分支未来的回答悄悄改变。

嵌套分支怎样工作

子分支还可以再次产生子分支。读取最下面的分支时，存储层会沿父关系逐层向上读取，然后在每一层应用自己的分叉位置。

三层分支根 Session：1、2、3、4
└─ 分支 A：继承到 2，再追加 3A、4A
   └─ 分支 B：继承 A 到 3A，再追加 4B

分支 B 最终看到：1、2、3A、4B

读取时会记录已经访问过的 Session。如果错误元数据让 A 指向 B、B 又指向 A，系统会报告循环引用，而不是无限递归。

Fork、Rewind 和 Switch 到底有什么区别

操作实际行为不会做什么
Fork从指定事件位置创建一个新 Session 分支不会删除或截断原 Session
Rewind同样创建新分支，但名称标记为“Rewind”，表达“回到这里重试”不会让原 Session 倒退
Switch加载目标 Session 的元数据、可见事件和运行状态不会移动或合并任何事件

从实现上看，Fork 和 Rewind 使用同一套增量分支机制，区别主要是用户意图和标题。Switch 也不是修改一个全局“当前分支指针”；每个分支本身就是独立 Session，切换只是让界面和 Core 加载另一个 Session。

Session 分支不是 Git 分支

最容易误解的地方

Session 分支只隔离对话和事件历史，不隔离 Workspace 文件。父分支和子分支仍然看到同一个本地项目目录。

问题Session 分支Git 分支
主要管理什么对话、工具事实和 Agent 状态项目文件版本
创建时是否复制历史文件不复制父事件，只保存引用和增量创建新的提交指针
切换后源码是否变化不会自动变化工作区通常切换到对应提交
能否合并当前没有自动合并对话分支可以 merge 或 rebase

例如，父 Session 在事件 3 修改了文件，之后又在事件 5 修改了同一文件。即使从事件 3 创建 Session 分支，磁盘上的文件仍然保持创建分支时的当前内容，不会自动回到事件 3。需要恢复代码时，应使用 ChangeSet、Checkpoint 或 Git，而不是只使用 Session Rewind。

创建分支时还要重建任务状态

事件历史不仅用于显示聊天，也用于建立当前任务账本。创建分支时，系统会用分叉位置之前的事件重新计算：

  • 最近一次用户目标；
  • 当前计划；
  • 已经发生的文件修改版本；
  • 测试或检查命令是否通过；
  • 尚未解决的重要错误。

计算结果写入子 Session 自己的 state.json。因此子分支既共享父历史，又拥有独立的后续任务状态。它不需要每次都从第一条事件重新计算全部账本。

分支元数据的四个字段

理解完整机制后，四个字段就只是对上述关系的简短记录：

字段通俗含义为什么需要
rootSessionId整棵分支树最早的根 Session识别所有分支的共同来源
parentSessionId当前分支直接来自哪个 Session读取时知道下一层应该找谁
forkedFromSeq继承父历史到第几个事件过滤父分支后续事件
compactionFloor允许分叉的最早事件位置防止绕过已经生效的上下文摘要

这些名称只存在于代码和磁盘元数据中。使用文档时只需记住：根来源、直接父分支、分叉位置、最早合法位置。

为什么不能回到任意早的位置

长 Session 会进行上下文压缩。压缩不会删除原始事件，但会生成一条摘要事件，用较短的模型消息替代更早的模型视图。最新摘要所在的事件位置就是压缩下界。

如果允许在摘要之前创建分支，新分支既没有包含摘要，又可能缺少压缩前完整且合法的工具消息组合，模型上下文可能变得不一致。因此系统只允许在“压缩下界到当前分支头”之间选择分叉位置。

这里需要区分两个事实：

  • 早期原始事件仍在磁盘上，可以用于审计。
  • 新的模型工作分支必须从合法摘要位置之后开始。

分支为什么不能随便删除父节点

子分支没有复制父事件。如果先删除父 Session，子分支读取时就找不到继承历史。因此当前删除规则是：

  • 运行中的 Session 不能删除，必须先结束或取消 Turn。
  • 仍有直接子分支的 Session 不能删除。
  • 需要删除整棵树时，应从最末端的子分支开始向上删除。

这是增量存储节省空间所带来的必要约束。未来如果要支持任意删除，就必须先把子分支重新挂接到其他父节点，或者把缺少的父事件物化到子分支。

事件与 Item 为什么同时存在

Event 描述“发生了什么”，Item 保存“恢复时需要的业务内容”。例如：

场景Event 的作用Item 的作用
模型输出文字message.delta 让界面实时追加文字流结束后保存完整 Assistant 消息
工具完成通知界面工具已经结束保存下一轮模型需要看到的 Tool Result
上下文压缩记录压缩前后 token 数保存恢复后使用的压缩消息视图

流式文字片段不会每个都写入 JSONL，否则一个长回答可能造成数千次磁盘追加。流结束后只持久化完整消息。实时展示和长期恢复因此使用同一事件协议，但保存粒度不同。

应用重启后怎样恢复 Session

  1. 读取 meta.json，确认 Session 属于当前 Workspace。
  2. 读取 state.json，恢复当前任务账本。
  3. 按分支关系计算完整可见事件。
  4. 按事件顺序重建用户消息、Assistant Tool Calls 和 Tool Result。
  5. 恢复 ChangeSet、Checkpoint、检索索引和压缩后的模型视图。
  6. 如果发现应用退出前没有终态的 Turn，将它标记为 interrupted，不重启后台动作。

回放器只做“历史事实 → 内存状态”的转换。它不调用模型、不运行命令、不写项目文件。这样才能保证打开旧 Session 不会产生新的副作用。

常见问题

Fork 后父分支新增回答，子分支会同步吗？

不会。子分支只继承到创建时记录的固定事件位置。

Rewind 会把文件恢复到旧版本吗？

不会。Rewind 只创建对话历史分支。文件恢复使用 ChangeSet、Checkpoint 或 Git。

Switch 会修改分支关系吗？

不会。Switch 只加载目标 Session，让后续 Turn 在那条可见历史上继续。

为什么不直接复制父事件？

增量方式更省空间，也不会在父历史很长时产生大量重复文件。代价是父节点不能在仍有子分支时删除。

分支之间是否有独立项目目录？

没有。当前所有属于同一 Workspace 的 Session 都操作同一目录。若需要代码环境隔离，应结合 Git Worktree 等机制，当前 Session 分支没有自动提供这种隔离。

对应源码从哪里看

protocol/src/index.ts定义 Session 和分支关系字段。
runtime/session-lifecycle.ts创建分支、重建任务账本、切换和恢复 Session。
storage/src/index.ts读取父事件、过滤分叉位置、拼接当前分支增量。
runtime/change-manager.ts真正负责文件修改的撤销和 Checkpoint 恢复。

分支机制

子分支在磁盘上只保存“父 Session、分叉位置和自己的新增事件”；读取时再把父历史截止部分与自身增量拼起来。它分叉的是 Agent 历史，不是 Git，也不是 Workspace 文件。
