第三部分 · 保证正确运行

测试、评估与可观测性

Agent 输出具有不确定性，只看一次演示成功不能证明系统可靠。SeeCoder 把协议、状态和工具做成确定性测试，再用真实 Prompt 评估端到端任务成功率。

测试对象不是只有最终回答

一次任务可能最终给出正确文字，但中间重复执行副作用、越出工作区或错误标记测试状态，仍然是不合格。测试需要同时检查消息协议、状态转换、Tool Call 数量、文件结果、验证 revision、取消效果和最终终态。

层次主要验证为什么需要

Fake Provider 为什么重要

真实模型响应会变化，也需要网络和费用，不能用于精确断言状态机。Fake Provider 按脚本返回文本、Tool Call、错误和 usage，可稳定复现“读取 → 修改 → 测试失败 → 修复 → 完成”。摘要请求通过 purpose 区分，不会消耗主 Agent 预设响应序列。

Fake 测试证明 Harness 按协议运行，真实 Eval 证明模型能在这个 Harness 中完成自然任务。两者互补，不能互相替代。

上下文方案怎样量化

长任务记录 beforeTokens、afterTokens、availableInput、summarySource、retrievedEntries 和 droppedEvidence。确定性验收包括：压缩后低于 availableInput 的 60%；工具协议组完整率 100%；摘要失败不增加 Turn 失败；相同文件重复正文注入减少至少 50%；固定夹具峰值输入 token 相比旧方案下降至少 25%。

真实 Eval 还记录重复读取、无效工具调用、修改文件范围、测试失败后的恢复、最终验证 revision 和完成状态。成功率不能只按“模型说完成”计算，而要按工作区最终状态和验证证据计算。

每个事件携带 sessionId、可选 turnId、timestamp 和 seq，工具事件继续携带 callId。开发日志记录类别、耗时和错误码；普通聊天只呈现用户做决定所需的信息。Trace 面板将主 Agent 与子 Agent 的阶段、token、耗时和结果组织在一起，因此能够回答“点击发送后后台发生了什么”。

性能重点看哪里

首屏主要受 Renderer 资源影响；发送到首个增量受 ContextBuilder 和模型网络影响；长会话受模型输入规模和 UI 消息数量影响；命令任务还要关注孤儿进程。上下文预算和 Observation 压缩解决网络与模型输入增长，工具卡默认折叠减少渲染噪音，AbortSignal 与进程树终止处理后台资源。

当前没有数据库、WebSocket、Redis 或 Queue，所以不应编造这些监控项。Electron Main 内部事件流通过 IPC 到 Renderer；模型流使用 SSE；本地命令使用子进程流。

怎样讲清楚

“我把模型不确定性与 Harness 确定性分开测试。Fake Provider 精确验证协议、状态和失败路径；真实 Prompt Eval 评估自然任务成功率。最终结论来自文件结果、工具轨迹和当前 revision 的验证，而不是模型自述。”
