第四部分 · 进入源码与答辩

源码阅读与答辩路线

最后一章把前面的概念映射到真实源码，并给出一条可以在答辩中自然讲完的主线。不要按目录逐个介绍文件，而要围绕“一次任务怎样可靠完成”展开。

推荐的源码阅读顺序

先读 Protocol，因为它定义系统共同语言。然后从 Agent Core 的 startTurn 进入 runTurn，顺着一次迭代看到 ContextBuilder、ModelProvider 和 executeCall。理解控制流后再分别深入 context、model、tools 和 storage。Main 负责把这些能力接到 Electron，Renderer 最后阅读。

packages/protocol/src/index.tsSession、Turn、Item、Event、ModelMessage、ToolCall、ToolResult。
packages/agent-core/src/index.tsstartTurn、runTurn、工具调度、审批、子 Agent、终止与错误归一化。
packages/agent-core/src/context.tsLedger、Evidence、Observation、MemoryIndex、摘要与预算分配。
packages/model/src/index.tsfetch、SSE、Tool Call 聚合、usage、finishReason 与重试。
packages/tools/src/index.ts工具定义、WorkspacePolicy、原子写入、补丁、命令和 Git。
packages/storage/src/index.tsJSONL、状态原子写入、Snapshot、Checkpoint 与回放。
apps/desktop/src/main/main.ts可信后端、IPC、工作区、设置、安全存储和事件转发。

用一条主线讲完整项目

第一步，定义问题。普通聊天模型不能读取本地项目，也不能保证自己声称的修改真实发生。SeeCoder 的目标是让模型在安全、可恢复、可审计的 Harness 中完成真实编程任务。

第二步，解释架构。React Renderer 是最小权限前端，Electron Main 是本地可信后端。Agent Core 维护循环，ModelProvider 负责 SSE，Tools 负责本地执行，Storage 保存事件和快照。核心逻辑全部自研。

第三步，走一遍循环。用户消息启动 Turn；ContextBuilder 生成受预算约束的上下文；模型返回文字或 Tool Call；Core 依次经过 Schema、路径、模式、风险和审批；Tool Result 反馈模型；循环直到完成、取消、失败或上限。

第四步，说明长任务。Session 保存完整历史，模型只接收分层视图。ContextLedger 保存权威事实，FileEvidence 避免重复代码，Observation 压缩长日志，轻量检索召回相关历史，语义摘要失败时可以确定性回退。

第五步，给出正确性证据。文件修改产生 revision、Snapshot 和 ChangeSet；测试记录绑定 revision；JSONL 保存轨迹；Fake Provider、集成测试和真实 Prompt Eval 分别验证 Harness 与模型表现。

高频问题的简洁回答

为什么不用 Agent SDK？

考核要求核心逻辑自行实现；同时自研能完整控制消息协议、上下文、安全、终止和错误恢复，答辩可以落到代码。代价是需要自行维护供应商兼容与工具 Schema。

为什么不是传统前后端？

它仍有前后端，只是后端是 Electron Main。本地代码和命令无需绕远程服务器，API Key 也不进入 Renderer。

上下文压缩会不会丢历史？

不会删除 JSONL。压缩只重建下一轮 ModelRequest；Ledger 的权威事实、工具协议组和当前证据优先保留。

模型为什么不能绕过权限？

模型只能生成 Tool Call。真正执行由 Core 的代码策略决定，Plan 副作用和工作区外路径会被硬拒绝。

怎样判断任务真的完成？

Core 根据无工具最终文本或 finish 进入完成，同时检查当前 revision 的验证。测试过期会明确警告，模型自述不作为验证证据。

是否支持沙箱？

当前是应用层策略隔离，不是 OS 沙箱。路径、审批、敏感文件和回滚已经实现；进程仍使用当前用户权限。

设计取舍要诚实说明

当前选择获得的好处接受的限制
模块化单体本地运行简单、模块可独立测试超大规模任务不适合单进程
JSONL + JSON追加审计、无需数据库、易恢复复杂跨 Session 查询能力有限

无原生 PTY跨环境简单、无需原生依赖不支持交互式 TUI

演示时应展示什么

选择独立演示工作区，输入一个需要搜索、修改和测试的真实任务。先展示 Explore 的只读证据，再展示计划和审批；修改后打开 Changes；运行测试并让第一次失败触发修复；最后使用 Review 检查 Diff，展示当前 revision 验证和 Trace。演示重点是“证据怎样推动下一步”，不是工具卡数量。

完成学习后的自检

如果你能不看文档回答下面五个问题，就已经掌握项目主干：为什么模型不能直接执行工具；Session 和 Model Context 有什么区别；Tool Call 为什么要与 Tool Result 成组保存；测试为何要绑定 revision；取消怎样从按钮到达 fetch 和子进程。

继续深入

本教程用于建立清晰主线。需要查看完整需求、测试矩阵、安全威胁和质量门禁时，继续阅读项目根目录的 docs/。当网站描述与源码冲突时，以已经测试的源码为准，并应及时修正文档。

一分钟总结

“SeeCoder 用 Electron Main 建立本地可信边界，用自研 Agent Core 维护模型—工具循环。Session 与 JSONL 保存完整历史，混合 ContextBuilder 控制模型视图，Tool Runtime 通过路径、模式和审批执行副作用，Snapshot 与 revision 保证恢复和验证。它不是现成 Agent 的封装，也不把模型输出等同于事实。”
