第一部分 · 先看全局

SeeCoder 是怎样的系统

先记住一件事：模型只负责判断下一步，SeeCoder 程序负责保存事实、执行工具、限制风险并决定任务何时结束。

模型为什么不能单独完成编程任务

大语言模型接收文字并生成文字。即使它能输出“请读取这个文件”或“把这段补丁写进去”，它本身也没有你电脑上的文件权限。模型说“已经修复”，不代表磁盘真的发生变化；模型说“测试通过”，也不代表命令真的执行过。

编程 Agent 要在模型外面补齐一个真实执行闭环：先收集用户目标和项目事实，再请模型选择下一步；如果模型请求工具，程序就校验并执行；执行结果重新交给模型；直到任务完成、失败、取消或达到限制。SeeCoder 的核心价值就在这个闭环，而不是一段很长的提示词。

最小 Agent 闭环用户目标
  → 构建本轮上下文
  → 调用模型
  → 执行工具并取得真实结果
  → 把结果交回模型
  → 继续或结束

从界面到磁盘的完整分层

SeeCoder 是一个本地 Electron 桌面应用。界面运行在 Renderer 进程中，只负责接收输入和展示状态；Preload 暴露少量类型明确的 IPC 方法；Electron Main 是可信的本地后端，持有工作区、模型配置和 AgentCore。Renderer 没有 Node.js 权限，因此网页内容不能直接读取文件或启动命令。

层次主要职责不负责什么
Renderer任务输入、消息展示、工具活动、审批、Diff、设置不直接接触文件系统和进程
Preload把明确的界面请求转换成类型化 IPC不实现 Agent 逻辑
Electron Main校验 IPC 参数，管理本机配置并调用 AgentCore不决定每轮模型策略
AgentCore对外门面、依赖装配、事件持久化和广播不再承载整个循环和工具细节
运行组件管理 Session、Turn、上下文、工具调用和修改恢复不直接操作界面
Tools 与 Storage执行受限本地动作，保存可恢复事实不相信未经校验的模型输出

六个核心部分分别解决什么问题

1. AgentCore：统一入口

桌面后端不需要知道内部有多少运行组件，只调用 AgentCore 的公共方法。例如开始任务、取消任务、处理审批、创建分支或恢复修改。AgentCore 在构造时创建所需依赖，再把具体工作转发出去。它像一个清晰的服务入口，但不是执行所有事情的“大类”。

2. TurnRunner：让一次请求持续推进

一次用户请求可能要经历多轮“模型—工具—模型”。TurnRunner 保存本次运行状态，构建上下文，消费模型流，执行一批工具，并检查完成、失败、取消和迭代上限。这里的 Turn 可以理解为“一次从用户发送到系统给出终态的任务运行”。

3. ToolCallExecutor：把模型请求变成受控动作

模型返回的工具名和参数只是一个请求。ToolCallExecutor 先检查调用是否重复，再校验参数、模式和审批；随后设置超时与取消，调用真实工具，最后把成功或失败统一成 ToolResult。只有一批工具都标记为可并行时才并行，否则整批按顺序执行。

4. Context：决定模型本轮看到什么

完整历史会越来越长，而模型输入窗口有限。上下文模块保留当前目标、代码证据、修改版本、验证结果和关键错误；旧的冗长过程先用确定性规则压缩，仍然过长时才请求模型摘要。完整历史没有被删除，它仍保存在 Session 中。

5. SessionStore：保存可以恢复的事实

用户消息、模型回复、工具结果、状态变化和文件修改都会成为事件。事件按顺序追加，应用重启后只回放事实，不重新执行历史工具。分支只保存父分支位置和自己的新增事件，因此不必复制整段历史。

6. Tools：在工作区边界内接触真实世界

文件读取、文本搜索、写文件、应用补丁、运行命令和 Git 操作都在这里。路径必须位于当前工作区，写入前可创建恢复点，敏感文件有单独限制。对同一文件的写入会排队，写入目标不明确的命令会锁住整个工作区。

先认识四个基础名词

Session

长期任务容器。它保存完整事件、状态和分支关系，关闭应用后仍可恢复。

Turn

用户在 Session 中发出的一次请求，从排队开始，到完成、失败、取消或达到限制结束。

Iteration

Turn 内的一次循环：准备上下文、调用模型、执行本轮工具、判断是否继续。

Tool

模型能够请求的本地能力。工具必须有名称、参数规则、风险属性和结构化结果。

三层关系是：一个 Session 可以包含多个 Turn；一个 Turn 可以包含多个 iteration；一个 iteration 可以产生零个、一个或多个 Tool Call。把这三个层次分开后，状态和日志才不会混在一起。

一次修改任务如何流动

  1. 用户选择项目目录，输入“修复空标题提交并运行测试”。
  2. 界面通过 Preload 把请求交给 Main，Main 调用 AgentCore。
  3. SessionLifecycle 确认 Session 可用，TurnRunner 建立新的 Turn。
  4. 上下文模块从历史、任务账本和代码证据中组装模型输入。
  5. 模型先请求搜索和读文件；只读工具满足并行条件时可以并行。
  6. 模型提出补丁；执行器经过路径、模式、审批和写入协调后修改文件。
  7. ChangeManager 记录变更版本和恢复信息，事件立即写入 SessionStore。
  8. 模型请求运行测试；命令退出码和输出成为新的工具结果。
  9. 测试失败就继续下一次 iteration；通过后模型可以调用 finish 结束。
  10. TurnRunner 写入唯一终态，释放控制器、审批等待和写入锁，界面停止运行状态。

这条链路中，模型没有直接写文件，界面也没有直接执行命令。每层只做自己拥有权限和上下文的事情。

当前系统为什么不只是 Demo

简单 Demo 通常只有“发送消息—收到回复”，最多再加一个不受控的工具循环。SeeCoder 已经具备持久化 Session、Turn 状态机、混合上下文、流式工具协议、审批、动态干预、可回滚修改、增量分支、写入并发控制、取消传播和自动化测试。这些能力共同解决长任务中的状态、风险和恢复问题。

它仍然有明确边界：当前是单机桌面应用，不是远程调度平台；写入协调器只在当前进程内生效；命令工具无法提前知道所有副作用，所以采用工作区级串行保护；自然文本仍可结束 Turn，因此“完成”还需要结合验证记录判断。明确边界比把系统描述成万能 Agent 更重要。

阅读后续章节的顺序

第 2 章用一个真实任务串起完整调用链；第 3 章解释模块边界；第 4 至 9 章分别深入 Session、上下文、主循环、动态干预、工具和模型协议；第 10、11 章说明终止恢复与测试；最后一章给出源码阅读路线。初次阅读不必记住类名，先回答三个问题：事实保存在哪里、谁决定下一步、谁真正执行动作。

模型、程序和用户各自决定什么

模型负责根据当前证据提出下一步，例如搜索哪个符号、读取哪个文件、应用怎样的补丁。程序负责判断这个请求是否符合协议、是否越过工作区、是否需要审批、是否可以并行以及是否已经执行过。用户负责给出目标、选择工作区、批准高风险动作，并可随时调整方向或取消。

这三个角色不能互换。程序不能凭空猜测用户想修什么；模型不能绕过本地权限；界面上的“停止”也不能只隐藏加载动画，必须真正中断后台模型请求、工具进程和审批等待。SeeCoder 的设计把决定权放在拥有事实的一层。

为什么所有动作都要形成结构化结果

如果工具只返回一段自由文本，上层很难区分成功、失败、取消和超时。SeeCoder 的 ToolResult 至少表达是否成功、结果代码、给用户或模型看的内容、持续时间和必要元数据。文件工具还会关联变更记录，命令工具会保留退出码及截断后的输出。

结构化结果有三个用途：TurnRunner 能可靠决定是否继续；模型能根据错误码修正参数；界面和测试能显示并断言同一个事实。它也避免通过“输出里有没有 success”这类脆弱字符串判断状态。

事件是系统共同的事实来源

任务开始、模型文字到达、工具启动、审批请求、工具完成、文件修改和 Turn 结束都会生成事件。事件先写入当前 Session 的追加日志，再广播给界面。应用异常退出后，恢复过程按顺序回放事件，重建消息和状态，而不是重新发送模型请求或再次执行工具。

因此事件不是调试时才看的日志，而是系统状态的一部分。日志可以记录更细的耗时和故障定位信息；事件只保留业务上已经发生、需要恢复和展示的事实。两者都不能保存 API Key，也不能保存模型私有思维。

系统如何控制本地风险

风险控制位置处理方式
页面直接访问电脑Electron 边界Renderer 关闭 Node 权限，只能调用 Preload 白名单
模型给出非法参数工具执行器先解析 JSON，再用工具 Schema 校验
路径越出项目WorkspacePolicy解析绝对路径和符号链接后检查工作区边界
高风险动作未经同意执行模式与审批Guided 模式暂停并等待用户明确选择
并发写入覆盖写入协调器同文件排队，未知范围命令锁整个工作区
修改后无法恢复ChangeManager记录哈希、恢复点和变更版本，冲突时停止覆盖
任务无限运行TurnRunner取消信号、无进展判断和 iteration 上限

“完成”为什么不只看最后一句话

模型可以在没有实际修改文件时说“完成了”，所以 SeeCoder 把回复、工具结果、文件变更和验证记录分开。ChangeManager 递增代码版本，测试记录绑定执行时的版本。若当前版本已有修改但没有对应的成功验证，finish 仍可结束任务，但会带出验证警告，用户能够看到证据不足。

自然文本没有工具请求时也允许结束，这保证解释类任务和兼容模型可以正常使用。代价是完成质量不能只靠状态字段判断。可靠交付要同时看最终摘要、实际 ChangeSet、测试命令和当前版本的 ValidationRecord。

SeeCoder 当前适合解决什么任务

它适合在一个本地工作区内完成代码阅读、定位问题、小到中等范围修改、运行验证、查看差异和恢复变更。长任务可以借助 Session、上下文压缩和分支继续。用户可以在运行中 Steering 改变方向，也可以用 Follow-up 安排当前任务完成后的下一项工作。

它暂不把多个电脑、远程沙箱或组织级权限纳入统一调度，也不承诺任意命令都能完全回滚。命令可能产生工具无法枚举的副作用，因此仍需要执行模式、审批和工作区级锁。理解这些边界，可以正确判断它是一个具备工程闭环的本地 Code Agent，而不是演示聊天框，也不是分布式 Agent 平台。

如果只想判断系统是否健康，可以沿着最短证据链检查：用户消息是否进入 Session，Turn 是否只有一个活动实例，模型工具请求是否与结果配对，文件变化是否产生 ChangeSet，验证是否属于当前代码版本，最终是否只写入一个终态。后续所有复杂功能都建立在这条证据链之上。

学习时也按这条链路逐层深入：先看一次任务怎样流动，再分别理解历史、上下文、循环和工具。这样遇到类名时能先知道它解决的问题，不需要先记住全部字段。
