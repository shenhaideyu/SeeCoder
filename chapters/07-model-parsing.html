第二部分 · 理解核心

动态干预与生命周期

任务运行后，用户仍然可以改变方向；扩展代码也可以在关键步骤前后检查或改写数据。

Steering 和 Follow-up 有什么区别

类型什么时候生效适合什么内容
Steering下一次模型调用边界优先注入“停止改后端，只修前端”这类方向调整
Follow-up当前工作完成后按顺序进入上下文“完成后再补一个测试”这类追加任务

InterventionQueue 解决什么问题

用户消息可能在模型输出或工具执行期间到达。直接修改正在使用的消息数组会造成协议断裂。InterventionQueue 先按 Turn 保存消息，再由 TurnRunner 在安全边界消费。每条干预都有 pending、consumed 或 discarded 状态，并写入事件。

拦截器可以做什么

AgentInterceptorPipeline 是进程内扩展点。拦截器可以观察关键阶段，也可以返回三种结果：继续、阻止或替换。当前阶段包括用户输入、Turn 启动前、模型请求前、文字分片、工具调用前和工具结果后。

概念接口intercept(context) →
  continue
  block(reason)
  replace(newValue)

拦截器异常不会破坏整个事件链，而会转成可控错误。系统也不会把模型私有思维写入事件或交给扩展。

Hook 与拦截器的区别

Hook 来自受信任的本地配置，可以在工具执行前、文件修改后和 Turn 结束时运行命令。拦截器是 Agent Core 内的程序扩展点，可以改写模型请求或工具数据。二者都必须经过超时、取消和结果归一化。

事件为什么重要

事件同时服务三件事：SessionStore 用它恢复状态；Renderer 用它更新界面；日志和测试用它证明执行顺序。事件是公开事实，不包含模型内部推理。

为什么不能立即把新消息塞进当前请求

模型请求发出后，服务端正在按原消息序列生成内容；工具执行时，当前 assistant 消息与 Tool Result 也必须保持协议配对。此时直接改写消息数组，既不会改变已经发送的网络请求，还可能让后续历史出现“没有请求的工具结果”或“结果插到错误工具后面”。

SeeCoder 把用户干预先保存为独立记录。TurnRunner 只在确定的消息边界读取队列：下一次调用模型之前消费 Steering；当前 Turn 完成后消费 Follow-up，并用合并后的追加文本启动一个新 Turn。这样用户能及时改变方向，同时不破坏正在执行的步骤。

Steering 的完整流程

  1. 用户在 Turn 运行中输入方向调整，并选择立即干预。
  2. Main 把内容交给 AgentCore，队列创建状态为 pending 的记录。
  3. 当前模型流或工具执行继续到安全边界，不会被静默篡改。
  4. TurnRunner 在下一次模型请求前取出尚未消费的 Steering。
  5. 内容作为清晰的用户方向说明加入本次工作视图，记录变为 consumed。
  6. 队列状态和注入事实写入事件，界面可以说明调整何时生效。

例如 Agent 正在修后端，用户补充“不要修改接口，只修前端展示”。若当前正在读取文件，读取可以完成；下一次模型决策会看到新约束。若当前补丁已经进入执行器，Steering 不会伪装成从未修改过，后续模型必须根据真实 ChangeSet 处理已有变化。

Follow-up 为什么会启动新的 Turn

Follow-up 表示“当前事情结束后再做另一件事”，例如“修完后再补一条文档说明”。如果立即注入当前上下文，模型可能在尚未验证主任务时扩大范围，也会让一个 Turn 的目标和终态变得含糊。

TurnRunner 先让当前 Turn 到达完成、失败、取消或限制终态。只有正常收尾并存在待处理 Follow-up 时，才取出同一 Session 中的消息，按到达顺序合并为下一次用户请求，再调用 start() 建立新 Turn。两个 Turn 各有独立编号、取消信号、迭代预算和终态，但共享 Session 历史。

队列记录为什么有三个状态

状态含义何时出现
pending消息已保存，尚未到生效边界用户提交干预后
consumedTurnRunner 已把内容加入正确的模型输入或新 Turn安全边界消费后
discarded消息不会再执行，但保留发生记录Session 删除、明确清除或取消清理时

状态使重启和测试能够回答“这条消息到底生效了吗”。若只把干预保存在内存数组，应用异常退出后会丢失；若消费后直接删除，又无法解释模型为什么改变方向。事件记录保留业务事实，但不保存模型私有思维。

拦截器的六个明确阶段

阶段看到什么常见用途
userInput用户输入进入 Session 前的数据清理格式、拒绝空请求、附加本地规则
beforeTurn即将开始的 Turn检查任务策略或补充运行配置
beforeModelCall已构建的模型请求追加允许公开的约束，或阻止非法请求
messageDelta模型产生的公开文字分片过滤不应展示的格式、记录可见输出
beforeToolCall工具名和解析后的参数阻止特定动作或替换受控参数
afterToolCall结构化 ToolResult补充诊断、审计结果或统一错误表达

拦截器返回 continue 表示保持原值，block 表示停止该阶段并给出原因，replace 表示用新值继续。替换必须仍通过后续 Schema、权限和工作区检查，不能借扩展点绕过工具门禁。拦截器异常会转成可控错误，而不是让订阅链静默断开。

Hook 与拦截器为什么不能混成一种机制

拦截器运行在 Agent Core 进程内，处理结构化数据，可以改写模型请求或工具数据。Hook 来自受信任的本地配置，通常在工具执行前、文件修改后或 Turn 结束时运行命令，用于格式化、检查或通知。Hook 接触真实进程，因此要经过命令策略、超时和取消。

二者的失败语义也不同。拦截器 block 是明确的程序决策；Hook 非零退出是外部命令结果。工具前 Hook 失败可以阻止副作用，工具后 Hook 失败应作为结果的一部分返回，Turn 结束 Hook 不能把已经持久化的完成事实改写成未发生。当前生命周期中的 Turn 结束使用 Hook，不存在同名的 Turn-end 拦截器。

动态干预如何与取消配合

取消比 Steering 优先。用户点击停止后，同一个 AbortSignal 中断模型 fetch、退避等待、工具命令和子任务；等待审批或用户输入的 Promise 也会被解除。TurnRunner 在边界检查 signal，并以取消状态作为唯一终态。尚未消费的干预按清理规则标记，不能在取消后突然启动新动作。

Steering 也不是强制中断工具的快捷方式。若用户要立即阻止正在运行的命令，应使用取消；若希望当前安全步骤结束后改变策略，使用 Steering；若只是追加后续任务，使用 Follow-up。三个操作的语义分开，界面才能给出准确反馈。

事件、日志与扩展的边界

AgentEvent 是可恢复、可展示的业务事实，例如干预已入队、工具已完成和 Turn 已取消。日志用于开发诊断，可以增加耗时、阶段和稳定错误码，但仍不能记录密钥或完整敏感文件。拦截器和 Hook 是执行扩展点，不是新的事实存储。

扩展若要影响结果，必须通过返回值进入原管线，再由核心发布事件。它不能直接修改 Session JSONL，也不能直接操作 Renderer 状态。这样重启回放仍然只依赖一个事件来源，测试也可以断言扩展前后发生了什么。

多个干预按什么顺序处理

同一 Turn 中的干预按到达顺序保存。下一次模型边界会消费当时仍为 pending 的 Steering，并把它们作为一段清晰的用户更新加入，而不是生成多组破碎消息。Follow-up 继续留在队列，等待当前 Turn 到达终态。新到达的 Steering 不会越过早先已经排队的方向说明。

如果两条 Steering 表达冲突，模型看到的是按时间排列的更新，较新的明确要求通常覆盖较早方向；程序不会偷偷删除旧记录。若冲突涉及高风险权限，工具模式与审批仍是最终边界，文字干预不能提高权限。

替换结果仍然要经过后续门禁

例如 beforeToolCall 把相对路径替换成另一个路径，新的参数仍要经过工具 Schema、WorkspacePolicy、敏感文件检查和审批。beforeModelCall 替换模型消息后，工具消息配对和 token 预算仍需有效。拦截器是受控扩展，不是绕过核心规则的后门。

多个拦截器按注册顺序运行，前一个替换后的值成为后一个输入；任一拦截器 block 就停止该阶段。测试应固定注册顺序，分别覆盖继续、替换、阻止和抛错，避免扩展组合产生无法解释的结果。

界面怎样让用户知道干预已生效

用户提交后，界面先显示“已排队”，不能立即宣称模型已经看到。队列记录被消费并产生事件后，状态更新为“已应用”；Follow-up 创建新 Turn 时，界面展示新的运行边界。取消或清除后则显示未执行，避免用户误以为要求已经包含在结果中。

这类反馈不需要展示内部标识，只要说明内容类型、当前状态和生效位置。内部标识仍保留在事件中，供恢复与测试准确配对。

动态干预的可靠性最终由三件事保证：消息先持久化、只在安全边界消费、每次状态变化都有事件。缺少任何一项，都可能造成要求丢失、重复执行或界面误报。

测试时要覆盖模型流中、工具执行中、等待审批时和自然结束前四个到达时机，确认 Steering 不拆协议组，Follow-up 只在成功收尾后启动新的独立 Turn。

Assistant Tool Calls 与 Tool Result 配对

OpenAI 兼容协议要求 Assistant 消息中的每个 Tool Call 都有唯一 id，后续 tool 消息使用 tool_call_id 引用它。若工具结果没有来源，或一个多工具组只保留部分结果，下次请求可能返回 HTTP 400。SeeCoder 曾经出现 missing tool_call_id 类问题，因此当前设计把协议配对作为硬不变量。

Core 的 sanitizeModelMessages 负责按协议组裁剪上下文，Provider 在真正发送 HTTP 请求前再做一次线性规范化。规范化只保留“一个 Assistant Tool Call 组及其全部匹配 Tool Result”，丢弃孤立 Tool Result、不完整工具组和重复结果，并按 Assistant 声明的调用顺序排列结果。这道发送前门禁不能替代 Core 的正确性，但能阻止恢复数据、第三方兼容消息或历史裁剪错误直接形成无效请求。

DeepSeek 的思考模式会在工具调用轮次产生 reasoning_content，后续请求要求回传该字段。SeeCoder 的安全规则禁止持久化和展示模型私有思维链，因此不能把该字段写入 Session 历史。对 DeepSeek 官方 Chat Completions 地址，Provider 在工具任务中显式关闭思考模式，只使用公开文本与 Tool Calls；这样既满足接口协议，也保持“私有思维链不入轨迹”的产品边界。其他 OpenAI 兼容服务不接收这一供应商专用字段。

正确结构如下：

~~~text assistant: content: "" toolCalls: - id: call-A name: read_file arguments: {"path":"a.ts"} - id: call-B name: read_file arguments: {"path":"b.ts"}

tool: toolCallId: call-A content: 读取 a.ts 的 Observation

tool: toolCallId: call-B content: 读取 b.ts 的 Observation ~~~

Core 先保存 Assistant，再执行 call-A 和 call-B，结果分别保存。messageGroups 扫描历史时，遇到带 Tool Calls 的 Assistant 就收集后续 tool 消息，只有所有 callId 都出现才保留该组。孤立 tool 被跳过。sanitizeModelMessages 在恢复、压缩前后都会运行。

同一模型响应中的工具先由批调度器判断安全性。只有整组工具都显式声明 parallelSafe=true 时才并行执行；只要包含写文件、命令、审批、用户输入或其他非并行安全工具，整组就保持串行。并行结果仍按模型原始 Tool Call 顺序写回上下文，ChangeSet 与 revision 的主写链始终只有一个写者。

动态干预队列

运行中的用户消息分为两种语义。steering 修改当前 Turn 的执行方向，在模型调用前、工具批次结束后和自然完成判定前的安全点消费；followUp 不污染当前 Turn，在当前 Turn 到达终态后自动创建后续 Turn。队列条目具有唯一 id、创建时间和 pending/consumed/discarded 状态。取消 Turn 会丢弃尚未消费的 steering；follow-up 只有在正常完成后才自动启动，失败或取消时不会静默执行。

可干预生命周期

Agent Core 将只读事件观察与可改变控制流的 Interceptor 分离。Interceptor 支持 userInput、beforeTurn、beforeModelCall、messageDelta、beforeToolCall 和 afterToolCall。每个阶段只能返回 continue、replace 或 block；异常和超时被转换为受控 block，不允许越过 TurnRunner。beforeModelCall 只修改本次请求的临时消息视图，除非后续产生正式 Item，否则不得直接改写 Session 权威历史。

工具执行边界

ToolCallExecutor 是工具异常边界。参数错误、未知工具、审批拒绝、Hook 阻止、Interceptor 阻止、普通异常、超时和取消都转换为结构化 ToolResult，并走相同的 tool.completed 与 callId 幂等收尾流程。普通工具异常不得直接击穿 TurnRunner；只有 Agent Core 自身不变量损坏才允许 Turn 级失败。

取消传播与资源清理

cancelTurn 首先 abort 本轮 controller，然后遍历 children 中属于该 Turn 的子 Agent 并 abort。等待审批的 Promise 以“用户取消了任务”解决，等待 ask_user 的 Promise 也被解决。这样取消不会因为一个永远没人点击的 Promise 卡住。

模型 Provider 的 fetch 使用同一 signal；重试 sleep 注册 abort；工具 ToolContext 携带 signal；commandRunner 在取消时终止进程树；summaryController 监听父 signal；子 Agent controller 也监听父 signal。取消是一条传播链，而不是一个 UI 标志。

TurnRunner.run() 在流结束后、每个 Tool Result 后再次检查 signal，防止取消与网络分片同时到达时继续执行下一个工具。catch 将 signal.aborted 优先映射为 cancelled，而不是把 AbortError 显示成 failed。

finally 删除 controllers、turnModes、turnSkills、turnLanguages、executedCalls，并解决属于本 Turn 的遗留审批。activeSessionTurns 在完成、失败与 finally 都进行幂等删除，保证异常路径也不会让 Session 永久处于运行中。

cancelAll 用于切换 Workspace 或关闭窗口。它中止所有主 Turn 和子 Agent，拒绝所有审批与输入。这样旧 Workspace 不会在用户切到新项目后继续写文件。

Skill、AGENTS.md 与 Hook 的区别

AGENTS.md 是 Workspace 根目录的长期项目规则，systemPrompt 每轮读取根文件并限制到 20000 字符。当前实现不会按子目录自动发现嵌套 AGENTS.md，因此只能声称“加载根规则”。规则被标记为低于系统安全规则，文件内容被视为不可信数据。

Skill 是用户导入并在本轮激活的 SKILL.md。它提供特定领域知识或操作流程，最多注入 20000 字符。Skill 影响模型决策，但不能新增工具，也不能绕过 ExecutionMode、WorkspacePolicy 或审批。

Hook 是确定性生命周期命令。preToolUse 在工具前运行，可阻止操作；postFileEdit 在文件修改后运行；turnEnd 在终态发布前运行。Hook 配置用 Zod 校验版本、id、命令、数量和超时。项目 Hook 首次启用需要由 Main 确认配置哈希。

三者解决不同问题：AGENTS.md 告诉模型项目长期约定；Skill 告诉模型本次如何完成某类任务；Hook 在确定时机执行程序。必须保证的规则应放在 Core、Policy 或 Hook，而不能只写在 Skill。

可观测性

一次任务至少可关联 sessionId、turnId、Tool Call ID、事件 timestamp、duration、status 和 error code。model.requested 到 model.completed 给出模型耗时、usage、重试和 finish reason；tool.requested 到 tool.completed 给出工具耗时与结果；tool.output 提供实时 stdout/stderr；context.compacted 记录 beforeTokens、afterTokens、availableInput、summarySource、retrievedEntries 与 droppedEvidence。

事件用于 UI 状态和 Session 恢复，MainLogger 用于开发诊断。日志只记录事件类型、标识、耗时与错误码，不记录 API Key 和完整文件正文。普通用户默认看到“读取了几个文件、修改了几个文件、测试是否通过”，需要时在 Terminal 或工具 Details 展开必要信息；原始事件不提供独立查看页面。

可观测性不是把所有数据打印出来。模型请求正文可能包含源码和用户隐私，工具输出可能包含凭据。SeeCoder 优先记录可关联元数据，并对正文执行敏感路径限制与长度控制。

为什么采用事件流而不是让 Renderer读取 Core

Renderer 如果直接读取 Core 内部 Map，就必须理解所有状态转移，也容易在页面刷新或多 Session 切换时拿到过期引用。事件流把后台发生的事实变成稳定协议：Core 发布，Main 路由，Renderer 归并展示。

事件信封显式携带 sessionId，使 UI 能丢弃不属于当前 Session 的事件；turnId 区分同一 Session 的多次执行；seq 用于重放顺序；event id 用于诊断重复。Renderer 的 Zustand 只保存视图状态，不复制工具权限和 Agent 状态机。

缺点是 UI 需要正确处理乱序、恢复和未知事件。V3 协议通过显式版本和稳定 type 降低风险，Renderer 对新增字段应安全忽略。业务真相仍在 Main/Core 与 Storage，不以页面当前显示为准。
