第三部分 · 保证正确运行

终止、安全与恢复

编程智能体会在模型调用与工具执行之间反复循环。可靠性取决于两个问题：系统怎样确认任务已经结束，以及某一步失败后应该继续恢复还是停止。本章沿 SeeCoder 一次 Turn 的完整生命期，解释状态机、停止判断、错误传播、取消链路与重启恢复。

为什么“会停止”与“会执行”同样重要

普通聊天请求通常只有一次模型响应。Coding Agent 需要多轮工作：搜索代码、读取文件、修改、运行测试、读取失败、继续修复。模型每轮都可能提出新动作。如果主程序没有边界，错误决策会形成无限工具循环；如果过早停止，界面可能显示完成，但代码尚未修改或测试仍然失败。

SeeCoder 把停止权放在 TurnRunner。Renderer 负责显示按钮和状态，模型负责提出文本或 Tool Call，最终是否继续由 TurnRunner 根据本轮响应、工具结果、取消信号和预算判断。AgentCore 只提供统一入口与事件出口，后台真实状态是唯一依据。

先区分 Session、Turn 和 iteration

Session 是用户在左侧看到的一条长期会话，保存目标、消息、变更和历史事件。用户完成一个任务后可以继续追问，所以 Session 本身不会在一次回答后结束。

Turn 从一条用户请求开始，到本次任务完成、失败或取消为止。一个 Session 可以包含多个 Turn，同一 Session 同一时刻只允许一个活动 Turn。用户在运行中追加的 Follow-up 仍属于当前 Turn，并在下一次模型调用前注入。

iteration 是 Turn 内部的一次模型决策轮。一次 iteration 可以返回文本、一个 Tool Call 或多个 Tool Calls。工具结果写回后，下一次模型请求进入新的 iteration。主 Agent 每个 Turn 最多 50 次 iteration。

三层关系Session：修复待办项目
├─ Turn 1：空标题不应提交
│  ├─ iteration 1：搜索代码
│  ├─ iteration 2：读取相关文件
│  ├─ iteration 3：应用补丁
│  └─ iteration 4：测试并完成
└─ Turn 2：继续补充边界测试

Turn 状态机保存什么

TurnStatus 是 Core、事件协议和 Renderer 共同理解的运行状态。它描述一项任务当前能做什么，以及用户是否需要采取行动。

状态含义何时进入
queuedTurn 已创建，尚未进入循环startTurn 创建 Turn
running正在构建上下文、调用模型或执行工具TurnRunner.run 开始或等待结束后恢复

waitingInput模型提出结构化问题ask_user 等待回答

queued 通常持续时间很短。TurnRunner.start() 发出的 turn.started 已向 UI 提供 running 状态，后台 run() 随即把内存 Turn 设为 running。Renderer 还维护“调用模型”“执行工具”“等待确认”等更细的 RunPhase，这些只服务界面提示，不替代持久化 TurnStatus。

running → failed / limitReached发生不可继续错误或耗尽迭代预算
任何活动状态 → cancelled同一个 AbortController 向全部后台操作传播取消

一个 iteration 怎样走到停止判断

循环开头先检查 AbortSignal，再设置 iteration 编号。TurnRunner 消费排队的 Steering，必要时加入收敛提醒，然后构建模型请求。模型流结束后，它保存完整 assistant 文本与 Tool Calls。Follow-up 要等当前 Turn 正常完成后才建立新 Turn。

接着分三种情况。纯文本达到输出上限时进入截断恢复；没有 Tool Call 时接受自然结束；存在 Tool Calls 时逐个执行，并把结构化结果写回上下文。工具组完成后再检查 finish、失败次数和迭代预算。

主循环的停止骨架for iteration in 1..50:
  if cancelled: throw cancelled
  response = callModel(context)
  saveAssistantMessage(response)

  if response.finishReason == "length" and noToolCalls:
    compactAndRetryOrFail()
    continue
  if noToolCalls:
    finished = true
    break

  for call in toolCalls:
    results = ToolCallExecutor.executeBatch(calls)
    saveToolResult(result)
    if call.name == "finish" and result.ok:
      finished = true

  if failuresWithoutSuccess >= 3:
    fail("no progress")

if not finished after iteration 50:
  fail("iteration_limit")

正常文本为什么可以结束 Turn

模型返回文本且没有 Tool Call，finishReason 也不是 length 时，Core 把 finished 设为 true。这个分支支持解释、代码阅读和兼容模型：用户只问“这个模块做什么”时，模型给出结论即可结束。

自然结束存在一个权衡。模型可能在代码任务中提前给出总结，没有调用 finish。Core 当前仍会接受，因为强制所有模型必须使用 finish 会降低 OpenAI 兼容模型的适配性。系统提示会要求完成任务时调用 finish，真实可靠性还依赖测试、Trace 和完成摘要供用户核验。

finish 工具提供了什么额外信息

finish 的参数包含 summary 与 verification。它让模型明确声明“工作已经结束”，并列出真实执行过的验证命令。工具成功后，TurnRunner 设置 finished=true；同批结果仍按模型原顺序写回，工具组结束后不再发起下一轮模型请求。

finish 还查询 ContextLedger。只要 Session 已产生文件变更，Core 就检查当前 changeRevision 是否存在成功的 ValidationRecord。验证存在时输出 verificationStatus=verified；缺少当前 revision 的成功验证时输出 warning。

警告不会阻止 completed。解释任务、文档任务或没有测试环境的项目仍可结束。这里的 completed 表示 Agent 控制流已正常收敛，不等同于“代码质量已经被自动证明”。UI 应把验证警告与控制流终态同时展示。

模型输出被截断时为什么不能完成

兼容接口返回 finishReason=length，表示模型触及 maxOutputTokens。纯文本可能停在半句话或遗漏结论，Core 不能把它当作最终回答。

第一次和第二次截断后，Core追加系统恢复提示，要求停止长篇分析、执行最小必要动作并调用 finish；同时强制压缩上下文，再开始新 iteration。连续第三次仍然 length 且没有 Tool Call，Core抛出 output_limit，Turn进入 failed。

如果截断响应已经包含 Tool Calls，当前代码仍会执行已经聚合出的调用。模型接口需要提供可解析的完整参数；不完整参数会在 JSON 或 Zod 校验中返回 invalid_args。

50 次迭代上限怎样工作

主循环固定为 1 到 50。第 46 次开始前，Core 注入一次迭代预算提醒：只剩最后五轮，停止扩大范围，使用已有证据完成必要验证并立即 finish。提醒只发送一次。

第 50 次结束后 finished 仍为 false，Core 抛出 AgentRunError('iteration_limit')。Turn.status 设为 limitReached，对外发出的终态事件仍是 turn.failed，其中 error.code 为 iteration_limit。这样 UI 可以使用统一失败入口，同时从 Turn 状态识别预算耗尽。

子 Agent 有独立上限，每个最多 6 次 iteration。子 Agent达到循环末尾后按当前已收集 summary 完成；模型或执行异常则返回 subagent_failed 给主 Agent。子 Agent失败通常是一个 Tool Result，主 Turn仍可选择其他方案。

SeeCoder 怎样抑制无价值探索

长任务常见退化是重复搜索与读取。Core统计连续只读探索 iteration。达到 4 次后注入提醒，要求根据现有证据实施最小修复，或指出唯一缺失信息。达到 7 次后，新的探索调用返回 exploration_budget_exhausted，不再访问文件。

这个错误属于控制信号。它会显示在轨迹中，但不写入 Ledger 的未解决错误，也不增加 noProgress。模型仍可修改、验证、提问或 finish。只要执行了写入、命令等行动，连续只读计数归零。

“无进展”当前怎样判断

Core 使用 noProgress 计数器。工具返回 ok=false 时加一；任一工具成功时把计数器归零。某个 iteration 没有任何成功结果，并且累计失败达到 3 次，Core抛出普通 Error：“连续三次工具调用失败，判定为无进展”。

这里统计的是连续失败，中间不能出现成功结果。当前实现没有比较工具名、参数和错误码是否完全相同。因此“连续三次相同失败调用”是设计目标的更严格表述，代码目前采用较简单的连续失败规则。探索预算控制信号被排除，用户拒绝审批则作为 approval_denied 失败结果参与计数。

普通 Error 会在外层归一化为 turn_failed。这种统一终止避免模型反复消耗 token，同时也意味着三个不同的可恢复失败可能提前结束。后续若要优化，应基于 call signature 与 error code 判断重复模式，并保持现有硬上限作为兜底。

错误处理先区分局部结果和 Turn 错误

编程过程里，大多数失败属于正常观察。测试退出码 1、补丁上下文不匹配、路径被拒绝、参数缺失，都以 ToolResult.ok=false 返回。Tool Result写入 Session，模型下一轮可以读取错误并修复。Turn保持 running。

模型请求失败、连续无进展、迭代耗尽或 Core 未预期异常会离开主循环，形成 AgentError 和 Turn终态。这两级结构限制故障范围：单个工具失败尽量局部处理，只有无法可靠继续时才结束本次任务。

两级错误边界
ToolResult 错误unknown_tool、invalid_args、patch_failed、command_failed、timeout、approval_denied
处理方式保存结果 → 生成 Observation → 模型重新规划；Turn 通常继续
AgentError模型请求最终失败、output_limit、iteration_limit、无进展或未预期异常
处理方式写入 Ledger → 发出 turn.failed → 清理活动资源；Session 仍可继续

ToolResult 错误包含哪些信息

ToolResult统一包含 ok、output、durationMs 和可选 error。error 只有稳定 code 与 message。例如 run_command 非零退出返回 command_failed，同时 output 保留 exitCode、stdout 与 stderr；apply_patch 冲突返回 patch_failed；Plan 模式副作用返回 plan_read_only。

Core 在 tool.completed 事件中保存完整结果，并把普通失败写入 ContextLedger。Observation Compressor为模型保留错误码、关键诊断、耗时与恢复信息。这样用户界面、模型和日志围绕同一次真实执行，不需要从字符串猜测工具是否成功。

AgentError 为什么有 retryable

AgentError 的实际协议很小：

packages/protocolinterface AgentError {
  code: string;
  message: string;
  retryable: boolean;
}

code供日志、测试和 Trace稳定识别；message给出具体原因；retryable表示外部条件恢复后重新开始 Turn是否有意义。它是说明字段，当前 Agent Core收到模型 error后不会再自动启动一轮主请求。Provider已经完成允许的网络重试，失败后由用户点击“重新尝试”或修正配置。

AgentRunError保留这三个字段。其他未预期异常被转换为 code=turn_failed、retryable=false。协议目前没有 category和 recovery字段；错误类别与恢复提示由 code、message和 UI映射共同表达。

模型服务错误在哪一层重试

ModelProvider对 HTTP 429、502、503、504 和网络中断最多进行三次总尝试。每次重试采用指数退避与随机抖动，并产生 retry事件。401、403、400等通常需要修正 API Key、模型名或请求格式，直接产生 http_状态码 error。

三次尝试后仍失败，Provider产生 ModelEvent error。Core完成本轮模型耗时事件后抛出 AgentRunError，Turn进入 failed。Provider的重试只包围同一次没有本地副作用的模型请求；已经完成的文件写入和命令不会因网络错误自动重放。

模型 Tool Call 错误怎样降级

流式 Tool Call 的 arguments 在响应结束后才 JSON.parse。JSON非法时，parseArgs 返回带 __invalid 的对象，随后 Zod校验失败，形成 invalid_args Tool Result。工具不会执行，模型有机会重新生成参数。

工具名未知时返回 unknown_tool。callId已经执行过时直接复用原 ToolResult，避免副作用重复发生。缺少工具名的片段当前只增加 noProgress，不产生完整 Tool Result；连续出现会进入无进展终止。这是兼容接口输出严重不完整时的保护路径。

摘要失败为什么不会拖垮主任务

语义摘要属于可再生的派生数据。摘要模型请求有独立 AbortController和 30秒超时。非法 JSON、网络错误或超时会发出 context.summary.failed，然后返回 null。ContextBuilder改用确定性摘要继续构建上下文。

摘要失败不增加主 Turn的工具失败次数，也不会产生 turn.failed。用户取消时，主 signal会中止摘要 signal，主 Turn随后进入 cancelled。这个设计体现故障隔离：辅助优化失效时保留核心执行能力。

取消从界面怎样到达全部后台工作

每个活动 Turn有一个 AbortController，保存在 controllers Map。用户点击停止后，Main调用 cancelTurn(turnId)。该函数先 abort主 controller，再取消所有 parentTurnId相同的子 Agent。

等待审批时没有网络轮询。cancelTurn会把等待 Promise解析为拒绝，理由是“用户取消了任务”；等待 ask_user时也会解析 pendingInputs。模型 fetch、上下文摘要和 run_command都收到同一个信号或它派生的信号。Windows命令运行时会使用 taskkill结束进程树。

TurnRunner.run() 在模型流结束后、每个工具执行后都会再次检查 signal。catch 分支优先以 controller.signal.aborted 判断终态，所以底层可能同时返回 cancelled ToolResult，最终仍只发布一个 turn.cancelled。Renderer 收到该事件后把 running 设为 false，并显示后台已停止。

工作区切换为什么要 cancelAll

切换工作区会改变所有工具的根目录。如果旧 Turn继续运行，它可能在用户已经看到新项目时写入旧项目。Main在更新 workspace前调用 core.cancelAll()：中止主 controller和子 Agent，解除全部审批与输入等待，再用新工作区创建 Agent Core。

同一 Session也不允许并发两个活动 Turn。startTurn检查 activeSessionTurns；已有任务时要求用户追加 Follow-up或先取消。这个单写者约束减少消息交叉、ChangeSet顺序冲突和 UI状态串线。

结束时怎样保证资源被清理

正常完成和 catch分支都会写 completedAt，并运行 turnEnd Hook。turnEnd使用新的 AbortSignal，所以用户取消主 Turn后，收尾 Hook仍可尝试运行。Hook错误会产生事件，但不会改写已经确定的 Turn终态。

Core在发布终态事件前释放 activeSessionTurns。UI收到完成、失败或取消后，可以立即启动下一个 Turn。finally继续删除 controller、模式、Skill、语言规则和 executedCalls，并解决仍残留的审批等待。即使终态事件持久化期间出现异常，finally仍尽量清理内存占用。

应用异常退出后怎样恢复状态

JSONL事件记录了 turn.started和终态。应用重启后，replaySessionEvents 只回放数据，不调用模型，也不重新执行历史工具。它恢复消息、ChangeSet和 Checkpoint，并检查已开始但没有 completed、failed或 cancelled的 Turn。

未完成 Turn被标记为 failed，error.code为 interrupted，retryable=true，提示后台执行已停止。重复 hydrate不会重复添加同一中断错误。这样系统不会假装断电前的进程仍在运行，也不会重放可能已经产生副作用的命令。

事件回放还诊断序号乱序、跨 Session事件和孤立 Tool Result。损坏的 JSONL尾行会被忽略，前面完整记录继续读取。恢复后的 ModelMessages再经过 sanitizeModelMessages，孤立 tool消息不会发送给兼容 API。

错误事件怎样进入日志与界面

MainLogger为模型、工具、摘要、子 Agent和 Turn记录 sessionId、turnId、callId、duration、status与 error code。日志不记录 API Key或完整文件内容。Trace使用相同事件重建执行阶段，开发者可以沿 UI → Core → Model → Tool → Result查找故障。

Renderer只把最新 Turn的终态作为当前横幅，防止上一 Turn的失败覆盖正在运行的新任务。模型协议错误、401、429和 timeout会转换为简短标题与建议；其他错误展示截断后的 message，并提供“重新尝试”和“查看详情”。取消使用独立提示，不按失败展示。

当前友好错误映射主要依据 message正则，而非 error.code。这能够兼容部分供应商文本，但维护性弱于稳定 code映射。后续优化应优先按 code映射，再把 message作为兼容回退。

场景一：测试失败后继续修复

用户要求修复空标题提交。模型修改文件后运行测试，命令退出码为 1。run_command返回 ok=false、code=command_failed，并保留失败断言。Core记录 Tool Result与 ValidationRecord(failed)，Turn仍为 running。

下一轮模型读取 Observation，定位 trim处理遗漏，再调用 apply_patch。补丁成功使 revision增加，noProgress归零。模型重新运行测试，结果 ok=true，Ledger记录当前 revision的 passed验证。finish成功，Turn进入 completed。

这个流程把测试失败视为证据。系统没有隐藏错误，也没有在第一次非零退出码后放弃整项任务。

场景二：连续失败后停止

模型第一次调用 apply_patch，目标上下文不存在，返回 patch_failed。第二次仍生成无法匹配的补丁，再次失败。第三次调用 read_file但路径越出工作区，返回 read_failed或 path_denied。期间没有任何工具成功，noProgress达到 3。

Core抛出普通 Error，catch把它转换成 code=turn_failed、retryable=false，Ledger记录错误，发布 turn.failed。Renderer停止加载，显示“任务未完成”，用户可以查看轨迹后调整请求。三个错误内容并不相同，当前代码仍会终止，因为它检查连续失败次数。

场景三：审批等待时取消

Guided 模式下模型请求 write_file。ToolCallExecutor 创建 Approval，把 Turn 设为 waitingApproval，并暂停在 Promise。此时没有模型请求或子进程占用资源。用户点击停止后，TurnRunner 中止 controller，同时执行器解除审批等待。

ToolCallExecutor.execute() 先形成 approval_denied ToolResult；回到主循环后 signal 检查抛出 cancelled。catch 以 AbortSignal 为权威，将 Turn 设为 cancelled，释放 Session 占用并发布 turn.cancelled。测试验证目标文件没有创建，随后同一 Session 可以启动新 Turn。

当前实现仍有哪些边界

自然文本无 Tool Call会被接受为 completed，因此完成质量仍需结合验证证据判断。无进展规则只统计连续失败，没有比较调用签名。retryable目前用于表达错误性质和 UI决策，Core不会自动新建 Turn。错误协议没有统一 category与 recovery字段，用户提示仍有少量基于 message的判断。

TurnStatus没有单独的 planning、waitingTool和 verifying；这些阶段由 UI RunPhase、计划事件和工具事件表达。当前状态模型较小，便于前后端保持一致。只有当新状态能改变持久化恢复或用户操作权限时，才值得加入协议。

为什么采用分层错误处理

把所有异常直接变成 turn.failed 会降低 Agent 自主修复能力；无限重试又会浪费 token 并扩大副作用风险。SeeCoder 在三层设置边界：Provider 处理短暂网络故障；ToolResult 把局部执行失败交给模型；TurnRunner 对取消、截断、无进展和迭代预算做最终裁决。

状态、事件和错误码都由自研协议定义，避免关键控制流隐藏在 Agent SDK中。追加式 JSONL保留每个决定的结果，重启时只恢复事实，不重新执行动作。这些选择共同保证任务能够继续、能够停止，也能够解释为何停止。

最后记住一条判断顺序

答辩时可以这样说明每轮先检查取消
→ 构建上下文并调用模型
→ 模型错误先经过 Provider 的有限重试
→ 完整保存文本和 Tool Calls
→ length 纯文本先压缩恢复，连续三次失败
→ 无 Tool Call 接受自然结束
→ 有 Tool Call 则执行并把局部错误反馈给模型
→ finish 成功后结束，并检查当前 revision 的验证
→ 连续三次工具失败判定无进展
→ 50 轮仍未收敛标记 limitReached
→ 任何终态都运行收尾、释放 Session 占用并清理资源

一句话概括：工具错误尽量留在循环内恢复，模型与系统错误由 TurnRunner 结束 Turn，取消通过同一个信号到达全部后台工作，所有终态都写入事件并释放资源。
